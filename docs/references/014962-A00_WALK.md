January 1989, and **it describes SR10 — the release this project runs**, where
`AEGIS_Internals_and_Data_Structures` describes SR9.0. Third document off the
shelf `SOFTWARE_SHELF_WALK.md` audits, read for one reason: the DS5500 stops in
a mechanism `004977-02` and `[AEGIS]` describe at the wrong release.

## It names the thing the DS5500 is executing

`PROJECT_STATUS.md` has a user process calling through a pointer taken from the
`A5` global-data area into a page of zeros:

```
00803112  206D xxxx   movea.l d(a5),a0      ; a0 <- 0091709C
00803116  4E90        jsr     (a0)
```

**Chapter 2 calls that pointer a transfer vector and says who fills it in.**

> "When a program that makes calls to global library entry points is loaded,
> **that program's transfer vectors are filled in** with the value" [from the
> Known Global Table]

> "The Domain/OS compilers can generate **position-independent code** (PIC).
> This has the effect of **inserting an extra level of indirection for each
> external procedure and each reference to global data**."

> "**All load-time relocation takes place in the data area**, which already must
> be writeable anyway."

So the indirection is by design, the vector lives in the writable data area, and
the loader patches it. That is `movea.l d(a5),a0; jsr (a0)` exactly.

**And chapter 4 says what happens when the vector is *not* filled in**, which is
the case this machine is in:

> "**Dynamic Linking.** Domain/OS supports a limited form of dynamic linking. A
> program loaded with references to undefined procedures has **a special jump
> vector created which points to a dynamic link snapper routine**. (References
> to undefined procedures were either not found in the KGT or found and
> specified as **load-on-reference**.)
>
> During execution, a call to this undefined symbol is vectored to the dynamic
> link snapper routine and is passed the ASCII text of the symbol name. It looks
> for the symbol in the KGT. If the referenced library is not loaded yet, **it is
> loaded, the jump vector is patched to the symbol, and the routine is
> executed.** ...
>
> **If the symbol is not found, a fault is generated to the program.**"

**An unresolved vector is supposed to point at the snapper, not at zero.** That
is a sharp, checkable statement about where `0091709C` should have pointed, and
it is the first thing this project has that says what the *correct* value would
have been rather than what the observed one is. **Not yet acted on**, and
deliberately: whether the vector was never patched, patched with a snapper
address that is itself in an uninitialised page, or patched correctly and then
overwritten, are three different bugs and nothing measured yet separates them.

## The Known Global Table is three tables

> "The KGT actually consists of three tables:
>
> - the **private KGT**, symbol entries currently loaded into the private A space
>   of the process ... the ASCII name, the address of the symbol, and information
>   as to the type of symbol (function, data, or common). **The table is indexed
>   by a hash of the symbol name.**
> - the **known library table (KLT)**, symbol entries that are in shared
>   libraries ... the ASCII name, a reference to the shared library so that it
>   can be loaded when needed, and a set of flags indicating the behavior that
>   this library should have (**loaded on program execution or loaded at program
>   reference**). The KLT is **inherited by child processes** (created via fork,
>   exec, or `pgm_$invoke`).
> - the **global KGT**, public symbols known to all processes ... Entries contain
>   **a compressed form of the name (32 bits)**, its type, and either an address
>   of the symbol in global space or information similar to that in the KLT."

`[AEGIS]` §9.1 places a "private KGT (2 segments)" in every process's private
address space and a "Known Global Table" in user global space; this says what is
in them.

## Four partitions, and a third address-space size

> "Domain/OS supports the concept of global user address space. Actually, it
> divides the address space into **four partitions: global supervisor, global
> user, private supervisor, and private user**."

Which is `[AEGIS]` Figure 9-1's four areas under SR10 names.

**And `/etc/sys.conf`'s compatibility flags give a size `[AEGIS]` does not
know.** SR9.0 has 16 Mbyte and 256 Mbyte systems; this lists

> `not_16mb_va` — do not load this global on a 16MB virtual address space
> machine (DN300, DSP80)
> `not_64mb_va` — do not load this global on a **64MB** virtual address space
> machine (**DN330, DSP90, DN5x0, some DN3000**)

so there is a **64 Mbyte** class between them, and *some DN3000s are in it* —
which matters to a project whose reference machine is a DN3500. **Recorded as a
question**: which class a DN3500 and a DS5500 fall into is not stated here, and
nothing in this core depends on it yet.

## The configuration file, and how a library gets loaded at all

`/etc/sys.conf`, read at boot: `lib[rary] shared_library_pathname flags`, the
path "either relative to the `/lib` directory or an absolute pathname", flags
`global`, `dynamic`, `optional`. **"If global or dynamic is not specified, the
library is loaded at program execution time."** Global libraries are loaded once
into global user space at boot and "have no cost at program load time"; they
"must have no duplicate symbol definitions". The shells add `inlib` and `llib`
as internal commands, which is `004977-02`'s INLIB from the user's end.

**Global libraries have four classes of storage**, and this is the fourth
independent statement of the zero-fill rule this session has now collected:

> "read-only procedure text, global storage (**which gets turned into read-only
> after library initialization**), dynamic storage (run-time stack), and
> **process-private storage (which is zeroed at the beginning of each
> process)**."

`004977-02` §4.4.1 says the same in binder terms — `data$` initialised once then
made read-only, every other data section zeroed per process — and `[AEGIS]`
§29's `pm_$init_first` "makes the global data section read-only". Three
documents, one rule.

## The rest, condensed

- **Backing store is allocated dynamically.** "Domain/OS allocates backing store
  for disk space dynamically, as it is requested by a process. Disk space does
  not have to be designated in advance as file space or swap space." No swap
  partition, which is why INVOL's paging file is a *file*.
- **Page tables are pageable.** "Domain/OS can swap the page tables for an
  active process out to the disk ... a fixed upper limit on the amount of
  physical memory devoted to page tables, with no effect on the amount of
  virtual address space a process can use." A 68040 table search can therefore
  fault on a *descriptor*, which this core's `AP_M68040_MMU_FAULT_SEARCH_BUS`
  and `[040]` §8.4.6.2's "bus error during table search" both anticipate.
- **Chapter 5, the I/O system**: drivers are reached through an **entry point
  vector (EPV)**; the disk EPV's entries open a device and return drive
  parameters, and service multi-block transfers. Drivers register their
  interrupt handlers with the I/O resource manager at initialization, so "the
  only entry point that needs to be directly exported from the driver module" is
  the initialization one.
- **Chapters 6-8** — extended ACLs over the UNIX model, the RGY registration
  system, the Network Computing Architecture and its NIDL/NDR/RPC — are
  distributed-systems architecture with nothing this core models. Read in the
  condensed pass and recorded as yielding nothing.
