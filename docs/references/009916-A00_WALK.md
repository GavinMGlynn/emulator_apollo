First printed June 1987; this is the August 1988 printing. It supersedes three
earlier manuals: *Planning and Preparing a DOMAIN System Site*, *Planning Domain
Internets* and *Planning for TCP/IP*.

This is `RING.md`'s `[PLAN]`. Finding 9 and `ap_ring_medium.h` cite it, and it
was never walked. A filename match of the software shelf then found that no
record covered it (`CONTENT_TRIAGE.md`).

## What it settles for this core

**1. Finding 9's quotation is not in this document.** Corrected, with no
behaviour change.

- **The claim.** `RING.md` finding 9 attributes to `[PLAN]` "a single ring
  scaled to well over a hundred nodes without the degradation contemporary
  Ethernet suffered — the reason Apollo kept it proprietary".
  `ap_ring_medium.h` puts "well over a hundred nodes" in quotation marks.
- **The search.** Neither phrase occurs anywhere in the 166 pages' text.

What the document actually says:

- **§2.2.** The ATR is "our proprietary high-speed token-passing ring". It lets
  you "Connect hundreds of nodes in a single network without using external
  transceivers and/or repeaters". And: "The token-passing mechanism results in a
  very fast network arbitration which allows the ATR to support heavy data loads
  without significant service degradation."
- **§4.1.1.** "You can install hundreds of Apollo nodes in a single Apollo Token
  Ring network ... We place no limit on the number of nodes you can install in a
  single ring (though there is a practical limit of 1024 nodes)". It then
  recommends "a Domain internet of several smaller rings" for reliability.
- **Table 2-1**, read as an image. For serially-wired and star-wired rings the
  maximum is "Several hundred". For a star-wired ring the ideal is "1 to 8 nodes
  per loop", with "no limit on number of loops".
- **§2.4.** The 802.3 network's disadvantage is "the loss of performance which
  can occur as a result of the collision and retransmission".

**So finding 9's substance stands, but its wording does not.** The document does
say hundreds of nodes, proprietary, and no degradation under load where 802.3
degrades. It never gives a reason Apollo kept the ring proprietary. The header's
quotation is replaced with the document's own words.

`AP_RING_MAX_NODES` stays at 64. The comment only ever justified it as enough
for the rings this project runs, never as a hardware limit.

**2. Table 3-1 is a second witness to the cable model.** Read as an image, its
electrical values are:

- operating voltage 30 V rms minimum;
- delay 1.3 ns/ft maximum;
- 18 AWG solid copper;
- conductor 7.5 Ω and shield 5.2 Ω per 1000 ft, both maximum;
- impedance 75 Ω and capacitance 17.3 pF/ft;
- velocity of propagation 78%;
- attenuation of 0.70, 1.40 and 2.10 dB per 100 ft at 10, 50 and 100 MHz
  (±0.10).

Every value matches `RING.md` finding 141, taken from `[MAC]` Table A-1, the
source of `ap_ring_medium.h`'s 51.2-bit-time kilometre. **Two documents, one
table: nothing changes.**

The physical half has two printed unit slips:

- the dielectric outside diameter reads "45.7 mm (0.180 in)", but 0.180 in is
  4.57 mm;
- the conductor diameter reads "0.00091 to 0.01016 mm (0.036 to 0.040 in)", but
  that inch range is 0.91-1.016 mm.

**3. §4.1.2 repeats `[MAC]` §3.4's 1 km limit between active nodes, and adds
what makes a node active:**

> Apollo nodes transmit and receive data through a set of relays. The nodes are
> considered active when these relays are connected to the network and the node
> is receiving, reclocking, and transmitting data. Normally, the relays are
> connected when the node is running the operating system. However, the relays
> are also connected when the node is performing diskless operations (e.g.,
> booting from another node) or running certain diagnostics from the Mnemonic
> Debugger (MD) program. The relays bypass the network when the node is powered
> off, removed from the network with the netsvc -o command, or sitting idle in
> the MD.

It adds that nodes logically disconnected with `netsvc -n` stay electrically
connected. Several in a row add enough attenuation to break communication
between the remaining active nodes.

`ap_ring_phy.h` models `[MAC]` §3.5's relays as switched "under command of the
controller". When they are commanded is therefore software's business, and this
passage is consistent with the model. Nothing owed.

*The glossary contradicts §4.1.2.* Its **Active Node** entry says the relays
bypass "when a node is logically disconnected with the netsvc -n command,
sitting idle in the MD, or powered off". §4.1.2 gives `netsvc -o` for removal,
and says `netsvc -n` leaves the node electrically connected. Recorded, not
resolved; the core has no `netsvc`.

**4. Tables 7-1 and C-1, the network controllers**, both read as images.

- **DN3000, DN4000, DSP3000 and DSP4000** use the "Apollo Token Ring Network
  Controller-AT (earlier systems also use a 2-slot version of this controller
  board)". That is a second witness to `008778-03` Table 2-10's "Apollo Token
  Ring (two-board set)". Their 802.3 controller is the "802.3 Network
  Controller-AT".
- **An AT-bus node takes "Up to 4 controllers total, maximum of 2 ATR and 2 IEEE
  802.3"**, repeated by §7.3 and Figure 8-12.
  - This core fits at most one ring card, since `ap_model.h`'s `has_ring` is a
    bool. That is a configuration the model does not offer, not a part it gets
    wrong.
  - Nothing here says where a second card would decode — no address, IRQ or DRQ
    — so it is recorded rather than made a gap.
- **The other buses:**
  - DN5xx-T VME: up to 3, 1 ATR and 2 802.3.
  - DN10000 VME: up to 4, 2 ATR and 2 802.3.
  - DSP90 MULTIBUS: the native ATR controller, plus one of Domain/BridgeA (T1) or
    EtherController-MB, both point-to-point only.

## What else it contains

**Chapter 1** is planning goals only.

**Chapter 2** covers:

- the ring's features:
  - each node "constantly monitors the presence of its upstream neighbor ... and
    transmits a failure report ... if it is unable to detect a coherent signal"
    (beaconing);
  - topology determination;
  - one token, always circulating in the same direction.
- serially-wired rings, and star-wired rings built with network switches;
- DFL-100 fibre extension, which forms "a single, larger ring" with no limit on
  the number of DFL links;
- 802.3 as CSMA/CD;
- internets, routing nodes and gateway nodes, and that "an internet can increase
  performance by reducing token latency (in an ATR network)".

**Chapter 3** covers:

- Table 3-1, above;
- the Domain/DQC wall unit, with cable assemblies of 3.04 m (10 ft) or 25 ft; it
  ships with Series 3000 and 4000 nodes;
- BNC connectors, the network switch (8.01 × 8.65 cm) with its loop bypass, and
  cable tags;
- fibre:
  - a DFL link up to 3 km, with an error rate of "one bit error per 10^9 bits";
  - Table 3-3, as an image: 50/125 µm cable at 3.0 dB/km, 850 nm;
  - Table 3-4, as an image: 62.5/125 µm cable at 5.0 dB/km (850 nm) and 3.0 dB/km
    (1300 nm);
  - both cables 160/200 MHz·km, with a 2 km maximum single length;
  - Table 3-5's connectors: 905 and 906 SMA, and ST.

**Chapter 4** covers:

- **ring layout:**
  - 1 km between active nodes, and five to eight nodes per loop;
  - diskless nodes on their partner node's loop;
  - coax kept 24 in from AC wiring;
  - 30 cm of cable allotted per DQC termination and 6 m per BNC termination.
- **DFL-100 placement:**
  - a fibre link of up to 3 km, with no serial chaining of units;
  - **at most 300 m of coax between a DFL-100 and each adjacent node, "because
    the DFL-100 unit does not contain signal amplification hardware"**;
  - no back-to-back units, because data between them "is not remodulated or
    reclocked";
  - redundant pairs and remote control.
- the network control room, and the layout diagram (Figure 4-7).

**Chapters 5-6** cover IEEE 802.3 media:

- thick segments of 500 m and thin segments of 185 m;
- 100 transceivers per thick segment, and 1024 nodes per network;
- at most five segments, four repeater sets and three populated segments in a
  path;
- link-segment propagation delay of at most 2570 ns (5140 ns for a double link);
- the SQE heartbeat;
- jabber control that cuts output after 20-150 ms and resets after 250-500 ms of
  silence;
- AUI cables up to 50 m;
- cable section lengths of 23.4, 70.2 and 117 m.

Nothing here reaches `device/ap_3c505`, which models the controller and not the
medium.

**Chapter 7** covers point-to-point links over an 802.3 link segment or T1:

- **the T1 interface device:**
  - 1.544 Mbit/s, full duplex, with data clocks of 1-2 MHz;
  - RS-449/RS-422 signalling;
  - within 25 ft of the node, the interface cable's length;
- **the carrier's guarantees:** 1.36 Mbit/s and 98% uptime;
- the two T1 devices tested, and Domain/Bridge G703 at 2 Mbps;
- Table 7-1, above.

**Chapter 8** covers:

- resource placement, redundant paths and limiting access;
- **the Domain internet rules**:
  - at most 16 hops;
  - at most 64 networks, agreeing with `[AEGIS]`;
  - links of at least 1 Mbit/s;
- adaptive routing by fewest hops;
- 32-bit network numbers, agreeing with `[AEGIS]`;
- TCP/IP's 30-hop limit, and AT-bus and MULTIBUS gateway topologies (Figures 8-7
  to 8-15).

**The appendices:**

- **A:** Instant Apollo catalogue part numbers (Tables A-1 to A-4).
- **B:**
  - Belden cable part numbers (Tables B-1 to B-3);
  - Table B-4, read as an image, permitting 14 dB (+0/−0.5) of loss on 50/125 µm
    links and 16 dB on 62.5/125 µm;
  - the attenuation examples, and installation guidelines.
- **C:** Table C-1, above.

**The back matter:**

- the network and internet planning checklists;
- the glossary, which names **Broken Link Detection** and **Topology
  Determination** as ring features and carries the Active Node entry above;
- the index;
- three reader's response forms.

## Slips in the document, none affecting this core

- **§8.3.1** gives "a maximum end-to-end delay of 100 microseconds (ms)".
  §7.2.2.2 gives the same limit as "100 milliseconds".
- **Figure B-1**, read as an image, computes a 3 km 50/125 µm link at **4.0
  dB/km**, footnoted "Maximum attenuation of cable at 850 nm, as specified".
  Table 3-3 specifies **3.0 dB/km**. At the table's figure the example link loses
  11 dB, not 14.
- **Figure B-2** writes its failing case as "16.0 dB ≥ 18.0 dB" and then says the
  loss exceeds the maximum. The inequality is the budget to meet, not a result.
- **Figure 4-2**'s label, in the text layer, gives the fibre maximum as "3 Km or
  9243 ft". The prose gives 9843 ft, which is what 3 km is.
- **Table 3-1**'s two diameters, and §4.1.2 against the glossary on `netsvc -n`,
  both above.
