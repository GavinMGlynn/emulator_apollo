June 1987, the **SR9 edition** of the manual whose SR10 successor is
`000959-A00_WALK.md`. `CONTENT_TRIAGE.md` ranked it first of everything left on
the shelf — **504 hardware terms**, four times the density of anything else.

**Read as a pair with its successor**, because the difference between two
editions of the same table is a fact neither edition states.

## The tape controller moved, and that explains a contradiction this project solved by arithmetic

The two editions print the same Table 3-1 a year apart:

| | `000959-10`, Jun 1987 | `000959-A00`, Jul 1988 |
| --- | --- | --- |
| Tape Controller | **`218-21F`** | **`200-207`** |
| Ethernet | `300-310` "Ethernet Controller" | `300-307` and `310-317` "802.3 Network Controller-AT" and its alternate |
| Ring | `220-23F`, `320-33F` "Domain Ring Controller" | the same two, "Apollo Token Ring Network Controller-AT" |

**`board/ap_tape.h` had already concluded the tape is at `200`**, and it did so
the hard way: `008778-03` Table 2-9 prints `218` while its own physical column
gives `050000`, and this board's mapping sends `218` to `050C00` and `200` to
`050000`. The `008778-03` walk hit that arithmetic three separate times and each
time preferred the physical column. `002398-04` p. 12-1 later gave `200`
outright.

**Now the `218` has a provenance.** `008778-03` is **August 1987** — one month
after this edition — so its prose carries the address of its own moment, and the
SR10 manual prints the moved one. *The wrong value was once right*: a reader
working from a 1987 document would place the drive at `218` and be following the
manual correctly. `ap_tape.h` now records that, because "a self-contradicting
table" and "a table that was overtaken" are different things to know about a
source.

## The AT mapping rule, printed identically in both editions

> "Ten-bit consecutive addresses in the I/O address space are mapped into
> processor address space in groups of eight bytes: each group is assigned the
> first eight bytes of a different, but consecutive, page (1024 bytes). Thus,
> the first 1024 addresses in AT-compatible address space (0-3FF) map to 128
> physical pages (40000-5FFFF) in processor address space."

Word for word what the SR10 edition says, and what corrected `ap_disk.h` and
`ap_board.c` — see `000959-A00_WALK.md`. **Two editions agreeing is worth
recording**: the rule was not a late clarification.

## Table 3-2 differs too, and in the direction of more graphics

| Physical | `000959-10` | `000959-A00` |
| --- | --- | --- |
| `0A0000-0BFFFF` | Color or Alternate Monochrome Graphics | the same |
| `0C0000-0DFFFF` | Alternate Monochrome Graphics | Alternate Monochrome **or Apollo Token Ring at `0D0000-0DFFFF`** |
| `0E0000-0FFFFF` | Alternate Color Graphics | Alternate Color **or Alternate/Second Single-Board Ring at `0E0000-0EFFFF`** |
| `100000-8FFFFF` | Main Memory | Main Memory, "on the DN4000 this area is not occupied by main memory" |

**The single-board ring appears between the editions**, taking two of the
graphics alternates' ranges — which is the generational fact behind
`RING.md`'s "AT board generation" distinction.

## The other two buses

Chapters 1 and 2 are the **MULTIBUS** and the **VMEbus**, neither of which the
machines this core models carry. Chapter 1 gives MULTIBUS compliance levels in
IEEE-796 notation ("MASTER D16 M16 I16 VO L"), the processor-to-MULTIBUS address
translation, a 20-bit MULTIBUS with 3 Mbyte of memory wrapping "65K … as a
reference to 1K", and the byte-lane rule that "single byte transfers always occur
on MULTIBUS data lines 0 through 7". Chapter 2's Table 2-1 is "Address Space
Allocated for **DN570/580-T** VME Devices", with a note that part is "available
only on DN570-T workstations", and §2.6.2's DDF for a VME device.

**Recorded and not pursued**: no model in `ap_model.c` has either bus, and the
`019411-A00` walk established the DS5500's is the AT bus retained from the
DN3500. If a DN5xx-T is ever modelled this chapter is where its address space
is.
