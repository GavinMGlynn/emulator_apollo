## What it changes in this core: nothing. What it changes is a diagnosis

**The DS5500's remaining symptom is correct behaviour.** A user process was
calling through a pointer at `0091709C` into a page of zeros, and the working
assumption was that something had failed to fill it. §4.4.1 and Appendix C say
the page is *supposed* to be zero:

> "If the static data is stored in a section other than `data$`, then the loader
> ignores the values specified in source code. Instead, when you boot your
> workstation or create a process, **the loader automatically sets the value of
> all static data in the section to zero.** Each process has its own private
> copy of this section, **and the virtual addresses the section occupies are the
> same for every process.** Most importantly, the loader gives this section the
> read/write attribute. Therefore, although you cannot force the loader to
> initialize this section at process creation, **you can initialize the data the
> first time that a running program accesses the installed library.**"

That is `00900000`–`0091E000` exactly: private, per-process, fixed virtual
addresses, read/write, zero-filled at creation, and initialised by the program
itself — which is what the copy loop at `008030F0` is doing when this core
watches it take sixty demand-paging faults across that range and service every
one. **A zero page there is not a fault to chase.**

Appendix C says the same thing as a section attribute, which is the mechanical
form of it:

> "**Zero Attribute.** A section may or may not have the zero attribute. If a
> section has the zero attribute, then the loader sets all of the section's
> bytes to zero at runtime. A section with the zero attribute must also have the
> read/write attribute."

And a real librarian map on p. 73 shows it in use, on a C module's data section:
`00000024 00000000 Concat Data Zero`.

*Two documents agreeing.* `AEGIS_Internals_and_Data_Structures`'s system
initialisation sequence, step 19, is "Makes the global data section read-only",
which is the other half of §4.4.1: `data$` is initialised once at boot or DM
restart and then write-protected, while every other data section is zeroed per
process and left writable.

## The section attribute set, complete (Appendix C, pp. 97-98)

Eight groups. The bold part is the abbreviation that appears in a binder `-MAP`
or librarian `-LIST` listing.

| Attribute | Rule |
| --- | --- |
| **Abs**olute | begin the section at a fixed virtual address; no high-level-language control |
| **Data** / **Instr**uction | mandatory, exclusive; users cannot control either |
| **Installed** (MARKSECTION) | the section may share data with a same-named section |
| **Long** / **Quad** / **Page**-aligned | mandatory, exclusive: a multiple of 4, 8 or **1,024** bytes |
| **Look**_installed (LOOKSECTION) | the non-installed side of the same sharing |
| **Overlay** / **Concat**enated | mandatory, exclusive: overlay components "share the same address space at runtime", concatenated ones are placed one after another. *"Mixed" is not an attribute* — it marks an attempt to combine both, and the binder then assumes overlay |
| **R/O** / read-write | read-only is write-protected, and "reduce[s] system overhead at runtime because the operating system doesn't have to copy the sections out to disk" |
| **Zero** | the loader zeroes every byte at runtime; requires read/write |

**The page size is 1,024 bytes and the manual states it two ways.** §2.4's
`-ALIGN` page says "a page (**8,192-bit**) boundary"; Appendix C says "a
multiple of **1,024 bytes**". The bit-denominated form is the trap — read
quickly it looks like 8,192 bytes — and the two agree only once converted. This
is the same 1,024-byte page the volume layout uses, where a *record* is a
*page*.

## The rest of what the document gives

- **Five kinds of installed library** (§1.5): user-defined installed libraries;
  object files installed with `-INLIB`; system-defined installed libraries;
  system-defined global libraries; the user-defined global library. Only the
  last two survive a process, and the user-defined one is `/lib/userlib.private`
  — "the loader automatically executes the main program of the object file
  stored in `/lib/userlib.private` if there is one", which is why the internals
  document's step 17 resolves it by name.
- **The loader's job, stated plainly** (§1.6): "A very important function of the
  loader is to resolve outstanding external references in your program with
  global symbols defined in the installed libraries. Thus, you might think of
  the loader as sort of an internal binder utility." There are no loader options
  and no way to talk to it.
- **Limits** (§1.7): the combined number of sections and marked global symbols
  cannot exceed **3,072**, per object module *and* per installed library; only
  the **first 32 characters** of a global variable or section name are
  significant. The preface dates the first figure: "We increased the maximum
  number of sections per module **from 2048 to 3072**" since SR9.0, so a
  pre-SR9.0 image is bounded differently.
- **Sharing takes both attributes** (§2.4, pp. 41-42): a section shares data
  only when `LOOKSECTION` is set on the non-installed side *and* `MARKSECTION`
  on the installed side. Both are off by default, and only sections with all
  three of **data, overlay and read/write** are eligible — a FORTRAN `COMMON`, a
  Pascal named `VAR` section, or a C global variable.
- **The C compiler makes one section per global variable**, which is why
  `-MERGEBSS` exists to fold them into a single `BSS$`, and why the 3,072 limit
  "primarily benefits C programmers".
- **Every DOMAIN global symbol contains `_$`** (§4.6) — `pas_$write`,
  `stream_$get_rec` — deliberately, so user symbols cannot collide with library
  ones. A useful filter when reading a symbol table out of a running image.
- **Start address rules** (§3.4): one possible start address wins; several, and
  the binder takes the first it encounters; none, and it searches unloaded
  library modules, but only if it had to scan the libraries anyway.
  `-ENTRY` overrides. `<APOLLO_C_STARTUP>` appears in the p. 63 cross-reference
  listing as the C runtime's own entry symbol.
- **Multiple definitions resolve by installation order and rebind on exit**
  (§4.6): the loader keeps using the first library's symbol for the life of a
  running program, and a later installation takes effect only for the next one.
- **`-SYSTYPE`** stamps the output with `sys3`, `sys5`, `bsd4.1` or `bsd4.2`,
  and the binder refuses to mix systypes across input files.

## Two internal inconsistencies, recorded rather than smoothed over

- **p. 41 cites the wrong appendix.** "(See Appendix B for a description of all
  attributes.)" — Appendix B is the *librarian* error list (pp. 91-96); the
  attributes are Appendix C (pp. 97-98). p. 56 cites C correctly, so the
  document contradicts itself and the correct pointer is the later one.
- **The Reader's Response form** on pp. 115 and 117 gives the document title as
  "DOMAIN Binder and **Language** Reference".
