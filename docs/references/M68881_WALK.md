## The 4096-ULP question is closed, from its own page

`ap_m68882_accuracy.h` recorded §4.3.2's "one unit in the last place of double
precision (which is equal to **4096** units in the last place of extended
precision)" as disagreeing with the arithmetic — a double ULP is 2⁻⁵² and an
extended ULP 2⁻⁶³, so the conversion is 2¹¹ = **2048**. It offered a reading
(a ±1 ULP bound spans a 2 ULP window), called it a guess, and recorded that
neither `[PRM]` nor the 68040 manual restates the conversion.

**Nobody had read §4.3.2's own worked example**, three paragraphs below:

> the relative difference between the correct result and the result calculated
> by the FPCP is 2⁻⁵⁷ (assuming an extended precision result) ... **This
> difference corresponds to an error of 64 units in the last place.**

2⁻⁵⁷/2⁻⁶³ = 2⁶ = 64. So the manual converts by the **plain ratio**, with no
doubling — which is exactly the reading the window guess proposed, and this
excludes it. Under the same convention one double ULP is 2⁻⁵²/2⁻⁶³ = 2048.

**4096 is a documentary error, an off-by-one in the exponent.** Both constants
stay as printed and the test still asserts the discrepancy; what changed is that
it is explained instead of flagged.

## `FATANH`'s infinity signs are transposed **twice**, and the code is right

`ap_m68882_transcendental.c` already overrode the `FATANH` page on mathematical
grounds: `atanh(x) = ½ln((1+x)/(1−x))`, so `atanh(+1)` is `+infinity`, and the
page's sentence has the two signs the other way round. Its comment calls this
"the one place in the session where a manual defect is corrected rather than
transcribed".

**§6.1.6 repeats the transposition**: "For the FATANH instruction, return a
+infinity if the source operand is −1; or a −infinity if the source operand is
+1."

Two statements, one error — which is what a sentence copied between an
instruction page and an exception chapter looks like, and not what two
independent derivations would look like. Both places' *operation tables* still
agree with the mathematics; only the prose is transposed, in both. Recorded in
the code, because a second witness looks at first like a reason to reverse the
decision and is not.

## A false start worth recording

§4.5.5.2: "The input operands to these instructions are assumed to be single
precision values, but no checking is performed to verify the inputs (**each
mantissa is truncated to 23 bits**, and the exponent is accepted as an extended
precision value)."

I read that, assumed a gap, and implemented it a second time.
`ap_m68882_single_mul` already calls `truncate_to_single`, which cites the same
sentence, masks the same bits, and additionally handles NANs and infinities —
which the duplicate did not. Reverted; the file is byte-identical to before.

**The tell was the test.** The first version passed with the new code removed,
because the behaviour was still happening elsewhere. *A test that cannot fail is
the instrument saying the premise is wrong.* The lesson is
`reference-search-is-not-a-code-check`, and it cost a round trip.

What *was* missing is a test that discriminates, since every existing `FSGLMUL`
case used operands exactly representable in single precision, where truncating
the inputs and rounding the result agree. `1 + 2⁻²⁴` separates them, and
`FMUL.S` on the same operands is the control.

## §7 settles a question the `[030]` walk had to leave open

The `[030]` §10 walk found that an addressing-mode refusal on a coprocessor
instruction is an **F-line**, not a protocol violation, and fixed four sites.
It left **three** open, because Table 10-6's split turns on the valid-EA class
the *coprocessor* declares — and `[030]` cannot state that, since it is the
68882's. They were recorded in `M68030_WALK.md` to settle here.

**Table 7-5, *Evaluate Effective Address and Transfer Data Primitive
Encoding*, declares them**, per opclass:

| Opclass | Instruction | Valid `<ea>` |
| --- | --- | --- |
| `010` | `F<op> <ea>,FPn` | `101` Data (lengths 1/2/4), `110` Memory (8/12) |
| `011` | `FMOVE FPm,<ea>` | **`001` Data Alterable** (1/2/4), `010` Memory Alterable (8/12) |
| `100` | `FMOVE <ea>,FPcr`, `FMOVEM <ea>,FPcr_list` | `111` Any, `101` Data, `110` Memory |
| `101` | `FMOVE FPcr,<ea>`, `FMOVEM FPcr_list,<ea>` | `011` Alterable, `001` Data Alterable, `010` Memory Alterable |

**So the store's refusal is an F-line.** For `FMOVE FPm,<ea>` the declared class
is Data Alterable, which excludes the nonalterable modes outright — so a
`(d16,PC)` destination is the *class mismatch* Table 10-6 puts in its F-Line
column, and never reaches the Protocol column's "Attempt to Write to
Nonalterable Address **Even if Address Declared Legal in Primitive**". That
clause describes a primitive declaring `101` Data or `111` Any and then asking
for a write, which the 68882 never does for a store.

`store_fp_destination` returned vector 13 and cited exactly the clause that does
not apply. Corrected to vector 11. *Verification: `step_suite`'s store test
changed vector; the source direction in the same test is the control, and still
runs, which is what keeps this the direction's rule rather than the addressing
mode's.*

The remaining two open sites — `transfer_fp_control`'s class check and `FScc`'s
— are opclass `100`/`101` and the conditional dialogue, and are still owed:
opclass `100`'s declared class varies with length (`111` Any at 4 bytes), which
this core's separate register-direct and immediate arms may already cover.
Recorded rather than changed.

## Table 7-2's CIR characteristics, field for field

`ap_m68882_cir.c` matches all thirteen rows: Response `$00` read-only, Control
`$02` write-only, Save `$04` read-only, Restore `$06` R/W, Operation Word `$08`
and Operand Address `$1C` **not implemented on the MC68881**, Command `$0A` and
Condition `$0E` write-only, Operand `$10` 32-bit R/W, Register Select `$14`
read-only, Instruction Address `$18` 32-bit write-only, and `$0C`/`$16`
reserved — plus the access rule, "if a register is read only, write accesses to
that location are ignored; while read accesses of a write-only register **always
return all ones**", which `ap_m68882_cir_unreadable_value` returns at each
register's own width and explains why it is not zero.

## Verified against this core, and holding

- **§2.2.2's `FSGLDIV`/`FSGLMUL` exception**: "regardless of the precision
  specified by the PREC bits, these instructions round the result mantissa to
  single precision and generate an extended precision exponent which may be out
  of range for a single precision number." `ap_m68882_arith.c` carries
  `precision` and `range` as separate parameters for exactly this, and says why
  folding them would make those two instructions overflow where the part does
  not. §6.1.4 and §6.1.5's NOTEs restate it from the exception end.
- **§2.3.4's five AEXC equations**, including the two most easily simplified
  wrong: `AEXC(UNFL)` needs `EXC(UNFL ∧ INEX2)` where every other term is an OR,
  and `AEXC(INEX)` accrues on `OVFL` as well as the two INEX bits.
- **§6.1.9's exception priority** — BSUN, SNAN, OPERR, OVFL, UNFL, DZ, then
  INEX — with the `INEX2`-through-`ENABLE(INEX2)`-on-overflow case that a plain
  bit scan would miss. *One comment corrected*: it claimed the priority "is not
  the bit order", and §2.2.1 says it is ("organized in decreasing priority, left
  to right"). The code was right; the reason given for it was not.
- **Table 6-3, all seven divide-by-zero cases**: `FATANH` at ±1, `FDIV` and
  `FSGLDIV` at a zero source with a non-special `FPn`, `FLOG10`/`FLOG2`/`FLOGN`
  at zero, and `FLOGNP1` at −1 — the last returning a **NAN** where `FLOGN(0)`
  returns a negative infinity, for the same mathematical singularity, which the
  code records as a trap it had to be told about.
- **§2.3's FPSR layout**: FPCC in bits 27-24, quotient sign in 23 with seven
  bits in 22-16, EXC in 15-8, AEXC in 7-3; and the FPCR's bits 31-16 "always
  read as zero and are ignored during write operations".
- **§3.4's intermediate format** — a 17-bit twos-complement exponent and a
  67-bit mantissa. This core computes exponents in `int` and carries
  guard/round/sticky beyond the 64-bit mantissa, so it cannot wrap where the
  part would not.
- **Table 4-10, *Effective Addressing Mode Categories***, which is a **third
  witness** against `[PRM]` Table 2-4: absolute short and long alterable, both
  PC memory indirect rows not alterable, Absolute Long's register field `001`.
  Recorded in `PRM_WALK.md`.
- **Tables 4-1 to 4-9** — the instruction groups and the 32 conditional test
  mnemonics — and **§4.4.1-§4.4.3's equations and predicates**, which match
  `ap_m68882_evaluate_condition` and confirm the BSUN rule as predicate bit 4 a
  third time.
- **§4.5.4's NAN rules** and **§4.5.5's post-processing order** (underflow,
  round, overflow).
- **Table 6-1's vector assignments**, matching `[PRM]` Appendix B and
  `AP_M68882_VECTOR_*`; and that "**neither the MC68881 nor the MC68882 reports
  the post-instruction exception**", so only pre- and mid-instruction frames can
  arise from this part.
