## The 4096-ULP question is closed, from its own page

`ap_m68882_accuracy.h` recorded §4.3.2's "one unit in the last place of double
precision (which is equal to **4096** units in the last place of extended
precision)" as disagreeing with the arithmetic — a double ULP is 2⁻⁵² and an
extended ULP 2⁻⁶³, so the conversion is 2¹¹ = **2048**. It offered a reading
(a ±1 ULP bound spans a 2 ULP window), called it a guess, and recorded that
neither `[PRM]` nor the 68040 manual restates the conversion.

**Nobody had read §4.3.2's own worked example**, three paragraphs below:

> the relative difference between the correct result and the result calculated
> by the FPCP is 2⁻⁵⁷ (assuming an extended precision result) ... **This
> difference corresponds to an error of 64 units in the last place.**

2⁻⁵⁷/2⁻⁶³ = 2⁶ = 64. So the manual converts by the **plain ratio**, with no
doubling — which is exactly the reading the window guess proposed, and this
excludes it. Under the same convention one double ULP is 2⁻⁵²/2⁻⁶³ = 2048.

**4096 is a documentary error, an off-by-one in the exponent.** Both constants
stay as printed and the test still asserts the discrepancy; what changed is that
it is explained instead of flagged.

## `FATANH`'s infinity signs are transposed **twice**, and the code is right

`ap_m68882_transcendental.c` already overrode the `FATANH` page on mathematical
grounds: `atanh(x) = ½ln((1+x)/(1−x))`, so `atanh(+1)` is `+infinity`, and the
page's sentence has the two signs the other way round. Its comment calls this
"the one place in the session where a manual defect is corrected rather than
transcribed".

**§6.1.6 repeats the transposition**: "For the FATANH instruction, return a
+infinity if the source operand is −1; or a −infinity if the source operand is
+1."

Two statements, one error — which is what a sentence copied between an
instruction page and an exception chapter looks like, and not what two
independent derivations would look like. Both places' *operation tables* still
agree with the mathematics; only the prose is transposed, in both. Recorded in
the code, because a second witness looks at first like a reason to reverse the
decision and is not.

## A false start worth recording

§4.5.5.2: "The input operands to these instructions are assumed to be single
precision values, but no checking is performed to verify the inputs (**each
mantissa is truncated to 23 bits**, and the exponent is accepted as an extended
precision value)."

I read that, assumed a gap, and implemented it a second time.
`ap_m68882_single_mul` already calls `truncate_to_single`, which cites the same
sentence, masks the same bits, and additionally handles NANs and infinities —
which the duplicate did not. Reverted; the file is byte-identical to before.

**The tell was the test.** The first version passed with the new code removed,
because the behaviour was still happening elsewhere. *A test that cannot fail is
the instrument saying the premise is wrong.* The lesson is
`reference-search-is-not-a-code-check`, and it cost a round trip.

What *was* missing is a test that discriminates, since every existing `FSGLMUL`
case used operands exactly representable in single precision, where truncating
the inputs and rounding the result agree. `1 + 2⁻²⁴` separates them, and
`FMUL.S` on the same operands is the control.

## §7 settles a question the `[030]` walk had to leave open

The `[030]` §10 walk found that an addressing-mode refusal on a coprocessor
instruction is an **F-line**, not a protocol violation, and fixed four sites.
It left **three** open, because Table 10-6's split turns on the valid-EA class
the *coprocessor* declares — and `[030]` cannot state that, since it is the
68882's. They were recorded in `M68030_WALK.md` to settle here.

**Table 7-5, *Evaluate Effective Address and Transfer Data Primitive
Encoding*, declares them**, per opclass:

| Opclass | Instruction | Valid `<ea>` |
| --- | --- | --- |
| `010` | `F<op> <ea>,FPn` | `101` Data (lengths 1/2/4), `110` Memory (8/12) |
| `011` | `FMOVE FPm,<ea>` | **`001` Data Alterable** (1/2/4), `010` Memory Alterable (8/12) |
| `100` | `FMOVE <ea>,FPcr`, `FMOVEM <ea>,FPcr_list` | `111` Any, `101` Data, `110` Memory |
| `101` | `FMOVE FPcr,<ea>`, `FMOVEM FPcr_list,<ea>` | `011` Alterable, `001` Data Alterable, `010` Memory Alterable |

**So the store's refusal is an F-line.** For `FMOVE FPm,<ea>` the declared class
is Data Alterable, which excludes the nonalterable modes outright — so a
`(d16,PC)` destination is the *class mismatch* Table 10-6 puts in its F-Line
column, and never reaches the Protocol column's "Attempt to Write to
Nonalterable Address **Even if Address Declared Legal in Primitive**". That
clause describes a primitive declaring `101` Data or `111` Any and then asking
for a write, which the 68882 never does for a store.

`store_fp_destination` returned vector 13 and cited exactly the clause that does
not apply. Corrected to vector 11. *Verification: `step_suite`'s store test
changed vector; the source direction in the same test is the control, and still
runs, which is what keeps this the direction's rule rather than the addressing
mode's.*

The remaining two open sites — `transfer_fp_control`'s class check and `FScc`'s
— are opclass `100`/`101` and the conditional dialogue, and are still owed:
opclass `100`'s declared class varies with length (`111` Any at 4 bytes), which
this core's separate register-direct and immediate arms may already cover.
Recorded rather than changed.

## Table 7-2's CIR characteristics, field for field

## Verified against this core, and holding

- **§2.2.2's `FSGLDIV`/`FSGLMUL` exception**: "regardless of the precision
  specified by the PREC bits, these instructions round the result mantissa to
  single precision and generate an extended precision exponent which may be out
  of range for a single precision number." `ap_m68882_arith.c` carries
  `precision` and `range` as separate parameters for exactly this, and says why
  folding them would make those two instructions overflow where the part does
  not. §6.1.4 and §6.1.5's NOTEs restate it from the exception end.
- **§2.3.4's five AEXC equations**, including the two most easily simplified
  wrong: `AEXC(UNFL)` needs `EXC(UNFL ∧ INEX2)` where every other term is an OR,
  and `AEXC(INEX)` accrues on `OVFL` as well as the two INEX bits.
- **§6.1.9's exception priority** — BSUN, SNAN, OPERR, OVFL, UNFL, DZ, then
  INEX — with the `INEX2`-through-`ENABLE(INEX2)`-on-overflow case that a plain
  bit scan would miss. *One comment corrected*: it claimed the priority "is not
  the bit order", and §2.2.1 says it is ("organized in decreasing priority, left
  to right"). The code was right; the reason given for it was not.
- **Table 6-3, all seven divide-by-zero cases**: `FATANH` at ±1, `FDIV` and
  `FSGLDIV` at a zero source with a non-special `FPn`, `FLOG10`/`FLOG2`/`FLOGN`
  at zero, and `FLOGNP1` at −1 — the last returning a **NAN** where `FLOGN(0)`
  returns a negative infinity, for the same mathematical singularity, which the
  code records as a trap it had to be told about.
- **§2.3's FPSR layout**: FPCC in bits 27-24, quotient sign in 23 with seven
  bits in 22-16, EXC in 15-8, AEXC in 7-3; and the FPCR's bits 31-16 "always
  read as zero and are ignored during write operations".
- **§3.4's intermediate format** — a 17-bit twos-complement exponent and a
  67-bit mantissa. This core computes exponents in `int` and carries
  guard/round/sticky beyond the 64-bit mantissa, so it cannot wrap where the
  part would not.
- **Table 4-10, *Effective Addressing Mode Categories***, which is a **third
  witness** against `[PRM]` Table 2-4: absolute short and long alterable, both
  PC memory indirect rows not alterable, Absolute Long's register field `001`.
  Recorded in `PRM_WALK.md`.
- **Tables 4-1 to 4-9** — the instruction groups and the 32 conditional test
  mnemonics — and **§4.4.1-§4.4.3's equations and predicates**, which match
  `ap_m68882_evaluate_condition` and confirm the BSUN rule as predicate bit 4 a
  third time.
- **§4.5.4's NAN rules** and **§4.5.5's post-processing order** (underflow,
  round, overflow).
- **Table 6-1's vector assignments**, matching `[PRM]` Appendix B and
  `AP_M68882_VECTOR_*`; and that "**neither the MC68881 nor the MC68882 reports
  the post-instruction exception**", so only pre- and mid-instruction frames can
  arise from this part.

## §3.2.2's NOTE was not implemented, and the glossary is what found it

Appendix A defines two categories where this core had one:

> **DENORMALIZED NUMBER**: A floating-point number having all zeros in the
> exponent and a non-zero value in the fraction/mantissa.
>
> **UNNORMALIZED NUMBER**: An extended precision external operand that contains
> an explicit integer part bit (j) of zero and an exponent that is neither the
> maximum nor the minimum for the format.

`ap_m68882_classify` returned `DENORMALIZED` for both, and nothing anywhere
folded the second into the first. §3.2.2's NOTE -- on a page this walk had
already marked read -- states the rule outright:

> "Such a number is called an unnormalized number. The MC68881 **never
> generates** an unnormalized number as the result of any operation.
> **Unnormalized inputs are always converted to normalized or denormalized
> numbers or zero before being used.** Thus, as required by the IEEE standard,
> the FPCP does not distinguish between redundant encodings of extended
> precision values."

**Why the fold is exact**, and why it is a fold rather than a rounding: Table
3-3 gives the *same* relation for the normalized and denormalized rows,
`(-1)^s x 2^(e-16383) x j.f`. The extended denormal exponent is `0 - bias`,
where single and double use `1 - bias`. One formula covers the format, so
shifting the mantissa up a place and the exponent down a place changes nothing
about the value -- which is exactly what makes these *redundant encodings*.

**Three witnesses that the part treats it as a distinct input type**, all in §5:
§5.1.1.2's conversion-unit rules say "If the operand data type is NAN,
**unnormalized**, or denormalized, waits until the APU is idle and hands off the
instruction to the APU" -- twice, for two operand directions; the CU "creates a
tag that represents the data type of the converted source operand (normalized,
**unnormalized**, denormalized, zero, infinity, or NAN)"; and Table 5-5's note
**b** degrades a fully-concurrent `FMOVE` to partial concurrency for "NAN,
**Unnormalized** or Denormalized Data Types". A redundant encoding is not
something the part copies through -- it is something that costs it the APU.

**Fixed** in `ap_m68882_normalize_input` (`ap_m68882_format.c`), called from the
one place both operands are in hand (`execute_general`) and from the extended
store. Deliberately **not** in `ap_m68882_from_extended`, which `FMOVEM` also
reaches: §4's `FMOVEM` page transfers registers without conversion, and the
NOTE's word is *used*.

*Verification, and both halves discriminate:* `m68882_store_suite`'s
`test_an_unnormalized_extended_store_folds_to_the_canonical_form` walks sixteen
redundant encodings of 1.0 and fails at the first one with the fold removed
(`Expected 0x3F Was 0x40`); `m68882_format_suite`'s
`test_an_unnormalized_operand_is_folded_before_it_is_used` runs `FGETEXP`
through `ap_m68882_execute` over thirty-two of them -- `FGETEXP` reads the
encoding directly, so it cannot be right about a redundant one -- and fails with
the operand fold removed. It goes through `ap_m68882_execute` rather than
calling the operation, so that a fold put in the wrong layer would still fail
it.

*Identity: `42B14372F3677EE8`, clocks `1408663613`, unmoved. Expected -- the
firmware writes no redundant extended encodings, so nothing in the boot reaches
the new arm.*

## §5, walked whole: the concurrency model, and three checks on the state frame

**§5.1's model is why the 68882 is "invisible to a program except through
timing", stated from the part's side.** The MC68882 adds a **conversion unit**
in front of the APU; the CU can hold one instruction while the APU runs another,
converting its operand and tagging its data type, and hands it over when the APU
goes idle. Tables 5-1 through 5-5 partition every instruction into
minimum-concurrency, partial and fully-concurrent -- the fully-concurrent set is
`FMOVE` alone, in five operand shapes, each with the notes that degrade it.
Nothing here changes a result; all of it changes *when*.

- **Table 5-7 prints three execution times** the timing gap does not have:
  `FMOVE.X FPx,FPy` **21** clocks, `FMOVE.D <ea>,FPy` **39**, `FMOVE.D
  FPy,<ea>` **55**. Recorded against the `PROJECT_STATUS.md` row that says this
  core charges nothing for the calculation.
- **Table 5-8's state frame sizes** -- null 4 / idle 28 / busy 184 on the
  MC68881, null 4 / idle **60** / busy **216** on the MC68882 -- second-witness
  Figure 6-5's `$3C`, which `AP_M68882_FRAME_IDLE_BYTES` already carries, and
  the busy size this core records as a named absence.
- **§5.2.2 reaches the same layout by a second route.** "The offset for the
  exceptional operand is `$08` in the MC68881 and **`$28` in the MC68882**",
  the 68882's offsets being `$20` greater, while "the negative offsets (from the
  bottom of the state frame) are the same for both": Figure 5-7's `XOPER EQU
  -16` and `OPEREG EQU -4`, indexed by the **size byte** rather than the frame
  length. `$38` - 16 = `$28` and `$38` - 4 = `$34`, against `$18` - 16 = `$08`
  and `$18` - 4 = `$14`. Both land exactly where `ap_m68882_save` puts them.
- **Figure 5-9 is the published way to tell the two parts apart**, and it reads
  the byte this core sets: `FSAVE -(SP)` / `MOVE.B 1(SP),D0` / `CMPI #$18,D0` /
  `BEQ ONE`. The `step_suite` frame test asserted
  `AP_M68882_FRAME_IDLE_SIZE_BYTE` against itself -- a tautology that would hold
  for any value. Now it also asserts the literal `$38` and the 60-byte total,
  with Figure 5-9 quoted as the reason the byte is observable at all.

**§5.2.2's exception-handler contract**, recorded because it constrains any
future busy-frame work: a handler containing floating-point instructions must
begin with `FSAVE`, set **`EXC_PEND`, bit 27 of the BIU flag long word** (Figure
5-6 does it as `BSET #3,(SP,D0)` -- bit 3 of the byte at the size-byte offset,
which is bit 27 of that long word), and end with `FRESTORE` before the `RTE`.
Omit the `FSAVE` and the next instruction takes the same exception forever; omit
the `BSET` and it also loops; omit the `FRESTORE` and a partially-executed
instruction never finishes.

**§5.2.3.4 states the no-coprocessor mechanism from the FPU's side**: "A bus
error during initiation of an instruction is used as an indication that the
coprocessor is not present, and the MPU takes an **F-line emulator exception**."
That is what `PROJECT_STATUS.md` means by attaching the part as a *pointer* so a
machine without one keeps its line-1111 trap.

## §9-§13: one gap-narrowing set of numbers, and four confirmations

- **Table 9-1's CIR selection matches `ap_m68882_cir.c` row for row**, from a
  second table: `$00` response read, `$02` control write, `$04` save read, `$06`
  restore R/W, `$08` and `$0C` reserved, `$0A` command write, `$0E` condition
  write, `$10` operand 32-bit R/W, `$14` register select read, `$16` reserved,
  `$18` instruction address 32-bit write, and `$1C` operand address with the
  footnote "**Not used by the MC68881 or MC68882**".
- **§9.9's reset** -- "initialize the floating-point data registers to
  non-signaling not-a-numbers and clears the floating-point control, status, and
  instruction address registers" -- is `ap_m68882_regs_reset` exactly, including
  the FPIAR that §10.2's restatement leaves out.
- **§10.2 is a second witness for a rule this core obeys by construction.** The
  `[030]` §10.5.3 walk found "the coprocessor should be affected by external
  reset signals only and **not by RESET instructions**". §10.2 argues it from
  the coprocessor's end -- "since the FPCP is considered to be part of the
  internal state of the main processor, prudent system design suggests that the
  FPCP should not respond to the assertion of the `RESET` signal by the main
  processor" -- and **Figure 10-3 draws the circuit**: the FPCP's `RESET` is
  wired to power-on reset only, not to the system reset the instruction drives.
  `drive_external_reset` calls `ap_board_reset_devices`, and the 68882 is
  `machine->fpu` rather than a board device.
- **§10.4 puts numbers on the coprocessor interface's bus cost**, which the
  recorded timing gap did not have. A **synchronous** read -- and §12.6 note 3
  says these "occur **only** when the save or response CIR locations are read"
  -- takes **five clock cycles (two wait cycles)** when the MPU and FPCP share a
  clock, and six or seven as temperature and chip-select delay push it out. An
  **asynchronous** read or write, which is every other CIR access, takes
  **three clocks with no wait states**, because those CIRs are dual-ported.
- **§12.6 specs 25 and 27 are given in clock units**, exactly as `[030EC]`'s
  specs 32/35/56 were: `START` true to data-out valid and to `DSACK` asserted
  are "`60 + 2.5` ns/Clks" over a "1.5" minimum at 25 MHz. That is the same
  documentary shape the `MC68030EC` walk warned about -- an AC table with
  behaviour hiding in it -- and it is the quantitative form of §10.4's five
  clocks. Note 10 gives the logical start condition itself:
  `START = CS + AS + (R/W . DS)`.
- **§10.6 names a 68881/68882 behavioural difference this core does not model
  and does not need to**: "the MC68882 may return an evaluate `<ea>` and
  transfer data primitive with **CA = 0**, which does not require the main
  processor to read the response register before proceeding", where the 68881
  always sets `CA = 1` there. It comes with a system constraint -- an
  MC68020/MC68030 "clock frequency cannot be more than **1.5 times** the
  frequency of the MC68882 clock", or the response CIR is read within three
  FPCP clocks of the last operand write and a protocol violation results. The
  primitive exchange is not modelled here, for the reason `ap_m68882.h` gives.
- **§11 is board wiring.** Figure 11-1 is the DN3500's case: `SIZE` and `A0`
  both to Vcc for a 32-bit port, `A1-A4` straight across, chip select decoded
  from `FC0-FC2`, `A16-A19` and `A13-A15`. Figures 11-2 to 11-5 cover the 16-
  and 8-bit ports and the 68000/68008/68010 peripheral connections, which this
  machine does not have.
- **§12 and §13 are electrical and mechanical.** Four speed grades -- `RC12`,
  `RC16`, `RC20`, `RC25` -- with the MC68882 offered at 16.67, 20 and 25 MHz and
  the 25 MHz part "**available 1st quarter 1988**", which dates the manual
  against the DN3500. `PD` 0.75 W max, `Cin` 20 pF, 68-pin grid array, and the
  `VCC`/`GND` groups from Table 9-4 repeated as Table 13-2's pin assignments.

## The appendices, the index and the back cover

Appendix A's glossary is where the unnormalized gap above came from; its
`EXTENDED PRECISION` entry also states the memory format as "a one-bit sign
field, an 15-bit biased exponent field, a **16-bit undefined field**, and a
64-bit mantissa", which is the layout `ap_m68882_from_extended` implements and
the trap `ap_m68882_format.h` warns about. Appendix B is abbreviations; the
INDEX runs ten pages, and the three **foldout** pages at the very end carry
Figures 12-3, 12-4 and 12-5, the read and write cycle waveforms §12.6 references
and does not print in place.

**The back cover is a usable cross-check**: "seven data types, **forty-six
instructions**, and eight **80-bit** floating-point registers". Tables 5-2 and
5-3 enumerate 25 monadic and 10 dyadic operations; add `FMOVE`, `FTST`,
`FSINCOS`, `FMOVECR`, `FMOVEM`, and Table 5-6's `FBcc`, `FDBcc`, `FNOP`, `FScc`
and `FTRAPcc`, plus `FSAVE` and `FRESTORE`, and the count is forty-six. The
"80-bit" is the *register*; the 96-bit memory format is the same number with the
sixteen unused bits added, which is the distinction this module keeps.
