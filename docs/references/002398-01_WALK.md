## Two structures this project reverse-engineered, given byte for byte

**The physical volume label** (`pv_label_t` in `vol.ins.pas`), p. 5-19:

| Offset | Field |
| --- | --- |
| +00 | VERSION (16 bits), then `"AP"` — `.version`, `.apollo` |
| +04 | `"OLLO"` — the string is `APOLLO` split across the two longwords |
| +08 | VOLUME NAME, 32 bytes — `.name` |
| +28 | UNIQUE ID OF VOLUME, 8 bytes — `.id` |
| +30 | unused, then DISK TYPE — `.dtype`, "describes variants of physical disk, e.g. double density. Today there are none, and the field contains 0" |
| +34 | TOTAL BLOCKS IN VOLUME — `.blocks_per_pvol` |
| +38 | BLKS PER TRACK, TRACKS PER CYL |
| +3C…+64 | **DADDR OF LOGICAL VOLUME [1..10]** — `.lv_list` |
| +68…+94 | **ALTERNATE LABEL DADDR [1..10]** — `.alt_lv_list` |
| +98 | end |

**Checked against `media/dn5500-invol-done.awd` and it matches byte for byte.**
Sector 0's data — after the 32-byte disk block header — begins

```
00 01 41 50 4F 4C 4C 4F 44 4E 35 35 30 30 20 20 20 20 ...
```

version `0001`, `"APOLLO"`, then `DN5500` blank-filled in the 32-byte name field
at +08. **Ten logical volumes maximum, each with an alternate label**, which is
`[AEGIS]` §4.2.1's "physical disk address of each alternate logical volume
label" given a size.

**The logical volume label** (`lv_label_t`), p. 5-17/18: version at +00, a
32-byte `.name` at +04, the volume's UID at +24, a **BAT header** at +2C and a
**VTOC header** at +4C, then the history — `.label_write_time`,
`.last_mounted_node`, `.node_boot_time`, `.mounted_time`, `.dismount_time`,
`.salvage_node`, `.salvage_time`, `.salvage_mode` and **`.sys_shut_state`**,
`.dump_start_time`, `.dump_end_time`, `.dump_cur_uid`, a UTC delta and timezone
name, `.last_valid_time`, then a **bad spot barrier** and a bad spot list
(`FFFFFFFF` = no continue, `FFFFFFFE` = +F0 is the DADDR of a continue block).
Sector 4's data reads `00 01 00 00 44 4E 35 35 30 30 …` — version, unused, name
— which is the layout exactly.

**`.sys_shut_state` is the "shutdown state word"** `[AEGIS]` §27.1 says SYSBOOT
checks to decide whether to run SALVOL, and the "BAT header volume trouble bit"
is in the BAT header at +2C. Two documents, one mechanism, and now a byte offset
for each half.

## The fault diagnostic record, and it is what the DS5500 prints from

p. 1-7, `fault_$diag_t` in `fault.ins.pas`:

| Offset | Field |
| --- | --- |
| +00 | `.pattern` = **`#DFDF`** |
| +02 | **STATUS WORD** — `.status` |
| +06 | REGISTERS, `$40` bytes — `.registers` |
| +46 | flags `R N … FFF` — `.bus_info` |
| +48 | ACCESS ADDRESS — `.access_address` |
| +4C | INSTRUCTION REGISTER — `.inst_register` |
| +4E | flags `P I V A` |
| +50 | SUPERVISOR ECB |
| +54 | SUPERVISOR SR |
| +56 | SUPERVISOR PC — `.sup_pc` |
| +5A | SR AT FAULT — `.sr`, the *user* SR |
| +5C | PC AT FAULT — `.pc`, the *user* PC |
| +60 | end |

with the flags spelled out: `R` read operation, `N` not an instruction
reference, `FFF` the function code (`001` user data, `010` user program, `101`
supervisor data, `110` supervisor program, `111` interrupt acknowledge), `P`
permit return from fault, `I` in supervisor, `V` registers valid, `A` bus info
valid.

**`#DFDF` is the pattern `[AEGIS]` §18.2.4.1 says the common fault handler
writes** "to flag the frame as a diagnostic frame; this pattern makes it easy to
identify diagnostic frames within stack dumps". So the DS5500's
`Crash_Status 0012004B` is this record's `.status` word at +02, and the record
is findable in a memory dump by searching for `DFDF`. **A concrete instrument
this project does not have and could build without a new run**, since the
existing `--dump-logical` can search a stack once the record's address is known.

00120003 integer divide by zero     0012000E correctable memory error detected
00120004 CHK instruction trapped    0012000F uncorrectable memory error

**That last one is `fault_$while_lock_set`**, which `[AEGIS]` §18.2.4 names
without a number, and it **refutes a candidate this project had recorded**: the
DS5500's `Crash_Status` is `0012004B`, not `00120020`, so the lock-check is not

years later than the last of those.

## Chapter 7 decodes `Crash_Status` and names what the DS5500 calls through

**The status word**, `status_t` in `base.spo.bbas`, p. 7-15:

```
31        24 23        16 15                     0
+-----------+-----------+------------------------+
| F SSSSSSS | A MMMMMMM |      C .......... C    |
+-----------+-----------+------------------------+

F = 1 => module couldn't handle error (fail bit)
S..S = Subsystem identification
A = 1 => asynchronous fault; only set during delivery of fault (.async)
M..M = Module identification
C..C = Module-specific error code
```

**So `Crash_Status 0012004B` decodes**: fail bit **clear**, subsystem `00`, async
bit **clear**, module **`0x12`** — the fault module chapter 4 lists — and a
module-specific code of `004B`. **The async bit being clear says it was a
*synchronous* fault**, which `[AEGIS]` §18 defines as "a direct result of program
execution", and that fits an instruction fetch at `0080000C` exactly. Only the
code's text is still unknown, and this shelf stops at `003A` in 1987.

**And the calling sequence**, p. 7-8, is the DS5500's own instruction sequence:

```
Call:    PEA  ARGn            push address of last arg
         ...
         PEA  ARG1            push address of first arg
         MOVE.L ECBADR,A0     GET ADDRESS OF ECB
         JSR  (A0)            jump and push PC
         ADD.W #4*n,SP        pop arg pointers off stack

Entry:   MOVE.L DB,-(SP)      save caller's data base reg
         CLR.L  -(SP)         push a reserved word
         MOVE.L A0,-(SP)      push address of my ECB
         MOVE.L 6(A0),DB      load my data base from ECB
         LINK   #autosize,SB  load my stack base
```

**`MOVE.L ECBADR,A0` then `JSR (A0)` is `movea.l d(a5),a0; jsr (a0)`** — the
three instructions `PROJECT_STATUS.md` records the DS5500 executing before it
lands in a page of zeros. `A5` is the **data base register**, `d(a5)` fetches an
**Entry Control Block address**, and the callee's first act is `MOVE.L 6(A0),DB`
— **loading its own data base out of the ECB**.

*So the thing at `0091709C` is an ECB*, and `[DP]`'s "transfer vector" is the
same object under the shared-library name. A call into a page of zeros would
give the callee a **null data base**, which is a sharper failure than "jumped
into nothing".

**The stack frame** (p. 7-15) that call builds: `SB+00` caller's `SB`, `+04` a
pointer to the ECB, `+08` a unit list (zero), `+0C` caller's `DB`, `+10` the
return PC, `+14` onward the argument pointers. "Caller's DB is an **optional**
field. **'DB not saved' bit in ECB** signals that it is not present", and
"registers other than **DB, SB, SP** are **not preserved**".

> **CORRECTION, measured 2026-09-10: the SR10.4 module the DS5500 dies in does
> not build this frame.** Its frame at `A6 = 75D7FF94` is a plain `LINK A6`
> frame — `+00` saved `A6`, `+04` the return address, `+08` the first argument —
> and three discriminators say so: the code at `[A6+04] = 0080949C` is
> `addq.w #4,a7`, a caller's cleanup popping one long, where an ECB's first
> instruction would be `MOVE.L DB,-(SP)` (`2F0D`); the one long popped matches
> the one argument at `+08`, where the `SB` frame carries a zero unit list; and
> `A4` holds that same argument. **The `SB` frame above is Rev 1's, 1983, and
> whichever compiler built this module in 1992 does not use it.** The *call*
> sequence — `movea.l d(a5),a0; jsr (a0)` — is unchanged and still exactly what
> the machine executes. Detail and the dumps in `PROJECT_STATUS.md`.
>
> *The row is kept as written above because it is what p. 7-15 says*, and
> because it is what a 1983-era binary should be read against.

## Chapter 5's volume structures read at 600 dpi (2026-09-12)

Read against one question: **did the VTOC header or the VTOC entry change
between revisions?** Both were read as page images and compared with `[EH3]`.

**`vtoc_hdr_t`, p. 5-22, is identical to Rev 3 p. 2-24** offset for offset —
`.version`/`.vtoc_size` at `+4C`, `.vtoc_blocks` `+50`, `.net_root` `+54`,
`.root_dir` `+58`, `.os_x` `+5C`, `.boot_x` `+60`, the eight-entry `.map` at
`+64`, `.pad` at `+94`, end `+B0`, with the same note that it "lines in logical
volume label. Offsets given are from start of label". The field *names* differ
slightly — Rev 1 has `.net_root` and `.root_dir` where Rev 3 has `.net_x` and
`.root_x` — and nothing else does. `vtoc_mape` is the same six bytes.

**`vtoce`, p. 5-21, is identical to Rev 3 p. 2-23** likewise: `+00` version /
sys_type / `UCCPIF` flags, `.uid` `+04`, `.type_uid` `+0C`, ACL UID `+14`,
`.cur_len` `+1C`, `.blocks_used` `+20`, `.dtu` `+24`, `.dtm` `+28`, `.dir_uid`
`+2C`, end of header `+40`, `.fm[0..31]` `+40`-`+BF`, `.fm2[1..3]` `+C0`-`+CB`,
end `+CC`. The flag legend is the same five, with `F` printed here as "File
repaired by salvager" against Rev 3's "File needs salvaging".

**Which is the point.** Both structures were stable from April 1983 to February
1985, and **neither describes an SR10.4 volume** — `FINDINGS.md` and
`docs/references/002398-03_WALK.md` record the measurement. A layout that two
revisions two years apart print identically did not drift; it changed at some
point after Feb 1985, and no document on this shelf covers the change. That is
a stronger statement than either revision alone supports, and it is the reason
to have read this one.
