## Two structures this project reverse-engineered, given byte for byte

**The physical volume label** (`pv_label_t` in `vol.ins.pas`), p. 5-19:

| Offset | Field |
| --- | --- |
| +00 | VERSION (16 bits), then `"AP"` — `.version`, `.apollo` |
| +04 | `"OLLO"` — the string is `APOLLO` split across the two longwords |
| +08 | VOLUME NAME, 32 bytes — `.name` |
| +28 | UNIQUE ID OF VOLUME, 8 bytes — `.id` |
| +30 | unused, then DISK TYPE — `.dtype`, "describes variants of physical disk, e.g. double density. Today there are none, and the field contains 0" |
| +34 | TOTAL BLOCKS IN VOLUME — `.blocks_per_pvol` |
| +38 | BLKS PER TRACK, TRACKS PER CYL |
| +3C…+64 | **DADDR OF LOGICAL VOLUME [1..10]** — `.lv_list` |
| +68…+94 | **ALTERNATE LABEL DADDR [1..10]** — `.alt_lv_list` |
| +98 | end |

**Checked against `media/dn5500-invol-done.awd` and it matches byte for byte.**
Sector 0's data — after the 32-byte disk block header — begins

```
00 01 41 50 4F 4C 4C 4F 44 4E 35 35 30 30 20 20 20 20 ...
```

version `0001`, `"APOLLO"`, then `DN5500` blank-filled in the 32-byte name field
at +08. **Ten logical volumes maximum, each with an alternate label**, which is
`[AEGIS]` §4.2.1's "physical disk address of each alternate logical volume
label" given a size.

**The logical volume label** (`lv_label_t`), p. 5-17/18: version at +00, a
32-byte `.name` at +04, the volume's UID at +24, a **BAT header** at +2C and a
**VTOC header** at +4C, then the history — `.label_write_time`,
`.last_mounted_node`, `.node_boot_time`, `.mounted_time`, `.dismount_time`,
`.salvage_node`, `.salvage_time`, `.salvage_mode` and **`.sys_shut_state`**,
`.dump_start_time`, `.dump_end_time`, `.dump_cur_uid`, a UTC delta and timezone
name, `.last_valid_time`, then a **bad spot barrier** and a bad spot list
(`FFFFFFFF` = no continue, `FFFFFFFE` = +F0 is the DADDR of a continue block).
Sector 4's data reads `00 01 00 00 44 4E 35 35 30 30 …` — version, unused, name
— which is the layout exactly.

**`.sys_shut_state` is the "shutdown state word"** `[AEGIS]` §27.1 says SYSBOOT
checks to decide whether to run SALVOL, and the "BAT header volume trouble bit"
is in the BAT header at +2C. Two documents, one mechanism, and now a byte offset
for each half.

## The fault diagnostic record, and it is what the DS5500 prints from

p. 1-7, `fault_$diag_t` in `fault.ins.pas`:

| Offset | Field |
| --- | --- |
| +00 | `.pattern` = **`#DFDF`** |
| +02 | **STATUS WORD** — `.status` |
| +06 | REGISTERS, `$40` bytes — `.registers` |
| +46 | flags `R N … FFF` — `.bus_info` |
| +48 | ACCESS ADDRESS — `.access_address` |
| +4C | INSTRUCTION REGISTER — `.inst_register` |
| +4E | flags `P I V A` |
| +50 | SUPERVISOR ECB |
| +54 | SUPERVISOR SR |
| +56 | SUPERVISOR PC — `.sup_pc` |
| +5A | SR AT FAULT — `.sr`, the *user* SR |
| +5C | PC AT FAULT — `.pc`, the *user* PC |
| +60 | end |

with the flags spelled out: `R` read operation, `N` not an instruction
reference, `FFF` the function code (`001` user data, `010` user program, `101`
supervisor data, `110` supervisor program, `111` interrupt acknowledge), `P`
permit return from fault, `I` in supervisor, `V` registers valid, `A` bus info
valid.

**`#DFDF` is the pattern `[AEGIS]` §18.2.4.1 says the common fault handler
writes** "to flag the frame as a diagnostic frame; this pattern makes it easy to
identify diagnostic frames within stack dumps". So the DS5500's
`Crash_Status 0012004B` is this record's `.status` word at +02, and the record
is findable in a memory dump by searching for `DFDF`. **A concrete instrument
this project does not have and could build without a new run**, since the
existing `--dump-logical` can search a stack once the record's address is known.

## Also in chapters 1 and 2

- **Chapter 1** is one page per AEGIS structure: the active segment table
  (`ARRAY [1..64] OF ASTE_T`) and its header (a 61-entry hash table at +00, free
  list and LRU replacement pointer at +7A, per-volume process counts at +80),
  the mapped segment table, the memory map and its entries, the OS mapping, the
  page map, the process control block, the boot shell commands, the clock, the
  disk controller and disk volume table entries, the stack frame, the system
  directories — and the **ring packet format** with its type field, early ACK
  field and message data, which is where `RING.md`'s findings 79-79c come from.
- **Chapter 2** is the CPU and memory boards: addressing modes, condition codes,
  the **exception error stack frame** and **special status word** for the
  DN4xx/DN600, the exception vectors, the **memory control/status registers
  (MCSR)** control and status halves, memory board jumpers, and the **MMU** —
  DN300 PID/PRN and status registers, DN4xx/DN600 PID/PRIV, CPU A control,
  enable CPU B, MMU status, clear MMU status and bus status registers.
- The DN4xx/DN600 special status word is `RR 0 IF DF RM HB BY RW 0 0 0 0 FCN`,
  a 68010-generation layout — a different part from anything this core models,
  but its function-code encodings are the same five and confirm them
  independently.

## Chapter 4 is the AEGIS error-code list, and it decodes a live measurement

Every code paired with its text, by subsystem and module — and **module `0012`
is the fault module**:

```
00120001 odd address error          0012000C bus time-out
00120002 illegal instruction        0012000D invalid user stack pointer
00120003 integer divide by zero     0012000E correctable memory error detected
00120004 CHK instruction trapped    0012000F uncorrectable memory error
00120005 arithmetic overflow        00120010 process quit
00120006 privileged instruction     00120011 access violation
00120007 invalid SVC code           00120015 single step completed
00120009 undefined TRAP             0012001C unimplemented SVC
0012000A unimplemented instruction  0012001D invalid stack format
0012000B protection boundary        0012001E memory parity error
                                    00120020 supervisor fault while resource
                                             lock(s) set
```

**That last one is `fault_$while_lock_set`**, which `[AEGIS]` §18.2.4 names
without a number, and it **refutes a candidate this project had recorded**: the
DS5500's `Crash_Status` is `0012004B`, not `00120020`, so the lock-check is not
why a user-mode fault reached the supervisor crash path.
`AEGIS_INTERNALS_WALK.md` carries the withdrawal.

**What survives is the module.** `0012` is faults, so the DS5500's crash *is* a
fault, and `004B` is one of them. **It cannot be decoded here**: the list runs to
`0020` in this revision, `002C` in Rev 3 and `003A` in Rev 4, and SR10.4 is five
years later than the last of those.

Chapter 4 also carries **BOOT ERRORS (PROM)** — "error: boot not found — The
SYSBOOT read from records 2 [thru B]", "boot error: unable to read `pv_label`",
"volume 'N' not found", "unable to read `lv_label`" — which `002398-04`'s walk
already has at its row 85, agreeing across four years.

## Chapters 3 and 5, condensed

**Chapter 3, display hardware**: board jumper placements with board orientation
("EJECTORS FACING UPWARDS"), the `FF9800` register block, a status register whose
bits are "asserted by micro code", and X and Y address controls. The DN400-era
display, not the DN3000's.

**Chapter 5, the file system**, beyond the two volume labels above: an ACL entry
(`acl_$entry` in `acl.ins.pas`), the directory info block
(`infoblk_hdr_t` in `name.pvt.pas`) and the directory operations, the registry
format's five record types, the **UID** (`uid_t` in `base.ins.pas`) and the
**canned UIDs** — the `0000.050x` series of "canned persons", with
`acl_$sys_user_uid` at `00000500,0`. `002398-04`'s row 50 has the disk-structure
canned UIDs (`pv_label_$uid 00000200,0`) that settled `ap_volume.h`'s `0x440`;
this is the *person* series beside them.
