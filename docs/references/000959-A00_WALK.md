Read because `[DP]` chapter 5 and `[AEGIS]` §5 both point at it for the

which is the bus a DN3000 and DN3500 carry and this core models.

## It corrected a rule this project had written down twice

`board/ap_disk.h` and `board/ap_board.c` both stated the AT I/O window's mapping
as `Apollo = 0x040000 + AT × 0x80`. §3.1 gives the general rule:

> "Ten-bit consecutive addresses in the I/O address space are mapped into
> processor address space in **groups of eight bytes**, and each group is
> assigned the first eight bytes of a different, but consecutive, page (1024
> bytes). Thus, the first 1024 addresses in PC AT compatible address space
> (0-3FF) map to **128 physical pages (40000-5FFFF)** in processor address
> space."

So `Apollo = 0x040000 + (AT >> 3) × 1024 + (AT & 7)`. **The two agree exactly at
multiples of eight and diverge within a group** — `AT × 0x80` puts AT `302` at
`058100` where the rule puts it at `058002`.

**And the rule has since been checked rather than argued** — `FINDINGS.md` C288.
Appendix A's `cvt_at` command prints three worked conversions, which also pin
the sixteen-bit *fold* that §3.1 mentions without defining: bits `[15:10]` enter
the page at 16 bytes each, so the whole map is `0x040000 + ((AT >> 3) & 0x7F) *
1024 + ((AT >> 10) & 0x3F) * 16 + (AT & 7)`, and the `iova` handed to `crddf` is
`AT & 0x3FF`. Table 3-1's rows then carry **eight** device addresses this core
already had — disk `1A0`, tape `200`, ring `220` and `320`, 802.3 `300`,
monochrome `3B0`, colour `3D0`, floppy `3F0` — onto the constants it defines,
with nothing adjusted. `atbus_suite` 16 → 20 asserts all of it.

**And this project's own measurement already agreed with the manual.**
`ETHERNET.md` finding 10 records "every oracle access landing on `058002` and
`058006`" for the EtherLink Plus at AT `300` — byte offsets *inside* a group,
which `AT × 0x80` cannot produce. `ap_3c505_decode` takes a base and computes
`offset = address - base`, which is the rule. **The code was right, the
measurement was right, and only the sentence was a special case presented as the
general one.** Both comments now carry the rule, with the divergence and the
evidence named. No behaviour changed and nothing needed to.

*Worth noting what this did not require*: no run, no instrument, no oracle. A
document already on the shelf, read for the first time.

## Chapter 3, the AT bus, is three tables of modelled hardware

**Table 3-1, I/O address space** — the AT-side addresses of the machine's own
devices, and the table that turned §3.1's rule into a checked map (C288): disk controller `1A0-1A7` and `3F0-3F7`, tape controller `200-207`,
**Apollo Token Ring Network Controller-AT `220-23F` and `320-33F`**, SPE serial
line 2 at `2F8-2FF`, 802.3 controller `300-307` with an alternate at `310-317`,
SPE parallel `378-37F`, monochrome graphics `3B0-3BF`, colour graphics
`3D0-3DF`, SPE serial line 1 `3F8-3FF`, everything else customer devices.

**Table 3-2, DN3000/DN4000 physical memory** — and it is the *complement* of
`008778-03`'s Table 2-6 rather than a duplicate: where the technical reference
gives the fine rows inside `000000-03FFFF` ("Reserved for the System" here),
this gives what lies outside — `040000-05FFFF` the I/O address space,
`0A0000-0BFFFF` colour or alternate monochrome graphics, `0C0000-0DFFFF`
alternate monochrome or **Apollo Token Ring at `0D0000-0DFFFF`**, `0E0000-0EFFFF`
alternate colour or a second single-board ring, `100000-8FFFFF` main memory
("on the DN4000, this area is not occupied by main memory"), `C00000-CFFFFF` and
`D00000-DFFFFF` the PC coprocessor and its alternate, `FA0000-FDFFFF` monochrome
graphics.

**Tables 3-3 and 3-4, unit numbers and interrupt priority** for the DN3000 and
DN4000: "The unit number of a PC AT compatible device is **identical with the
Interrupt Request (IRQ) line**. There are 16 possible unit numbers; unit number
0 has the highest priority." Timer, keyboard and two others are marked "used by
the processor and **not available on the bus**".

**Read as a page image** (PDF page 42, printed 3-7, 190 dpi), which the row
above said was owed before any IRQ assignment was taken from them. Table 3-3 is
the DN3000; Table 3-4 is the DN4000 and differs only in the SPE serial-line
numbering:

| Unit/IRQ | Priority | Device |
| --- | --- | --- |
| 0* | 1 | Timer |
| 1* | 2 | Keyboard |
| 2* | — | Reserved |
| 3 | 3 | Apollo Token Ring Network Controller-AT |
| 4 | 12 | SPE — Serial Line 1 or User Device |
| 5 | 13 | Tape Controller |
| 6 | 14 | Disk Controller or User Device |
| 7 | 15 | SPE — Parallel Line or User Device |
| 8* | 4 | Calendar — Serial Lines 1 and 2 |
| 9 | 5 | ETHERNET 2, SPE — Serial Line 2 or User Device |
| 10 | 6 | ETHERNET 1 or User Device |
| 11 | 7 | PC Coprocessor or User Device |
| 12 | 8 | User Device |
| 13* | 9 | Reserved |
| 14 | 10 | Disk Controller |
| 15 | 11 | PC Coprocessor Alternate or User Device |

"*This IRQ line is used by the processor and is not available on the bus." —
so units 0, 1, 2, 8 and 13 are off the bus, which is why the **calendar's IRQ 8
can be shared with the serial pair without a strap**: no expansion card can take
it.

**Four rows agree with this core and nothing needed changing**: tape 5
(`AP_TAPE_IRQ`), floppy 6 (`AP_DISK_FLOPPY_IRQ`), fixed disk 14
(`AP_DISK_FIXED_IRQ`), calendar 8 (`AP_CALENDAR_IRQ`).

**And the priority column closes `FINDINGS.md` C11's open question.** C11
measured the cascade on master **IR3** (master `ICW3 = 08`, slave ID 3) and left
open whether Apollo's "IRQ3" names master IR2 by convention or whether
`[S3K]` Table 2-3's IRQ2/IRQ3 labels were transposed in that scan. The priority
order printed here — 1 = unit 0, 2 = unit 1, **3 = unit 3**, 4-11 = units 8-15,
12-15 = units 4-7 — is exactly the order a cascade on IR3 produces, with **unit
3 in master IR2's slot** and the slave's eight units interposed between IR3 and
IR4. A second manual, a year later, reproducing the same pairing is not a scan
artefact. `AP_BOARD_RING_IRQ 2` is confirmed, from the document rather than by
elimination. The `RING8_$INT` vector-163 tension C11 records is untouched by
this and stays open. Recorded as **C287**.

*Original row, kept because it explains why the page-image read was owed:* "The
OCR interleaves the unit, priority and device columns, so the individual rows
here are owed a page-image read before any IRQ assignment is taken from them."

## Appendix D, performance, and what it is and is not a source for

**D.1, DMA bandwidth** — hardware figures: "Bus acquisition time can range from
**100 nanoseconds** (minimum) to **2 microseconds** (typical) to **1
millisecond** (worst case; usually during a ring or disk transfer). Once the
controller acquires the bus, it can transfer data over the bus at a rate of **1
microsecond per 16-bit word**." And a design rule: no more than **20 percent** of
bus bandwidth as a long-term average, and "**no single transfer should take
longer than 10 microseconds**".

**These are a cross-check, not a source to adopt.** This core's DMA timing comes
from the 8237's own datasheet — `INTEL_WALK` records "seven separate states,
each composed of one full clock period" — which is the part's behaviour, where
these are the system's including contention. The resolution order puts the
part's manual first. What the appendix offers is a way to *check* the model: a
modelled transfer that is far from 1 µs per 16-bit word would be worth
explaining. **Not measured yet.**

**D.2, interrupt processing overhead** — Table D-1, microseconds, "observed times
may vary up to 10 percent": device interrupt to the first instruction of the
interrupt routine **125**; enabling the device on return **10**; exit with no
eventcount advance **110**; with an advance and nobody waiting **200**; with
someone waiting **265**. A routine that wakes a waiting process therefore costs
125 + 265 = **390 µs**, and with no user routine at all the system handler's own
advance costs **260** or **325 µs**.

**These are AEGIS's software costs, not the machine's**, and this core models the
hardware. They are recorded because they bound what a *real* DN3000 could do
with interrupts, which is the kind of figure that settles an argument about
whether an emulated rate is plausible.

**D.3** gives `pbu2_$wire`, `pbu2_$map` and `pbu2_$unwire` costs on a DSP80 as
SVC overhead plus a per-page term — `0.909 + 1.091n` milliseconds for the
wire/map/unwire approach against `0.913n` for a permanently wired buffer.

## Chapters 1 and 2: two buses this machine does not have

**Chapter 1, the MULTIBUS** (1-1 to 1-14). Compliance levels `MASTER D16 M16
I16 VO L` and `MASTER D16 M20 I16 VO L` and which node type has which (Table
1-1: `DN660`/`DSP160` 16-bit serial arbitration, `DSP80`/`DSP90` 20-bit
parallel, `DN5xx`/`DN5xx-T` 20-bit serial); bus control, data path, memory and
I/O address paths; eight interrupt request lines, "line 0 is the highest
priority", non-bus-vectored; address translation both ways, the I/O map, and the
CSR page; configuration rules for 8- and 16-bit controllers (one 8-bit
controller per bus, CSRs at `80-FF` of page 0 because an 8-bit controller
"respond[s] to any address in the range 0-FF, modulo 255"); Table 1-2's
system-device address usage; Table 1-3's interrupt line owners (0 customer, 1
COM-ETH, 2 COM-X.25/ComController, 3 Magtape, 4 SMD/FSD-500, 5
VERSATEC/IMAGEN, 6 parallel/line printer, 7 reserved); and §1.4 byte swapping
with `pbu_$control`'s `pbu_swap_off`, `pbu_swap_words` and `pbu_swap_bytes`.

**Nothing here is implementable and nothing is owed.** No model in
`src/core/model/` has a MULTIBUS, and Table 1-3's interrupt owners are a
different bus's lines from the AT bus's IRQs — they are not a cross-check on
`AP_TAPE_IRQ` and must not be read as one. Recorded so the next reader does not
open chapter 1 expecting the DN3500.

**Chapter 2, the VMEbus** (2-1 to 2-4). Table 2-1's DN5xx-T address layout, bus
grant level 2, address modifiers `2D`/`3D`/`0D`, customer interrupt level 5,
the status/ID byte (`F8`-`FE` for customer units 8-14, whose bottom nibble is
the unit number), and the GPIO calls that do not apply because there is no I/O
map between the bus and the device. The `DN5xx-T` is not a model this core
carries either.

## Chapters 4 to 12: the GPIO runtime, which is the software our traces run

These chapters describe `pbu_$`/`pbu2_$` — the PBU Manager — and this matters
because the kernel symbols a boot trace resolves to (`PBU_$DMA_STOP`,
`PBU_$PAGE_END`) are this package. Read for what they say about the *hardware's*
behaviour; the driver-authoring advice is not repeated here.

**§3.3 and §6.1.3: the AT bus does not generate bus time-outs.** Stated twice,
and a third time in §7.2.2's NOTE. "Therefore, you cannot use the GPIO calls
`pbu_$read_csr` or `pbu_$write_csr` to test for controller presence on the bus
... you must tweak the appropriate device register and see if it responds."
§6.1.3's body says the MULTIBUS and VMEbus *do* time out, so this is a property
of the AT bus alone. `ap_board.c`'s empty-slot branch already answered `FF`
without faulting and called that an inference; it is now cited.

**§3.4: DMA and IRQ lines float on AT controllers**, and the enable bit must be
set before `pbu[2]_$dma_start` — "the DMA line will float unless the dma enable
bit is set", from the §7.1.2 listing. §8.2.2's NOTE says the same for interrupt
lines.

**§7.1.2 and §3.6: the DN3000's non-bus-master DMA is one page at a time.**
"DMA transfers without the I/O map are limited to **1024 bytes** of data per
operation and **must not cross page boundaries**", and the interrupt routine
restarts the next 1 KB itself. That is what `PBU_$PAGE_END` is, and why a tape
read of one 512-byte block is not one long DMA. `pbu_$dma_start` and
`pbu_$dma_stop` must surround **every** operation "whether successful or not",
and `pbu_$dma_stop` "must, in any case, be made so that software can reset its
knowledge of who is using the DMA channel" — a `dma_start` without its
`dma_stop` leaves the channel unavailable and the next one fails with
`REQUESTED DMA CHANNEL IN USE`.

**§7.3: 12 MHz and 6 MHz.** "The MC68020 programmed I/O transfer rate is 12 MHz
versus the specification for the PC AT compatible bus DMA transfer rate of 6
MHz." A second document for the pair `002398-04` Appendix A gives as `#25` and
`#26`; cited in `board/ap_atbus.h`.

**§8.2.3.1: the System Interrupt Handler masks the device on entry.** "After
determining which device has requested the interrupt, it disables further
interrupts from the device by **resetting the appropriate bit in the interrupt
mask register**." If no user interrupt routine exists it advances the eventcount
and exits *without* re-enabling, and the driver must call `pbu_$enable_device`
again. With Appendix B's `pbu_$interrupt_flags_t` — `pbu_$interrupt_advance`
and `pbu_$interrupt_enable`, returned *by* the user routine — this is the whole
explanation of the 8259 IMR traffic around every device interrupt in a boot
trace. Nothing to implement; it is why the trace looks the way it does.

**Appendix B's `pbu_$dma_options_t` names exactly the 8237 modes this core
implements**: `pbu_dma_adr_decr` ("DMA hardware decrements the address ... the
default is to increment"), `pbu_dma_auto_init`, `pbu_dma_cascade`, and
`pbu_dma_ext_mem` ("DMA to PC AT compatible or PC XT compatible extension
memory", i.e. the page register). `pbu_$dma_direction_t` is `pbu_dma_read` /
`pbu_dma_write`, defined from the *controller's* point of view —
`pbu_dma_read` is "the PC AT compatible controller **reads** processor memory",
which is a write to the bus. Channel numbers are 0-7.

**Chapters 5, 9, 10, 11 and 12 are software structure** — insert files, global
drivers and MUTEX locks, binding and DDE, the Device Descriptor File in its
three versions, and `pbu_$acquire`/`aqdev`. The one fact with hardware content:
a DDF's unit number "must match the **lowest** interrupt level on which the
device interrupts", AT range 0-15, MULTIBUS 0-5 (16-bit) or 0-7 (20-bit),
VMEbus 8-14.

**Appendix A, the commands** — `aqdev`, `crddf`, `cvt_at`, `rldev`. `cvt_at` is
where C288's three worked conversions come from. `crddf -dma_channel` is how a
driver is told its channel, and the DESCRIPTION notes that option "is not used
by the operating system and [is] only for the optional use of the driver".
