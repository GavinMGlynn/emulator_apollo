# `008778-03` walked whole — coverage record

*Domain Series 3000/4000 Technical Reference*, Aug 1987. **209 PDF pages.**

## Why this file exists

`CLAUDE.md`: *a document that turns out to contain one unimplemented thing is a
document that must be read WHOLE — page by page, line by line.* This one
triggered it on 2026-08-19: Table 2-3 was found to name IRQ1 as "2681 SIO
**Port 1**" and to list **no on-board line for Port 2**, where `ap_sio_irq` ORs
both DUARTs into IRQ1 (`FINDINGS.md` C237). That is one fact this core did not
have, so the whole document is now being derived.

**A document consulted about one question was never consulted about the rest.**
`019411-A00` was grepped, declared silent, then read as page images and yielded
three registers, a whole address map, a fourth memory bank and a bank-layout
correction — from ten pages.

## How to read this record

Every page range gets a row, including the ones that yield nothing: a section
recorded as *no emulator content* is a finished section, and that is what makes
a **walked** document distinguishable from a **sampled** one later. Pages are
read as **images**, never as a text layer — OCR mangles precisely the register
and timing tables that matter, and `pdftotext` interleaved this document's
two-column tables when it was tried.

Status values: `derived` (everything in it is in code or in a named gap),
`confirms` (agrees with code already, nothing to change), `none` (no emulator
content), `GAP` (something is missing from code and is named).

| 33 | Table 2-3, Interrupt Request Priorities | **GAP** | IRQ1 is "2681 SIO **Port 1**"; the starred rows enumerate the on-board CPU lines (timer, SIO port 1, cascade, calendar, diagnostics) and **none is SIO Port 2**. `ap_sio_irq` ORs both DUARTs into IRQ1. The two "SPE Board Serial Line" rows (IRQ4, IRQ9) are an AT-bus expansion board, not the on-board second DUART. Tension: Domain/OS *arms* `sio2`'s IMR, which it would not do for a part it believed could not interrupt. `FINDINGS.md` C237 states the discriminating experiment |

| 16 | §1.1 System-Level Operation, §1.2 System Buses | `confirms` | Dual bus; the bus interface holds the DMA and interrupt controllers. **Series 4000 Address Translation Map**: noncontiguous DMA and the "512-KB window through which external AT-compatible bus masters can access CPU main memory" — already cited in `ap_atmap.h` |
| 17 | §1.3 Virtual Bus | `confirms` | "In the Series 3000, the virtual address appears to *wrap* at 26 bits, the five high-order (27:31) bits are simply ignored. The Series 4000 makes use of all virtual address bits." Already the `address_mask` of both maps in `ap_board.c`, quoted there |
| 17 | §1.3.1 **Virtual Cache** | **GAP** | "implemented in the Series 4000. It is an **8-KB, direct-mapped** cache that contains **2048 4-byte** instruction and/or data entries. The virtual cache uses a **write-through with write-allocate** design that causes the cache to be updated (along with main memory) for every memory write placed in the cache." **Nothing in `src/core` models a board-level virtual cache** — `grep -rn "virtual cache\|virtual_cache"` is empty. This is *not* the 68030's on-chip cache: §1.3 has the MC68020 generating the address and the cache sitting on the **virtual bus** beside a separate PMMU. **Open question the walk must settle in chapter 3**: whether a DS3500, whose 68030 has on-chip caches, carries this external cache at all, or whether it is a DS4000-era (68020 + 68851) structure |
| 17 | §1.3.2 **Write Buffer** | **GAP** | "a Series 4000 device ... that resides on the virtual bus **between the microprocessor and the PMMU**. This buffer allows the CPU to concurrently update the cache and execute cache read cycles **without waiting for write cycles to complete**." Nothing models it. It is a timing structure and this core's whole claim is emergent timing, so it is not cosmetic |
| 17 | §1.4 System Interrupts | `confirms` (one note) | IRQ0–IRQ15 into the controller. **Note for later**: "All of the devices shown on the AT-compatible bus ... **except for the floppy drive** ... use interrupts", against Table 2-3's "IRQ6 Floppy Drive or User Device" and `AP_DISK_FLOPPY_IRQ 6`. The two are reconcilable — the line is *assigned* and this drive does not *use* it — but it is flagged until a page settles it |

| 18 | Figure 1-1, DS3000 block diagram | `confirms` | **12-MHz MC68020**, MMU, FPU, boot PROM; main memory **2–8 MB**; physical bus 24 address / 32 data; 18-bit physical addresses to the memory control and mux; 8-MHz AT bus with 24 address, 16 data, **7 DMA channels**, 16 interrupt lines. `dn3000` in the model table is 68020 @ 12 MHz with 8 MB — agrees. **One** serial-port block, labelled `KBD` and `SIO1` only, which is why Table 2-3's single "2681 SIO Port 1" row fits a DS3000 exactly. **No virtual cache and no write buffer appear on this diagram** |
| 19 | Figure 1-2, DS4000 block diagram | **GAP (a whole model)** | **25-MHz MC68020**, **PMMU MC68851**, FPU **MC68881**, **VIRTUAL CACHE** on the logical bus and **WRITE BUFFER** between it and the PMMU; main memory **4–32 MB**; serial ports **`KBD`, `SIO1/2/3`**. **This machine is absent from the model table.** `--list-models` has `dn3000` (68020 @ 12 MHz = the DS3000) and `dn4500` (68030 @ 33 MHz = the Series *4500*); the DS4000 is a 25-MHz 68020 with a 68851 and a 68881 and is neither. `DS4000_MAP` in `ap_board.c` is named after it while actually serving the DS3500 |
| 18–19 | where §1.3.1/§1.3.2 belong | *resolves the open question above* | The virtual cache and write buffer are drawn on the **DS4000** figure and **not** on the DS3000's, and both sit on a **68020** logical bus beside a separate 68851. So they are DS4000-era structures, not something a 68030 DS3500 is shown to carry. Whether a DS3500 has them is still not settled by these figures; chapter 3 is where to look |
| 19 | FPU part number | **note** | The DS4000's FPU is drawn as **MC68881**, not the MC68882 the model table gives every Series 3500/4500 row. Consistent — different machine — but recorded so a later reader does not "correct" one to the other |
