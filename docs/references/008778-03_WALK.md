*Domain Series 3000/4000 Technical Reference*, Aug 1987. **209 PDF pages.**

## Why this file exists

`CLAUDE.md`: *a document that turns out to contain one unimplemented thing is a
document that must be read WHOLE — page by page, line by line.* This one
triggered it on 2026-08-19: Table 2-3 was found to name IRQ1 as "2681 SIO
**Port 1**" and to list **no on-board line for Port 2**, where `ap_sio_irq` ORs
both DUARTs into IRQ1 (`FINDINGS.md` C237). That is one fact this core did not
have, so the whole document is now being derived.

**A document consulted about one question was never consulted about the rest.**
`019411-A00` was grepped, declared silent, then read as page images and yielded
three registers, a whole address map, a fourth memory bank and a bank-layout
correction — from ten pages.

## How to read this record

Every page range gets a row, including the ones that yield nothing: a section
recorded as *no emulator content* is a finished section, and that is what makes
a **walked** document distinguishable from a **sampled** one later. Pages are
read as **images**, never as a text layer — OCR mangles precisely the register
and timing tables that matter, and `pdftotext` interleaved this document's
two-column tables when it was tried.

Status values: `derived` (everything in it is in code or in a named gap),
`confirms` (agrees with code already, nothing to change), `none` (no emulator
content), `GAP` (something is missing from code and is named).

## Where the walk and the oracle disagree

The walk is checked against `ext/mame` where the oracle has an opinion. **Twice
the oracle was wrong; once the manual was.**

### The manual, once — Table 6-6's 348 Mbyte geometry (chapter 6)

Recorded first because it is the one that goes the other way, and because a
record that only ever catches the oracle is not being read critically.

Table 6-6 prints, in one column: "Capacity **380 MB**", "Capacity per track
**20,808 bytes**", "Number of cylinders **1023**", "Number of heads **8**".
20,808 × 8 × 1023 is **170 MB** — the column contradicts itself three rows up.
20,808 × **15** × **1223** is **381.7 MB**, which is the stated capacity
exactly. The cylinder and head cells are copied from the 155 Mbyte column
beside them, and Table 6-5 carries the same slip: "Formatted sectors 147,312"
is 1023 × 8 × 18, the *other* drive's count, where 1223 × 15 × 18 is 330,210.

`omti8621.cpp`'s disk type for the Maxtor EXT-4380-E is 1223 × 15 × 18, which
Apollo's own published capacity confirms and Apollo's own published geometry
contradicts. `image/ap_awd.h` keeps the oracle's numbers and now says why.

### The oracle, twice

1. **`DN3500_RAM_END 0x3ffffff` for a 32 MB build.** `1000000`–`3FFFFFF` is
   48 MB. The same file gives `DN5500_RAM_END 0x2ffffff` for the same 32 MB,
   four lines apart, so the oracle contradicts itself and §1.5.2's four-point
   progression says which one is the slip. This core had imported the wrong one.
2. **`DN5500_MEM_PRESENT_BYTE 0xAA // 8-8-0-0`.** `019411-A00` §4.2.1.18's
   published table gives `AA` for **four 4-MB boards** and **`F0`** for
   `8 8 - -`. Our implementation, built from that table rather than from the
   oracle, produces `F0` — checked by running it. Nothing was changed here; it
   is recorded because it is the second time the published table has
   out-accurated the oracle.
