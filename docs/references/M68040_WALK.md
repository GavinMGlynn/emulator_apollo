## The deferral was false, twice over

The plan item read "**no 68040 core exists**", and I repeated that several times
today before checking it. `src/core/cpu/m68040/` holds **26 files** — registers,
ATC, cache, descriptors, FPU, FP pipeline and six timing modules — with **14
test suites**, and every header cites `MC68040 User's Manual (1993)` by section
and figure, several of them "transcribed from the page images". Two rows of the
model table declare `.cpu = AP_CPU_M68040`.

What does *not* exist is an instruction **stepper**, which is the separate
DN5500 item. The manual is already a load-bearing source for this core.

**That is the second deferral in one day whose premise was false**, after
`[020]`'s. The pattern is worth naming: *a deferral that names a missing
subsystem is a claim about the code, and claims about the code get checked with
`grep`, not with memory.*

| 222-253 | **§8 EXCEPTION PROCESSING — done, 32/32.** **Table 8-1 Exception Vector Assignments**, Table 8-2 Tracing Control, 8.2.8 Breakpoint, **Table 8-4 Exception Priority Groups**, 8.3-8.4, Table 8-5 Write-Back Data Alignment | **completes the vector picture across three parts, and names a stack frame this core has never had** | **Table 8-1 is explicit about what each part does *not* use**, which is what makes it settle the question the `[020]` walk opened. Vectors **48-55 are "Floating-Point Exception Vectors"** here, and this core already names 48-54 from `[881]` Table 8-1 — so `confirms`, and it **refines the `[020]` finding**: that manual's "48-63 unassigned" is the *processor* leaving them for a coprocessor to define, not a contradiction, and a 68020 with a 68881 uses them. **Vector 56 is the real divergence and this table states it outright**: "Defined for MC68030 and MC68851, **not used by M68040**", with 57 and 58 the same for the 68851. So `AP_M68030_VECTOR_MMU_CONFIGURATION = 56` is right for the 68030, absent on the 68020 and **explicitly not used** on the 68040. Vector 13 gets the same treatment — "Defined for MC68020 and MC68030, not used by M68040" — retiring the coprocessor protocol violation. Also renamed here: vector 2 is **Access Fault** (was Bus Error), 5 is **Integer** Divide by Zero, and 7 adds **`FTRAPcc`**. **§8.3/§8.4 name a frame format this core has never had**: "exception processing for access error exceptions creates a **format `$7`** stack frame", and `ap_m68030_exception.h`'s enum holds `$0`, `$1`, `$2`, `$9`, `$A`, `$B` — `$7` appears nowhere in either CPU tree. Consistent with there being no 68040 stepper, and now recorded rather than implicit. **Three behaviours worth having from the same pages.** `RTE` on a `$7` frame **mutates it**: if the status bits indicate a pending trace, floating-point post-instruction or unimplemented floating-point exception, "the `RTE` **changes the access error stack frame to match the pending exception** and fetches the vector for the exception" — an `RTE` that rewrites its own frame and vectors elsewhere. On an odd-PC restore with user trace enabled an address error is taken, and "the SR stacked for the address error has the SR **S-bit set**. For previous members of the M68000 family the S-bit is **clear**" — a stated difference from every earlier part. And the M68040 "uses **long-word operand transfers wherever possible**" for stack frames and "does **not necessarily** read or write the stack frame data in sequential order", with the warning that "system software should not depend on a particular exception generating a particular stack frame". **Table 8-4 is a different exception *model*, not a different table**, and the manual says so: "the method used to process exceptions in the M68040 is **significantly different** from that used in earlier members of the M68000 processor family due to the **restart exception model** ... the remaining exceptions are **regenerated when the current instruction restarts**." Nine priority groups (0-8) where `[020]` Table 6-3 has three, and **Address Error moves from group 1 to group 5** — below the data access error and above trace. *That is the explanation for the frame findings above*: a part that **restarts** needs no 46-word continuation frame, which is why it has `$7` and the 68030 has `$B`. **Table 8-2's tracing control is identical to `[020]` Table 6-5** — `00` none, `01` change of flow, `10` any instruction, `11` undefined — a third printing of the four modes `ap_m68030_regs.h` holds, and the same "an illegal or unimplemented instruction does not cause a trace since the instruction is not executed". **§8.2.8's breakpoint diverges from the 68020's**, which matters because this core implements the 68020/68030 behaviour: the opcodes are `$4848`-`$484F`, the acknowledge is "a breakpoint acknowledge cycle (read cycle) with an **acknowledge transfer type and transfer modifier value of `$0`**" rather than the 68020's CPU space `$0` with the number on `A4:A2`, and — the behavioural half — "after external hardware terminates the bus cycle with **either `TA` or `TEA`**, the processor performs **illegal instruction exception processing**". On the 68020 a `DSACKx` termination returns a word that *replaces* the instruction in the pipe; on the 68040 both terminations end the same way. **Table 8-5** gives write-back data alignment across `WB1D`, `WB2D` and `WB3D`, with `WB1D` **memory**-aligned in the byte positions of the data bus lanes and `WB2D`/`WB3D` **register**-aligned in the least significant byte or word. **The frame set is different again, and smaller.** §8.1: "the processor creates one of **five** exception stack frame formats", against the 68020/68030's six. Named here: **`$0` four-word** (`RTE` increments the stack by **eight**), **`$2` six-word**, **`$3` floating-point post-instruction** (increments by **`$C`**, and "if another floating-point post-instruction exception is pending, exception processing begins immediately for the new exception"), and **`$7` access error — thirty words**, "created for data and instruction access faults other than instruction address errors". `$3` and `$7` are both absent from `ap_m68030_exception.h`'s enum, and `$9`, `$A` and `$B` are absent from this part. **The `$7` frame carries work, not just state**: it "contains pending write-backs that the access error exception handler **must complete**", in the order write-back 1, 2, 3, with a push completed first. **Table 8-6 is that handler's contract** — six main cases (all-read, cache push, normal write, `MOVE16` write, write page fault, and impossible combinations) against `SSW_RW`, `SSW_PUSH` and the three write-back status fields, giving the data to write for an easy cleanup and the action for a hard one. Note c is the one to carry: "a cache push physical bus error is normally considered a **fatal error**. For these cases, the `FA` field is a **physical** address, not a logical address as in the other cases." §8.4.6's continuation bits `CP`, `CT` and `CU` are how the `RTE` rewrite works, and **"the processor sets only one ... if the access error exception handler sets multiple bits, operation of the `RTE` instruction is undefined"**. `ATC` distinguishes an ATC fault — nonresident entry, bus error during table search, invalid descriptor, or privilege violation — from a bus-errored access; `LK` marks a locked read-modify-write. *Also captured*: §8.2.10's reset state, `S` = 1, `M` = 0, `T1`/`T0` = 0, `I2:I0` = **`$7`**, `VBR` = `$0`; §8.1's warning that the bus cycles of exception processing "are **not guaranteed to occur in the order** in which they are described"; the double-bus-fault halt, from which "only an external reset can restart"; and §8.2.9's interrupt-mask worked example, where a level 7 handler behaves differently from a level 6 one because level 7 is transition-sensitive. *Fidelity*: pp. 226, 240, 252 read as page images; the other 29 as text |
