## The deferral was false, twice over

The plan item read "**no 68040 core exists**", and I repeated that several times
today before checking it. `src/core/cpu/m68040/` holds **26 files** — registers,
ATC, cache, descriptors, FPU, FP pipeline and six timing modules — with **14
test suites**, and every header cites `MC68040 User's Manual (1993)` by section
and figure, several of them "transcribed from the page images". Two rows of the
model table declare `.cpu = AP_CPU_M68040`.

What does *not* exist is an instruction **stepper**, which is the separate
DN5500 item. The manual is already a load-bearing source for this core.

**That is the second deferral in one day whose premise was false**, after
`[020]`'s. The pattern is worth naming: *a deferral that names a missing
subsystem is a claim about the code, and claims about the code get checked with
`grep`, not with memory.*

**Corrected 2026-09-09, and the correction is about the method.** The §10 and §3
predictions held exactly — both read as confirmation, page after page. **§4's
did not**: the audit called it "barely touched" on two citations, and
`ap_m68040_cache.h` turns out to quote §4.1 and §4.2 at length. The reason is
that the audit counted citations of the form `§N.M`, and that header quotes the
manual's prose **without a section number**. *Counting citations by section
number undercounts a header that quotes rather than references.* A walk planned
only on the audit would have re-derived a finished module.
