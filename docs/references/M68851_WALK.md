## Method: this one is scanned, and it defeated the test I was using

what a born-digital PDF looks like, and is how `[PRM]` was (correctly) judged.

It is wrong here. `pdfimages -list` shows **full-page 2728×3621 JBIG2 images at
400 dpi** on every page: this is a scan whose OCR layer happens to be typeset in
Helvetica. Its text extracts `$00A01A00` as `$OOA01AOO` — letter-O for zero,
the exact failure mode `CLAUDE.md` names.

**So the discriminator is `pdfimages -list`, not `pdffonts`.** A full-page image
at scan resolution means the text layer is a recognition and cannot be trusted.
`[PRM]` passes that test too — small figures only — so its conclusion stands,
but it passed the weaker test first, and `[851]` is what showed the weaker test

## §5.1 — walked, and it confirms throughout

No defect. Every rule checked is implemented and cited, several to the figure
that states them.

- **§5.1.1's tree structure**: up to five levels, three root pointers — SRP,
  CRP and **DRP** (the DMA root pointer, one of the six features `[030]` §9.6
  lists the 68030 as lacking).
- **§5.1.2.2's indirection rule, and the prohibition inside it.** "The page
  descriptor located at the address given by the address field of the indirect
  descriptor **must not have a DT field with the long or short code**...
  Otherwise, the descriptor will be treated as invalid, and the MC68851 will
  create an ATC entry with an error condition signaled (BERR bit set)." That is
  what stops a chain of indirections, and `ap_m68851_search.c` implements it as
  "`DT = 'PAGE DESCRIPTOR'` is accepted and `OTHERWISE` is invalid", citing
  Figure 5-10's two illegal cells.
- **§5.1.4.1.2's limit bypass**: "The limit field and L/U bit of the root pointer
  are **ignored if the first level of the table search is a lookup by function
  code**." `limit_violated` has it, cited to Figure 5-26 — and extends it
  correctly to the DMA root pointer, on the ground that "a DMA search always
  performs a function code lookup, so its root pointer's limit is bypassed for
  the same reason `FCL` bypasses the others'".
- **§5.1.4.1.1's L/U bit**: zero means the limit is an unsigned *upper* limit,
  one means a *lower* limit — the same polarity `[030]` §9.5.2 gives and
  `ap_m68030_desc_index_within_limit` implements.
- **§5.1.2.1's type-2 page descriptor** (a page descriptor above the lowest
  level, giving early termination and a contiguous mapping), **§5.1.2.4's paging
  of tables**, **§5.1.2.5's dynamic allocation**, **§5.1.3.1's protection
  fields** (`WP`, `S`, `RAL`, `WAL`, `G`), **§5.1.3.2's ATC management bits**
  (`L` lock and `SG` shared-globally, and that an `SG` entry ignores the task
  alias and can only be removed by `PFLUSHS`/`PFLUSHA` or by altering `TC` or
  the root pointer), and **§5.1.3.3's `CI` cache-inhibit bit** driving `CLI`.

## §6.1.1 — the root pointer registers, and one investigated non-defect

`ap_m68851_rp.c` and `_regs.c` match §6.1.1 field for field: `L/U` at bit 63,
`LIMIT` at 62-48, `SG` at 41, `DT` at 33-32, `TABLE ADDRESS` at 31-4, and bits
3-0 "not used by the MC68851 and may be used by the operating system for other
purposes". The four `DT` encodings — `$0` invalid, `$1` page descriptor, `$2`
valid 4-byte, `$3` valid 8-byte — and the rule that `PMOVE` refuses to load an
invalid one while `PRESTORE` can.

### §6.1.1.4 reads like a defect report against this core, and it is wrong

Its `$1` entry ends: "If the DT field of a root pointer is set to `$1`, the
MC68851 performs a limit check **regardless of the state of the FCL bit**."
`ap_m68851_search.c` returns an early-termination mapping from a root
`DT = $1` and performs no limit check at all, so at face value that is a defect.

**It is not, and two sources settle it:**

- **Figure 5-23, *Detailed Flowchart of MC68851 Table Search Operation*, draws
  the path with no limit check on it.** `CHECK DESCRIPTOR TYPE OF ROOT POINTER`
  → `DT = 'PAGE DESCRIPTOR'` → `TYPE ← 'EARLY'` → `CREATE ATC ENTRY`.
  `PERFORM LIMIT CHECK` appears only after `ENTERING A LEVEL TABLE SEARCH`.
- **§6.3.1.2 defines the violation** as "a table index extracted from a logical
  address exceed[ing] the limit field of a corresponding long format
  descriptor". This path extracts no table index.

The flowchart and the error definition against one sentence of register-field
prose — the same shape as `[881]`'s transposed `FATANH` signs, where the
operation tables were right and the paragraph was not. Left as it is, and
recorded in the code, because the next reader to meet §6.1.1.4 will read it as a
bug.

**Figure 5-26 is `limit_violated` branch for branch**: `y = 'RP'` with
`FCL = 1 OR DRP IS RP` returns, `LAST_SIZE = 4` returns, and `LAST_SIZE = 8`
performs `LPA[TIx] ≤ LIMIT` for `L/U = 0` and `≥` for `L/U = 1`. That is what
the module already had, cited to that figure.

## §7 — the gap: the table search enforces `WP` and nothing else

**`ap_m68851_search.c` accumulates the write-protect bit across the path and
drops every other protection field.** `ap_m68851_descriptor.c` decodes `RAL`
(bits 47-45), `WAL` (44-42) and `S` (40) from every long-format descriptor, and
`ap_m68851_search_result_t` carries `write_protect`, `cache_inhibit`,
`modified`, `gate`, `lock` and `shared_globally` — but neither the supervisor
bit nor either access level. They are read and discarded at the search boundary.

Four sections require them:

- **§6.3.1.3, attempted user access of supervisor address**: "If bit FC[2] of a
  logical address is zero and a set S bit is encountered during the table search
  in a long format descriptor for that address, an ATC entry will be made with
  its internal bus error (B) bit set."
- **§6.3.1.4, access level violation**: an access whose level is "less privilege
  (numerically greater) than that indicated by the RAL field of a long
  descriptor in the table search path for a read, or less privilege than the RAL
  or WAL fields for a write" makes a `B`-bit entry.
- **§7.2.3.1, write protection**: a write needs a level "less than (more
  privileged than) or equal to the lowest value (most privileged) of **all WAL
  or RAL fields** in the branch" — and, because denying read implies denying
  write, "the MC68851 **prohibits write accesses to all areas to which a task
  does not have read access**... regardless of the write access level".
- **§5.1.3.1** names all of `WP`, `S`, `RAL`, `WAL` and `G` as the protection
  information carried in the tables.

`ap_m68851_atc.h` already describes the *mechanism* correctly — protection is
"evaluated when the ATC entry is made" and a denial is cached with the `B` bit,
rather than storing `RAL` and `S` and re-checking on every hit — so the design
anticipated this. What is missing is the evaluation itself.

**Scope, stated so the gap is not overstated.** `PVALID`'s access-level
comparison against `CAL`/`VAL` *is* implemented, in `ap_m68851_pvalid`; this is
about the table search, not the instruction. And the DN3500's MMU is the
68030's, which has **no access levels at all** (`[030]` §9.6 lists them among
the six features it lacks) and whose supervisor protection *is* enforced —
`ap_m68030_search_permits_access` takes the supervisor flag. So no in-scope
machine is affected: this is the `m68851` reference module being incomplete
against its own manual.

*What would close it*: accumulate `S`, `RAL` and `WAL` across the search the way
`write_protect` already is, take the most privileged of all `RAL` and `WAL` seen
for the write test, and return a denial the ATC fill can cache as `B`. The
suites to extend are `m68851_search_suite` and `m68851_atc_suite`.

## §8 — walked 6/6, and its two figure captions are transposed

**Figures 8-3 and 8-4 have their captions swapped.**

| Figure | Caption | Contents |
| --- | --- | --- |
| 8-3 | "Breakpoint Acknowledge **Data** Register Format" | `BACx` — `BPE` at bit 15, `BREAKPOINT SKIP COUNT` at 7-0 |
| 8-4 | "Breakpoint Acknowledge **Control** Register Format" | `BADx` — `REPLACEMENT OPCODE`, all sixteen bits |

The register labels *inside* the figures are right; only the captions are
exchanged. The surrounding prose settles it twice over: §8.1.1 says the data
registers `BAD0`-`BAD7` "can be loaded with an opcode to be transferred to the

**This core has it right**, and `ap_m68851.h` states it in the same words the
figure contents do: "`BADx` is sixteen bits of replacement opcode with no other
fields; `BACx` is an enable at bit 15 and a skip count at bits 7-0". So it was
derived from the register labels and the prose rather than from the captions —
which is the reading that survives.

Also captured: the eight breakpoint opcodes `$4848`-`$484F` and their
register-pair correspondence; the breakpoint acknowledge cycle's CPU-space
address encoding (Figure 8-1, `FC = $7`, breakpoint number at bits 4-2); the two
terminations, bus error giving illegal-instruction vector 4 and a supplied
opcode replacing it in the pipe; and that "during the breakpoint cycle, the skip
count is decremented by one", which `ap_m68851_breakpoint_acknowledge` is

### One rule captured that belongs to a layer this project does not have

§9.1.2: "Although the MC68851 decodes the full address range specified on
A0-A12, the MC68851 register set occupies only the lower 32 bytes of this range.
**Any access above this range (A0-A12 ≥ `$20`) is ignored for a write cycle and

Also captured: §9.1.1's chip-select derivation from `FC0-FC3`, the CPU space

## §1-§4 — walked, and §4.2.3.3 completes the protection gap's specification

§1 and §2 are architectural. Two facts worth keeping: "up to eight coprocessors
may reside on the same local bus simultaneously, although **only one of those
may be an MC68851**" — because it always operates as coprocessor zero, which
§9.1.1 and `[030]` §10.1.3's CpID rules both state; and §3.7.1's `RMC`, "asserted
for the duration of the read-modify-write sequence and should be used as a **bus
lock**", which is a fifth witness for the semantics wired into
`ap_board_set_processor_rmc` on 2026-09-06.

**§4.1.1's reset specification is exact and this core matches it**, including
the part that is easy to miss. Reset clears `TC`'s `E` bit, the `E` bit in each
of the eight `BACx`, and the `AC` register's `ALC` field — and §8.1 adds that
"the BPE bit is cleared at reset; **the skip count field is not**".
`ap_m68851_reset` zeroes the structure and then *restores* the skip counts and
replacement opcodes, with a comment saying why: "a reset that cleared them would
silently rearm every breakpoint at its first fire".

**§4.2.3.3 enumerates every condition that terminates a translation with
`BERR`**, and that list is what makes the protection gap above actionable:

1. a write to a write-protected page — **implemented**
2. an access that exceeds the current access level — **the gap**
3. an access through an ATC descriptor with its bus error bit set —
   **implemented**
4. a breakpoint acknowledge against a `BACx` with a zero skip count —
   **implemented**
5. the same against one with its `E` bit clear — **implemented**
6. a read-modify-write to a page with no resident ATC descriptor, or with its
   modified bit clear, or write-protected — **the gap**

Condition 6 is *not* the status write-back's own read-modify-write, which is
modelled and cited to §4.3.2.2 — "the part holds the bus for the read and the
write together so that another MC68851 sharing the tree cannot slip between
them". It is a translation-time fault, and it belongs with condition 2.

Also captured: §4.1.2's reset-time configuration latched from `D0-D7` (bus size,
ATC decision time, `CLI` assertion, `PAS` timing, fast table search on `D5`,
early processing startup on `D6`, assertion inhibit on `D7`); §4.2's synchronous
and asynchronous translation modes with their `LAS`/`PAS` relationships; §4.3's
table search bus operation, where the part drives `FC3-FC0 = $5` as bus master
and "the only write cycles initiated by the MC68851 are byte operations to
update the used bit, modified bit, or both"; and §4.4's logical bus arbitration.

## §5.1.6 and §5.2 — the gap's algorithm, and the ATC entry format

**§5.1.6 specifies the accumulation the search is missing**, completely:

> The supervisor-only, write-protect, and shared attributes may be specified at
> any level of the translation tree when using long format descriptors. **An
> attribute will be conferred if the corresponding bit is set at any level.**
> The effective RAL of a page will be the **minimum (most privileged) of all RAL
> fields encountered**. The effective WAL of a page will be the **minimum of all
> WAL fields encountered**, with the exception that **if a WP bit is set for the
> page at any level, the page will not be writable for any access level**. If
> there are no long format descriptors in the path ... the page is not
> restricted to supervisor-only, and the effective RAL and WAL are **both `$7`**
> (least privileged).

So `S`, `WP` and `SG` OR across levels; `RAL` and `WAL` each take the minimum;
`WP` anywhere beats any `WAL`; the defaults are not-supervisor and `$7`/`$7`.
The gap needs no design work — the algorithm is written down. Folded into the
plan item.

**§5.2's ATC entry formats** are what `ap_m68851_atc.h` already carries: the tag
is `SG | TA | FC | LOGICAL ADDRESS` and the data entry is
`L | B | C | W | M | G | PHYSICAL ADDRESS`, 64 of each. Also confirmed there:
the lock ceiling ("it will not be a copy of the page descriptor L bit if there
are already **63** entries with set L bits"), the invalid-first-then-pseudo-LRU
replacement with its valid and history bits, and that "the inverse of the CI bit
is presented on the `CLI` output".

And §5.2.1.2 states the `B`-bit mechanism a third time — "instead of maintaining
the RAL field and S bit in the ATC, the validity of the access is evaluated when
the ATC entry is made. If access is to be denied, an ATC entry is made with the
B bit set" — which is the sentence `ap_m68851_atc.h` quotes and the gap's fix
must satisfy.

## §6.1 — the register set, walked whole

`ap_m68851_regs.c`, `_tc.c` and `_rp.c` carry these field for field.

- **§6.1.2's `PCSR`**: `F` at 15, `LW` at 14, `TA` at 2-0, updated whenever the
  CPU root pointer is written. The root pointer table it reports on is already a
  named `PROVISIONAL` gap in `PROJECT_STATUS.md`, and the `PMOVE` to `CRP` arm
  takes the conservative branch and says so.
- **§6.1.3's `TC`**: `E` at 31, `SRE` at 25, `FCL` at 24, `PS` at 23-20, `IS` at
  19-16, and `TIA`-`TID` in 15-0. Three rules, all implemented and cited:
  writing with `E` clear **flushes the entire ATC**; writing with `E` set runs
  the consistency check where "the TIx fields are added together, and this sum
  is added to PS and IS. The total must be **32**" — the same rule `[030]`
  §9.7.5.3 gives; and on the exception "the TC register is updated with the data
  **except that the E bit is cleared**", which `ap_m68851.c` does in that order
  so software can read back what it tried.
- **§6.1.3.4's eight page sizes**, `$8` = 256 bytes through `$F` = 32K.
- **§6.1.3.3 confirms the DRP limit bypass explicitly**: "A function code lookup
  is **always** performed when the MC68851 executes a table search using the DMA
  root pointer" — which is the reason `limit_violated` gives for extending
  §5.1.4.1.2's bypass to the DRP, and it turns out the manual states it outright.
- **§6.1.5-§6.1.7**: `CAL`, `VAL`, `SCC` and the `AC` register with `MC` at 7,
  `ALC` at 6-4 and `MDS` at 1-0, plus their encodings — `ALC` `$0`-`$3` for zero
  to three access-level address bits, `MDS` `$0`-`$3` for invalid through 64-byte
  module descriptor alignment. `ap_m68851_ac_access_levels` and
  `ap_m68851_pvalid` are built on these, including §6.1.7.1's "the PVALID
  instruction will always cause an exception when MC is clear".
- **§6.1.8's `PSR`**: `B`=15, `L`=14, `S`=13, `A`=12, `W`=11, `I`=10, `M`=9,
  `G`=8, `C`=7, `N`=2-0, with each bit's rule differing between a `PTEST` level
  of zero and one of one-to-seven. The bit order exists so that `BFFFO` finds
  the most significant fault first, and the manual gives the code sequence.

### The protection gap has a second consequence, in `PTEST`

§6.1.8.5's `W` bit: "set if the address tested is not writeable. This may occur
if any descriptor encountered in the search contained a set `WP` bit, **or if
the address tested exceeded the `WAL` field of any long descriptor
encountered**." And §6.1.8.4's `A` bit is set when the address "exceeded `RAL`
for the `PTESTR` instruction, or exceeded `WAL` or `RAL` for `PTESTW`".

So the missing `RAL`/`WAL` accumulation is not only a translation-fault gap — it
also makes `PTEST`'s `W` and `A` bits unreportable. Folded into the same plan
item.

### One rule stated without a consequence

§6.1.3.1: "The E bit must be clear before it can be written set (i.e., the
MC68851 must be disabled before the TC contents can be updated)." This core
accepts a `TC` write with `E` set regardless of the current `E`. The manual
states a requirement **on software** and names no hardware consequence for
breaking it, so the permissive reading is the containable one — the same shape
as the `[146818]` `UIP` case. Recorded rather than invented.

## §6.2-§6.4 — the instructions, and §6.3.1.7 explains condition 6

**§6.3.1.7 gives the reason behind §4.2.3.3's condition 6**, and it is a good
one: the part asserts `BERR` "if the logical bus master attempts to execute a
bus cycle with the `RMC` signal asserted to an address that does not have a
descriptor in the ATC, or to an address whose ATC entry does not have the
modified (M) bit set", because

> This action, by the MC68851, is necessary to allow the **uninterrupted
> sequence of bus cycles required by the TAS, CAS, and CAS2 instructions** of
> the MC68020, without increasing bus arbitration latency to an unacceptable
> level.

So the external MMU refuses up front rather than running a table search *inside*
an indivisible sequence, and the handler is expected to `PLOAD` and rerun. **The
68030 solves the same problem differently** — its MMU is on-chip, so there is no
arbitration latency to protect, and `ap_m68030_access.c` simply carries
`access->rmc` into the walk and `ap_m68030_desc.c` treats it as a write for the
`M` bit. Two parts, two answers, and this core has each part's.

The manual even gives the operating-system workaround: "maintain the page
descriptors of semaphore areas with their L (lock), M (modified), and U (used)
bits always set."

- **§6.2**: `PMOVE`, `PVALID`, `PTEST`, `PLOAD`, `PFLUSH`/`PFLUSHS`/`PFLUSHR`,
  `PBcc`/`PDBcc`/`PScc`/`PTRAPcc`, `PSAVE`/`PRESTORE` — the set
  `ap_m68851_decode.h`'s type and opcode enumerations carry.
- **§6.3.2**: the 68851 returns F-line as **vector 11** for "an unrecognized
  command or condition" and protocol violation as **vector 13**, both as
  *pre-instruction* exceptions — the same two vectors and the same split this
  session worked through for the 68882 on the 68030 side.

### One documented rule the module does not express

§6.2: "**All MC68851 instructions are privileged except PVALID.** An attempt to
execute any other MC68851 instruction while the CPU is in user state will cause
a privilege exception."

Nothing in `src/core/cpu/m68851/` says which instructions are privileged.
`ap_m68851_decode.h` is a *structural* decoder — operation word fields, condition
encodings — and carries no attribute for it, and there is no dispatcher above it
because no machine wires this part.

That is the same shape as the protection gap: **this module is a decoder plus
per-instruction semantics, with no layer that enforces access.** Both belong to
the dispatcher that does not exist, and both are recorded on the one plan item
rather than split.
