## Method: this one is scanned, and it defeated the test I was using

`pdffonts` reports **Helvetica and Times-Roman, Type 1, no OCR font** — which is
what a born-digital PDF looks like, and is how `[PRM]` was (correctly) judged.

It is wrong here. `pdfimages -list` shows **full-page 2728×3621 JBIG2 images at
400 dpi** on every page: this is a scan whose OCR layer happens to be typeset in
Helvetica. Its text extracts `$00A01A00` as `$OOA01AOO` — letter-O for zero,
the exact failure mode `CLAUDE.md` names.

**So the discriminator is `pdfimages -list`, not `pdffonts`.** A full-page image
at scan resolution means the text layer is a recognition and cannot be trusted.
`[PRM]` passes that test too — small figures only — so its conclusion stands,
but it passed the weaker test first, and `[851]` is what showed the weaker test
was not a test. Corrected in `PRM_WALK.md` and `M68881_WALK.md`.

## §5.1 — walked, and it confirms throughout

No defect. Every rule checked is implemented and cited, several to the figure
that states them.

- **§5.1.1's tree structure**: up to five levels, three root pointers — SRP,
  CRP and **DRP** (the DMA root pointer, one of the six features `[030]` §9.6
  lists the 68030 as lacking).
- **§5.1.2.2's indirection rule, and the prohibition inside it.** "The page
  descriptor located at the address given by the address field of the indirect
  descriptor **must not have a DT field with the long or short code**...
  Otherwise, the descriptor will be treated as invalid, and the MC68851 will
  create an ATC entry with an error condition signaled (BERR bit set)." That is
  what stops a chain of indirections, and `ap_m68851_search.c` implements it as
  "`DT = 'PAGE DESCRIPTOR'` is accepted and `OTHERWISE` is invalid", citing
  Figure 5-10's two illegal cells.
- **§5.1.4.1.2's limit bypass**: "The limit field and L/U bit of the root pointer
  are **ignored if the first level of the table search is a lookup by function
  code**." `limit_violated` has it, cited to Figure 5-26 — and extends it
  correctly to the DMA root pointer, on the ground that "a DMA search always
  performs a function code lookup, so its root pointer's limit is bypassed for
  the same reason `FCL` bypasses the others'".
- **§5.1.4.1.1's L/U bit**: zero means the limit is an unsigned *upper* limit,
  one means a *lower* limit — the same polarity `[030]` §9.5.2 gives and
  `ap_m68030_desc_index_within_limit` implements.
- **§5.1.2.1's type-2 page descriptor** (a page descriptor above the lowest
  level, giving early termination and a contiguous mapping), **§5.1.2.4's paging
  of tables**, **§5.1.2.5's dynamic allocation**, **§5.1.3.1's protection
  fields** (`WP`, `S`, `RAL`, `WAL`, `G`), **§5.1.3.2's ATC management bits**
  (`L` lock and `SG` shared-globally, and that an `SG` entry ignores the task
  alias and can only be removed by `PFLUSHS`/`PFLUSHA` or by altering `TC` or
  the root pointer), and **§5.1.3.3's `CI` cache-inhibit bit** driving `CLI`.

## §6.1.1 — the root pointer registers, and one investigated non-defect

`ap_m68851_rp.c` and `_regs.c` match §6.1.1 field for field: `L/U` at bit 63,
`LIMIT` at 62-48, `SG` at 41, `DT` at 33-32, `TABLE ADDRESS` at 31-4, and bits
3-0 "not used by the MC68851 and may be used by the operating system for other
purposes". The four `DT` encodings — `$0` invalid, `$1` page descriptor, `$2`
valid 4-byte, `$3` valid 8-byte — and the rule that `PMOVE` refuses to load an
invalid one while `PRESTORE` can.

### §6.1.1.4 reads like a defect report against this core, and it is wrong

Its `$1` entry ends: "If the DT field of a root pointer is set to `$1`, the
MC68851 performs a limit check **regardless of the state of the FCL bit**."
`ap_m68851_search.c` returns an early-termination mapping from a root
`DT = $1` and performs no limit check at all, so at face value that is a defect.

**It is not, and two sources settle it:**

- **Figure 5-23, *Detailed Flowchart of MC68851 Table Search Operation*, draws
  the path with no limit check on it.** `CHECK DESCRIPTOR TYPE OF ROOT POINTER`
  → `DT = 'PAGE DESCRIPTOR'` → `TYPE ← 'EARLY'` → `CREATE ATC ENTRY`.
  `PERFORM LIMIT CHECK` appears only after `ENTERING A LEVEL TABLE SEARCH`.
- **§6.3.1.2 defines the violation** as "a table index extracted from a logical
  address exceed[ing] the limit field of a corresponding long format
  descriptor". This path extracts no table index.

The flowchart and the error definition against one sentence of register-field
prose — the same shape as `[881]`'s transposed `FATANH` signs, where the
operation tables were right and the paragraph was not. Left as it is, and
recorded in the code, because the next reader to meet §6.1.1.4 will read it as a
bug.

**Figure 5-26 is `limit_violated` branch for branch**: `y = 'RP'` with
`FCL = 1 OR DRP IS RP` returns, `LAST_SIZE = 4` returns, and `LAST_SIZE = 8`
performs `LPA[TIx] ≤ LIMIT` for `L/U = 0` and `≥` for `L/U = 1`. That is what
the module already had, cited to that figure.

## §7 — the gap: the table search enforces `WP` and nothing else

**`ap_m68851_search.c` accumulates the write-protect bit across the path and
drops every other protection field.** `ap_m68851_descriptor.c` decodes `RAL`
(bits 47-45), `WAL` (44-42) and `S` (40) from every long-format descriptor, and
`ap_m68851_search_result_t` carries `write_protect`, `cache_inhibit`,
`modified`, `gate`, `lock` and `shared_globally` — but neither the supervisor
bit nor either access level. They are read and discarded at the search boundary.

Four sections require them:

- **§6.3.1.3, attempted user access of supervisor address**: "If bit FC[2] of a
  logical address is zero and a set S bit is encountered during the table search
  in a long format descriptor for that address, an ATC entry will be made with
  its internal bus error (B) bit set."
- **§6.3.1.4, access level violation**: an access whose level is "less privilege
  (numerically greater) than that indicated by the RAL field of a long
  descriptor in the table search path for a read, or less privilege than the RAL
  or WAL fields for a write" makes a `B`-bit entry.
- **§7.2.3.1, write protection**: a write needs a level "less than (more
  privileged than) or equal to the lowest value (most privileged) of **all WAL
  or RAL fields** in the branch" — and, because denying read implies denying
  write, "the MC68851 **prohibits write accesses to all areas to which a task
  does not have read access**... regardless of the write access level".
- **§5.1.3.1** names all of `WP`, `S`, `RAL`, `WAL` and `G` as the protection
  information carried in the tables.

`ap_m68851_atc.h` already describes the *mechanism* correctly — protection is
"evaluated when the ATC entry is made" and a denial is cached with the `B` bit,
rather than storing `RAL` and `S` and re-checking on every hit — so the design
anticipated this. What is missing is the evaluation itself.

**Scope, stated so the gap is not overstated.** `PVALID`'s access-level
comparison against `CAL`/`VAL` *is* implemented, in `ap_m68851_pvalid`; this is
about the table search, not the instruction. And the DN3500's MMU is the
68030's, which has **no access levels at all** (`[030]` §9.6 lists them among
the six features it lacks) and whose supervisor protection *is* enforced —
`ap_m68030_search_permits_access` takes the supervisor flag. So no in-scope
machine is affected: this is the `m68851` reference module being incomplete
against its own manual.

*What would close it*: accumulate `S`, `RAL` and `WAL` across the search the way
`write_protect` already is, take the most privileged of all `RAL` and `WAL` seen
for the write test, and return a denial the ATC fill can cache as `B`. The
suites to extend are `m68851_search_suite` and `m68851_atc_suite`.

## §8 — walked 6/6, and its two figure captions are transposed

**Figures 8-3 and 8-4 have their captions swapped.**

| Figure | Caption | Contents |
| --- | --- | --- |
| 8-3 | "Breakpoint Acknowledge **Data** Register Format" | `BACx` — `BPE` at bit 15, `BREAKPOINT SKIP COUNT` at 7-0 |
| 8-4 | "Breakpoint Acknowledge **Control** Register Format" | `BADx` — `REPLACEMENT OPCODE`, all sixteen bits |

The register labels *inside* the figures are right; only the captions are
exchanged. The surrounding prose settles it twice over: §8.1.1 says the data
registers `BAD0`-`BAD7` "can be loaded with an opcode to be transferred to the
MC68020 during the breakpoint acknowledge cycle", and the sentence immediately
after Figure 8-4 says "Bit [15] of the **BACx** register is the breakpoint
enable control" — which is the field Figure 8-3 draws.

**This core has it right**, and `ap_m68851.h` states it in the same words the
figure contents do: "`BADx` is sixteen bits of replacement opcode with no other
fields; `BACx` is an enable at bit 15 and a skip count at bits 7-0". So it was
derived from the register labels and the prose rather than from the captions —
which is the reading that survives.

Also captured: the eight breakpoint opcodes `$4848`-`$484F` and their
register-pair correspondence; the breakpoint acknowledge cycle's CPU-space
address encoding (Figure 8-1, `FC = $7`, breakpoint number at bits 4-2); the two
terminations, bus error giving illegal-instruction vector 4 and a supplied
opcode replacing it in the pipe; and that "during the breakpoint cycle, the skip
count is decremented by one", which `ap_m68851_breakpoint_acknowledge` is
mutating for.
