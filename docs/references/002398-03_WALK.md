February 1985, the middle of three. **Eleven chapters, three appendices and an
index**, against Rev 1's eight chapters and two appendices and Rev 4's own
arrangement — so the handbook grew in both directions and no one revision
contains the others.

Opened for the same reason as Rev 1: it is a *hardware* document, and
`SOFTWARE_SHELF_WALK.md` records why both were sitting unlisted.

## What it adds over Rev 1

- **The active segment table grew.** Rev 1: `AST: ARRAY [1..64] OF ASTE_T`.
  Rev 3: `ARRAY [1..N] OF ASTE_T`, `N = 448 or 1984 (DNx60)`. The ASTE gained a
  pointer to the file map, a system type and flag byte at +14, a current length
  and flags at +18, `.dtm` at +1C, `.extdm`/`.event` at +20, `.type_uid`,
  `.acl_uid`, a file lock key at +34 — and on a DNx60 two more fields, an
  **ASTE-to-MSTE back thread chain** at +38 and the **physical address of the
  page map** at +3C, which is the BST chain `[AEGIS]` §11.2.3 describes for
  forward-mapped systems.
- **A disk volume table entry** (`dvte_t` in `disk.prv.pas`): `.state`
  (0 free, 1 being mounted, 2 assigned, 3 mounted), `.dcte` pointer, `.unit`,
  **`.dtype`**, `.blocks_per_vol`, `.blocks_per_track`, `.tracks_per_cylinder`,
  `.current_cyl`, `.owner_proc`, `.lv_base`, the volume's UID, and flags
  `U use_caller_blkhdr`, `N no_crc_retry`, `W write_protect`.
- **A whole peripheral I/O chapter** Rev 1 does not have: device addresses,
  disk parameters, the I/O map and its allocation, both keyboards (880 and
  Low-Profile) with physical *and* translated charts, the magtape controller,
  and a **system configuration pointer at `xxxFF6`** with its configuration
  block, channel control block and parameter block.
- **Per-model chapters** for DN400/420/600 and DN460/660/DSP160 carrying fault
  frames, fault types, fault vectors, floating-point formats, BLT registers,
  display control and status registers, MCSR halves, the cache, CPU control
  registers, the **control panel (CPIO) registers** and an **LED register**.
- Chapter 2's file-system structures are more numerous than Rev 1's: **VTOC
  block, VTOC entry, VTOC header, VTOC map entry and VTOC index**, where Rev 1
  has the entry alone.

## Chapter 2's VTOC structures, which Rev 4 names and does not decode

`ap_volume.h` carries the logical volume label from `002398-04` p. 2-18 offset
for offset, and that page names `+4C` "**VTOC header**" as a single block.
**Rev 3 p. 2-24 prints its seven fields**, with its own note that they are
label-relative:

| Offset | Field |
| --- | --- |
| `+4C` | version, and the number of blocks for the hash — `.version`, `.vtoc_size` |
| `+50` | number of VTOC blocks used |
| `+54` | VTOCX of the network root |
| `+58` | VTOCX of this volume's root directory |
| `+5C` | **VTOCX of the paging file for AEGIS** |
| `+60` | **VTOCX of the boot file** |
| `+64` | the VTOC map, 8 entries |
| `+B0` | end |

A **VTOC map entry** is six bytes — a count of consecutive blocks and the disk
address of the extent's first block — and "VTOC extents are **preallocated by
INVOL** to be near the middle of the logical volume and to avoid badspots",
which is what the INVOL sessions in `tools/dn5500/` are doing.

A **VTOCX** is a tagged 32-bit value with three forms: a local object's `DADDR`
plus an index (0-4 within the VTOC block, or 0-7 as a file map index); a
**remote** object's node ID; and a local object whose `DADDR` is unknown,
carrying a logical volume number.

**Recorded in `ap_volume.h` and not read**, on the same terms as
`.sys_shut_state`: nothing needs them yet, but `.os_x` and `.boot_x` are exactly
what a check that a volume is bootable would read, and this project builds
volumes with `/sau14/invol` and then asks SYSBOOT to find both.

## What it does not add, checked rather than assumed

**Its disk parameter table is superseded.** Chapter 6 tabulates every approved
drive by Dtype class — 000/001/006/007 PRIAM on the 14" ring/disk interface,
100/103/104/105 on 8" ANSI, 200/201/202 NEC and Micropolis on 8" SMD, 300-306
Micropolis/Fujitsu/Maxtor/Vertex on 5¼" ST412, plus floppy `CTYPE=1` and the
Intel and Xylogics SMD controllers at `CTYPE=4` — with cylinders, heads,
sectors, total blocks, and then **track/average/maximum seek, rpm, latency,
transfer rate and average read**, where "average read = Avg. Seek + Avg. latency
+ Sector Time".

**Every drive in it predates the two this core models.** `ap_omti.h` already
derives its timings from `008778-03` Table 6-5 (the **Maxtor EXT-4380**, 348
Mbyte) and Table 6-4 (the **Micropolis 1355**, 155 Mbyte), and already records
that `002398-04` p. 6-3 — Rev 4's version of this same table — gives
`604 Max 380: T-to-T 4, AVG 27, MAX 52, RPM 3600, AVG LATENCY 8.33, TRANSFER
RATE 1.25, AVG READ 35.3`, agreeing with Table 6-5 except on the average seek,
where the two Apollo documents are 10% apart and the code says so. **Rev 3's
table stops at the 190 Mbyte Maxtor and has no row for either drive.** So it
confirms the table's *shape* across three revisions and supplies no figure this
core can use. Recorded as a negative result, which is what most of a third
revision should be.

## Chapter 6 read: what it holds, and why almost none of it applies here

**Device addresses** (§"DEVICE REGISTERS (PIO)") defers to each model chapter.
**Disk parameters** are the superseded table above. The rest:

- **The I/O map and its allocation** — a 16-bit address from the controller
  with "0-2 bits *strapped*", then a page table of I/O pages, colour D/A and
  the rest.
- **Four keyboard charts**: the **880** and the **Low-Profile**, each given
  *physical* and *translated (user mode)*, as 16 × 16 grids indexed by high and
  low nibble.
- **The magtape controller**: control page at `FE8000`, "Interrupt vector
  number: **B3** (`$2CC` in page 0)", "MULTIBUS interrupt level: **3**", its
  I/O map entries, the acknowledge sequence (`$09FF` to `GATE`, `$20` to the
  command byte) and command bits including "**Bus width** (0 => 8 bits, 1 =>
  16)", "Grab bus before tape movement" and "Operate in **streaming mode**".
- **The DMA controller**, `9000`/`0FFA000`: "**The DMA controller is a Motorola
  M68450**", with `9000`-`903F` the ring receive header, and its **Channel Error
  Register**.
- The floppy/disk ANSI command set, the display control and status register, the
  destination count registers, and a **register set** diagram.

**The keyboard charts are the only part that touches modelled hardware, and they
are not needed.** `device/ap_kbd.h` derives its translation from **the boot
PROM's own table** — `CB DB -> 0D`, read out of the ROM image and checked against
`008778-03` Table 12-1, with the raw-mode bit measured at `21` during a boot.
**A ROM read beats a handbook chart**, and Rev 3's grids are the most
OCR-damaged pages in the document. They are a cross-check available at 600 dpi
if the translation is ever disputed, and nothing more.

**The M68450 is the generational marker.** This core models an **8237** for the
AT-bus machines (`device/ap_i8237.c`, `INTEL_WALK.md`); the DN3xx/DN5xx carry a
Motorola M68450. Same function, different part, different manual — and one more
reason chapters 8 and 9's per-model registers are not owed to this core.

## One question raised, and answered before it was asked

Rev 1's physical volume label matches `media/dn5500-invol-done.awd` byte for
byte at +00 (version `0001`), +02/+04 (`"APOLLO"`) and +08 (the 32-byte name,
`DN5500`) — see `002398-01_WALK.md`. **The later fields do not.** The image
reads `00000504` where Rev 1 puts `.dtype` at +30, `00013F4C` (81,740) where it
puts `.blocks_per_pvol` at +34, and `0012 000F` (18, 15) at +38 for blocks per
track and tracks per cylinder — but the volume INVOL built is 326,956 kB, which
is not 81,740 blocks of any size this project uses.

**It resolves by arithmetic, and it confirms the page-size finding rather than
troubling it.** INVOL built a logical volume of **326,956 kB** and the label
says **81,740** blocks: `326956 / 81740 = 4.0`. **A block here is 4 Kbytes** —
one DS5500 page, four 1,056-byte sectors — which is the same unit change
`AEGIS_INTERNALS_WALK.md` settled from the other end, now visible in a field of
the label itself. 18 blocks per track and 15 tracks per cylinder give 270 pages
a cylinder and about 303 cylinders.

*And the question should never have been written down, because the answer was in
this repository.* `002398-04` is walked whole; its record's row 43 has "block 00
of the physical volume is the physical volume label (1 block)", row 50 settles
the canned UIDs including `pv_label_$uid 00000200,0`, and row 52 is marked
"CONFIRMS `ap_volume.h` OFFSET FOR OFFSET". `src/core/image/ap_volume.h` carries
the whole layout with `.dtype` at `+30` and `.blocks_per_pvol` at `+34`, the
six-character `APOLLO` signature as its own constant, and the mount history at a
base of `0x440` "found by differencing rather than read off the diagram" because
"the diagram is a scan whose hex OCRs badly". Every part of my question was
already answered, more carefully than I asked it. **`reference-search-is-not-a-
code-check`: grep `src/` before writing "open".**

## The 600-dpi figure read, 2026-09-12 — the caveat below is lifted

Every page in chapters 1 and 2 carrying three or more `+NN` offset rows was
rendered at **600 dpi and read as an image** — 28 pages. At that resolution the
figures are clean, and the transcriptions this record made from the damaged text
layer are **confirmed offset for offset**. What follows is what the images add
over them.

**The active segment table entry** (p. 1-2, `aste_t` in `vm.ins.pas`) is exactly
as recorded, and its **bit legends are now legible**, which the text layer had
lost entirely: `CC` concurrency control from the VTOC entry (`.con_ctrl`), `P`
permanent, `I` immutable, `F` file trouble, `T` in transition, `H..H` ASTE hold
count (`.ehcnt`), a second `F` file-map modified (`.fm_mod`), `D..D` blocks
added to the segment since it went active (`.blocks_delta`), `G` global
transparent mode — no `dtm` (`.gtms`), `V..V` index in the DVT (`.volx`), `D`
DTM needs updating (`.dtm_fl`), `R` grace flag (`.gracef`), `N..N` number of
pages resident (`.npr`). The DNx60 pair at `+38`/`+3C` is `.mst_thread` and
`.pmap_phadd` as recorded.

**The BAT header** (p. 2-3, `bat_hdr_t`) was recorded here only as "lives in the
logical volume label". Its six fields are now in `image/ap_volume.h`, which had
`+2C` as one opaque block: `.n_blk`, `.n_free`, `.daddr`, `.base_add`,
`.vol_trouble` and `.bat_step`, ending at `+4C`. **`.vol_trouble`'s `V` bit is
the salvage flag** — "set by OS if volume needs salvaging, cleared by SALVOL" —
which is the same subject as `[RN104]` §5.5's warning about salvoling a volume
between SR10.3 and SR10.4.

**The VTOC header** (p. 2-24) is confirmed, and gains one row the text layer had
dropped: `.pad` at `+94`, so the eight six-byte map entries fill `+64`-`+93`
exactly and the header ends at `+B0`.

**The VTOC entry** (p. 2-23, `vtoce_hdr_t` + `vtoce`) is **0xCC bytes**: version
/ sys_type / flags at `+00`, `.uid` `+04`, `.type_uid` `+0C`, `.acl_uid` `+14`,
`.cur_len` `+1C`, `.blocks_used` `+20`, `.dtu` `+24`, `.dtm` `+28`, `.dir_uid`
`+2C` — "UID of directory where object is catalogued" — `.pad2` `+34`, end of
header at `+40`, then `.fm[0..31]` `+40`-`+BF` and `.fm2[1..3]` `+C0`-`+CB`.
Flags: `U` VTOC entry in use, `CC` concurrency control (00 none, 01 shared, 10
exclusive), `P` permanent, `I` immutable, `F` file needs salvaging.

**The VTOC block** (p. 2-22, `vtoc_blk_t`) is 1024 bytes and has two shapes:
`.next_add` at `+00` — "next block in hash bucket" — then five VTOC entries at
`+04`, `+D0`, `+19C`, `+268`, `+334`, ending at `+400`, which is 4 + 5 × 0xCC
exactly; **or** a file map of `.fm[0..255]`, four bytes each, filling the block,
pointed to by `vtoce.fm2[1-3]`. *The figure's second shape is drawn as eight
rows at `+80` intervals labelled `fm[0]`…`fm[6]`, `fm[255]`, which does not
reconcile with 256 four-byte entries — read it as the array the type names, not
as the rows the schematic draws.*

**The directory** (pp. 2-4 to 2-6). `dir_t` is five regions: header, **linear
list** ("sequentially used directory entries"), info block ("ACL manager's
initial ACL description block"), hash threads, entry blocks. The header is
`.version` (1), `.hash_value`, `.list_size` (**18**), `.pool_size` (**429**),
entries per block (**3**), high block number, free block thread, four unused
words, entry count and maximum count (**1300**). `infoblk_hdr_t` is version,
info block length, header length (8), MBZ, a default ACL UID for directories at
`+08` and one for files at `+0C`, 24 unused bytes, end `+30`. `dir_entry_t` is
**48 bytes**: a 32-byte name, three reserved words, `+26` name length and entry
type (0 not in use, 1 name/UID pair, 3 name/link-data pair), and four words of
entry data — the UID for type 1, or for type 3 a link-text length and two block
numbers holding characters 1-144 and 145-256. `entry_block_t` is **150 bytes**:
next and previous block numbers, use count and block type (0 not in use, −1 a
hash block with three directory entries, −3 a link-text holding block), then
three entries or 144 characters of link text.

**The file map** (p. 2-11) is the structure that makes an offline file reader
possible, and it matches the VTOC entry exactly: `+00`-`+7C` are **32 direct
pointers** to data blocks 1-32, `+80` points at a level-1 block of 256 pointers
(blocks 33-288), `+84` at a level-2 block of 256 pointers to level-1 blocks and
`+88` at a level-3 block. "Maximum file size = (32 + 256 + 256² + 256³) × 1024
bytes = 17,247,300,000." "File map resides in VTOCE and AST entries" — so the
VTOC entry's `.fm[0..31]` at `+40` are the direct pointers and `.fm2[1..3]` at
`+C0` are the three indirect levels.

**The disk block header** (p. 2-8, `blk_hdr_t`) is the same figure `002398-04`
p. 2-8 gives and `image/ap_awd.h` already transcribes: `.uid` `+00`, `.page`
`+08`, `.dtm` `+0C`, `.blk_type`/`.sys_type` `+10`, `.chksum` `+18`, `.daddr`
`+1C`, end `+20`; `BLKTYP` 0 data and 1/2/3 the file map's index levels,
`SYSTYP` 0 file, 1 directory, 2 system directory. Confirmed, nothing changed.

**`DISK_$ERROR_INFO`** (p. 2-9) is how a header mismatch is diagnosed: time,
daddr, blocks-per-track and tracks-per-cylinder, then a **requested header** and
a **read header** side by side at `+0C` and `+2C` — each a whole 32-byte block
header, UID, page and daddr — then `VOLX | PPN` and a status word.

**The stream file header** (p. 2-15, `stream_$hdr_rec_t`) is the first 32 bytes
of any file reached through the stream interface: header length and version,
a CRC that is "-(integer sum of (1 + 3 through n longwords))", record length,
file length including the header, then record type (variable with counts, fixed,
or no record structure), ASCII-or-binary, sparse, carriage-control, and a
concurrency field. Worth having if a reader ever extracts a text file.

**The registry** (p. 2-12, `ppo_$header_t` and `ppo_$record_t`) and the ACL
entry (p. 2-2) are AEGIS's own and bear on nothing here.

### Chapter 1's tables, and the two that connect to work in this core

`aste_t` and its bit legends are above. Also read: `dcte_t` (p. 1-6), the disk
controller table — controller type and number, status, lock, block-header
pointer and page, **the I/O register page pointer `.csrs_ptr`**, an eventcount,
a **page-zero interrupt vector** and an actual interrupt entry, a
device-dependent interrupt routine, `dinit`/`format`/`read_write` entry points,
and flags `N` no headers on device, `C` do checksumming, `D` driver supports
multi-read, `L` liberty (SMD) winchester. `dvte_t` (p. 1-7) is as this record
had it, with `eventcount_t` beside it — `.value`, `.nnext`, `.nprev`, which is
what `[GPIO]`'s `pbu_$get_ec` hands back a pointer to.

**`fault_$diag_t`** (p. 1-8) is the `DFDF`-patterned record `[EH1]`,
`002398-04` and `[AEGIS]` §18.2.4.1 all describe. Rev 3's is *shorter* than Rev
4's — `.bus_info` at `+26` and flags at `+2E`, against Rev 4's register file
running to `+46` — so the record grew between revisions and a reader should take
the revision that matches the release. The `DFDF` magic and the `R`/`N`/`FFF`
bus-info decode are identical.

**`mste_t`** (p. 1-9) is the per-ASID mapped segment table, `ARRAY[0..26,
0..319]` for 16 Mb of virtual address on a non-DNx60 and `[0..26, 0..7680]` for
256 Mb on a DNx60 — which is the *segment* `[RN104]` §5.5 calls "the Domain/OS
unit of mapping and protection ... (32K, 128K, 512K), and not the page". Its
access field enumerates nil / read / read-execute / write-read /
write-read-execute and the four supervisor counterparts.

**`pmape_t`** (p. 1-4) is worth one line for the MMU work: on a DNx60 "these are
the **page tables used by the address translation hardware**", and their `U`
"page has been used, **set by hardware**" and `M` "page has been modified, **set
by hardware**" are the same used/modified bits a 68030 or 68040 descriptor
carries. Not this core's machine — DNx60 is the DN460/DN660 — but it is Apollo's
own statement that the OS expects the hardware to write those bits back, which
is what the 68040 ATC `M` fix of 2026-09-11 restored.

### And a second measurement, which is an open question rather than a mismatch

`tools/awd_read.py` implements the chain above and runs it on the DS5500 volume
this project builds. The labels read cleanly — name `DN5500`, both UIDs, the
mount and dismount times, shut state 0 (dismounted), the BAT's 74,036 free of
81,728 — and the **VTOC header is internally consistent**: `.vtoc_blocks` reads
226 and `.map[0]` reads "226 blocks at DADDR 40901", the same number arrived at
from two different fields six bytes apart.

**But `.root_x` does not land.** It reads `0009B324`, which p. 2-25's split
makes DADDR **39730** index 4 — *below* the VTOC extent that begins at 40901 —
and that block is zeros. `.net_x`, `.os_x` and `.boot_x` all name the same
DADDR with indices 5, 7 and 0, and index 5 and 7 are outside the 0-4 an entry
index may take (p. 2-25 allows 0-7 only for the *file map* use).

*Two further numbers do not cohere either*: `.blocks_per_pvol` reads 81,740 on
an image of 345,553 blocks, and 18 blocks/track × 15 tracks/cylinder does not
divide 81,740.

### And the reason the DADDR does not land: a DS5500 block is four sectors

Measured 2026-09-12, after `tools/kernel_symbols.py` refused the volume with
"its blocks' DADDRs do not match their positions" — a check that tool has always
made and that a DS5500 volume has always failed.

    index 165750  uid a4615f80.40012345  page 0  daddr 41131
    index 165751  uid a4615f80.40012345  page 0  daddr 41131
    index 165752  uid a4615f80.40012345  page 0  daddr 41131
    index 165753  uid a4615f80.40012345  page 0  daddr 41131
    index 165754  uid a4615f80.50012345  page 0  daddr 41132   (a different object)

**Four consecutive 1056-byte sectors carry one logical block**, all four with
the same header — UID, page and DADDR. On `media/dn3500-sr10.4-installed.awd`
every one of 4,096 sampled blocks has `daddr == index`; on the DS5500 volume
**one** does.

That is the **4 KB block** `[RN104]` names twice for SAU 11, 12 and 14 — §4.10.3
"nodes with 4-KB disk block size" and §5.5 "4K-page machines" — seen from the
image. So `.blocks_per_pvol` 81,740 is in 4-KB blocks (× 4 = 326,960 sectors
against the image's 345,553, the difference being the badspot and diagnostic
cylinders), and a DADDR indexes 4-KB blocks rather than sectors. `awd_read.py`'s
`vtoc_entry` read zeros because it took a DADDR for a sector index.

**And the mapping is per cylinder, which the label's own geometry supplies.**
It is not affine — `index - 4·daddr` is 0 near the start and 1226 at index
165750 — because the step is a *cylinder*. The physical label gives 18 blocks
per track and 15 tracks per cylinder, so a cylinder is **270 sectors**; 270 does
not divide by 4, so a cylinder holds **67 blocks and two sectors go spare**:

    sector = (daddr // 67) * 270 + (daddr % 67) * 4

Verified three ways: 541 sampled blocks of the restored volume all agree; the
VTOC's first extent, `daddr 40901`, lands on sector 164824 **whose own header
reads `daddr 40901`**; and the root directory's page 0, `daddr 41131`, lands on
sector 165750, which is where a search for its UID had already found it. A
DN3500 volume derives `sectors_per_block` 1 by the same route and the formula
becomes the identity. `tools/awd_read.py` does this and
`tools/test_awd_read.py` 10 → 15 holds it.

*Why it hid*: the formula agrees with a naive `4 · daddr` for the whole **first
cylinder**, 67 blocks, and only diverges after it.

### One thing the mapping proves rather than explains

> **CORRECTED 2026-09-12, later the same day. Everything from here to the end of
> the next section was resolved, and the original text is kept beneath each
> correction because it is what explains why the reader looked the way it did.**
>
> **`.root_x` is not stale and the block is not missing.** A `vtocx`'s upper
> field is a **VTOC page**, not a DADDR, and the VTOC is laid out so that page P
> is at **DADDR P+1**; `.root_x` `0009B324` is page 39730, index 4, and the
> block at DADDR 39731 is `vtoc_$uid` page 39730 and carries the root
> directory's entry at index 4. The same is true of the DN3500 volume, where the
> two readings happen to differ by one block and the wrong one still landed on a
> VTOC block — which is exactly why that volume "resolved as documented" and
> this one did not.
>
> **The rule is general**: every block address stored in a VTOC entry's file
> map, in a `vtocx`, or in the VTOC header's extent map is **one less** than the
> `daddr` the target block's own header carries. 76,576 file-map pointers across
> both volumes were checked against the object UID *and* the page number in the
> target header; 76,576 resolve at `stored + 1` and **none** at `stored`.
> `.lv_list` is the control: it stores a plain DADDR.
>
> **The SR10 VTOC entry and directory entry are now measured in full** — sizes,
> offsets, and what proves each — in `docs/PROJECT_STATUS.md`,
> *`tools/awd_read.py`: a volume read end to end*. The entry is 0x150 bytes at
> a 1 KB block and 0x1D0 at 4 KB, starting at +008, and the block ends with
> `FEDCA984` and its own page. The earlier reading below — "image block 160572,
> slot 3", a UID tail where `.version` should be — was a **misaligned slot**:
> p. 2-23's 204-byte stride is SR9's, and the UID it found at a p. 2-23 offset
> belonged to a different field of a differently-sized entry.
>
> **Two canned UIDs were missing from this record**: `00000203,0` and
> `00000204,0`. The second is the VTOC's index, and it is what `.map[0]` has
> always been describing — 907 blocks on the DN3500 volume and 226 on the
> DS5500, matching `.vtoc_blocks` in each case.
>
> What stands unchanged below: the VTOC *header* did not change between Apr 1983
> and a 1992 volume, and chapter 2's *directory* figures describe a format an
> SR10.4 volume does not use.


`.root_x` on the restored volume is `0009B324`, which p. 2-25 splits as DADDR
**39730**, entry index 4 — and **no block anywhere in the image carries daddr
39730**. Not a mapping failure: a scan of all 345,553 sectors finds 40901 and
41131 exactly where the formula predicts and 39730 nowhere at all. The VTOC's
written blocks (those with `vtoc_$uid` `00000202`) are 50 scattered daddrs
between 34773 and 44232, and 39730 falls in that range but was never written.

*The DN3500 volume does not behave this way*: its `.root_x` is `002716E1` →
daddr 160110, and sector 160110's header is `vtoc_$uid`, page `0002716D`, daddr
`0002716E`. The field resolves there exactly as documented.

So on an SR10.4 DS5500 volume `.root_x` names a VTOC block that does not exist,
while the volume **boots Domain/OS perfectly well** — so the operating system is
not finding its root directory the way p. 2-24 describes. Whether SR10 redefined
the field or the RBAK restore leaves it stale is not established, and the tool
reports the decode and the empty result.

**It is not the VTOC header that changed.** `[EH1]` p. 5-22 was read at 600 dpi

## Chapter 1, *AEGIS*, pp. 1-1 to 1-22 (PDF 13-34) — read whole 2026-09-13

**The clock page derives a constant this project measured.** p. 1-5: "the
hardware clock is only 16 bits. The upper 32 bits are maintained by the clock
interrupt routine", the `clock_t` low-order bit "represents four microseconds",
and there are **three hardware clocks** — **clock 1 at 4 µs (real-time clock),
clock 2 at 8 µs (process timer), clock 3 at 128 µs (real-time intervals)** —
not counting the calendar. A 16-bit counter ticking at 4 µs overflows every
**2^16 × 4 µs = 262,144 µs**, which is exactly the tick
[[volume-label-mount-history]] measured off a volume label and recorded without
an explanation. The explanation is that the label's time advances once per
overflow of the hardware clock.

**The ring packet is specified here, and `RING.md` did not have it.** pp. 1-15
to 1-18:

- **Message header**: `+00` TO ADDRESS (4 bytes), `+04` TYPE FIELD, `+06` zeros
  and the **EARLYACK** byte, `+08` FROM ADDRESS, `+0C` header data, ending
  `+40C` — so the data field is **0 to 1024 bytes** and "must always be an even
  number of bytes (on the APOLLO I the controller always uses word DMA)".
- **Type field**: **bit 15 is BST (broadcast)**, "if it is set, the To Address
  field is ignored"; bits 14-0 are the type, and "each 1 bit in the received
  Type field is compared to the corresponding bit in the controller Type
  register. If any bit selected in the Type register is a 1, the message is
  received." **The APOLLO I implements bits 14 through 8 only; bits 7 through 0
  never match.**
- **Early Acknowledge field**, bit by bit: `7`=0, `6`=X, `5`=X, `4`=0,
  **`3`=ICP (Intend to Copy)**, `2`=X, **`1`=PAR**, `0`=0. The zeros "prevent
  the remaining bits in the late-acknowledge byte from being modified by the
  bit-stuffing protocol"; ICP "is set by an addressed receiver if it was set up
  to copy a message and the type field matched. **A NAK condition is indicated
  when no receiver sets this bit**"; PAR makes the byte's bit count **odd**.
  And the rule that makes it work: **"For the purposes of the CRC calculation,
  the EARLY ACK field is treated like a byte of zeros. This allows receivers to
  modify the ACK field without having to recompute the CRC checksum."**

**The boot chain, agent by agent** (p. 1-20). PROM reads **`/SYSBOOT`, records
2-B on track 0** — the same blocks `[AEGIS]` §27.1 gives, which this project
resolved to sectors 8-47. SYSBOOT reads `/SAUn/AEGIS` and `/SAUn/SALVOL` (only
if salvage is required). AEGIS reads the uncatalogued paging file, `//`, `/`,
`/COM`, `/SYS/NODE_DATA` and `` `NODE_DATA/SHELL``. SHELL reads
`/SYS/APOLLO_LOGO`, `` `NODE_DATA/STARTUP_SHELL`` and **`/SYS/ENV`**, and ENV
chooses one of three: **`/SYS/DM/DM`** on "GO" or a normal boot, **`/SYS/BOOT`**
on "SH" or a boot from an SIO line, or **`/SYS/SPM/SPM`** on "SPM" or a normal
boot on a **server node**. That is why this project's DS5500 ends at
`SPM system init complete` — no display fitted makes it the server-node branch.
Two notes matter: **"if booted from cartridge tape, the tape is first searched
for `BSCOM/RBAK_SHELL`"**, and "if no registries are available, you can login
only as `USER.NONE.NONE`".

**And the rest of the chapter**: the AST/ASTE and its page maps in both
families; the AST header with its hash table, free list and LRU pointers; the
disk controller table entry (`dcte_t`) with its four disk entry points and the
`N/C/D/L` flags — **`L` is "liberty (smd) type winchester"**; the disk volume
table entry; the MMAP and MMAPE in both families; the MST/MSTE with its
**nine-value access encoding** (`00000` nil through `10111` supervisor
write-read-execute) and the guard bit; the **process control block** and the
**PID/ASID table** — PID 1 the initial user process and DM, 2 null, 3 clock,
4 page purifier, **5 network-receive, 6 network-paging, 7 network-general
server**, 8 terminal helper, 9 the first user process, 25 the last; the
**resource lock list**, 26 named locks with `ring_$xmit_lock` at 22 and the
clock's two highest; the **stack frame** (`SB+00` caller's SB, `+04` ECB,
`+08` unit list, `+0C` caller's DB, `+10` return PC, `+14` ARG1...); the
**status word** `F|SSSSSSS|A|MMMMMMM|CCCCCCCCCCCCCCCC`; the **system
directories**, which name `/sau1` to `/sau5` for the 1985 machines and
`/sys/net` as "Netman (diskless node support)"; and the **trap codes** — `0`-`6`
SVC by argument count, `6` from GPIO interrupt routines, `7`-`D` undefined and
reflected to user space, `E` the software-generated fault, **`F` undefined and
traps to the PROM debugger**.

**The fault diagnostic record** (p. 1-8) opens with `.pattern` = **`#DFDF`**,
then a status word, the registers, and `.bus_info` carrying `R` read/write,
`N` not-an-instruction-reference and a three-bit **function code** — `001` user
data, `010` user program, `101` supervisor data, `110` supervisor program,
`111` interrupt acknowledge.


## Chapter 2, *File System*, pp. 2-1 to 2-25 (PDF 35-59) — read whole 2026-09-13

**p. 2-10 explains a rule this project measured and could not explain.**
DISK/VOLUME FORMAT draws the whole layout — physical volume label at block 00 of
the *physical* volume, logical volume label at block 00 of the *logical* one,
the **boot file at LV block 01 for 10 blocks** (so 01-0A), free blocks from 0B,
then the VTOC, then the BAT, then free blocks, and **a second copy of the
logical volume label in the last block of the logical volume**, with the next
logical volume after it. Then the sentence:

> "**NOTE: all disk addresses (DADDRs) in a logical volume are relative to the
> start of a logical volume.**"

That is the `stored + 1` this project measured over **76,576** file-map pointers
and recorded as an unexplained offset. It is not one: it is **`lv_base`**, the
logical volume's own first physical block — `.lv_list[0]`, which is 1 on both
volumes held here because the logical volume starts immediately after the
physical label. `tools/awd_read.py` now reads it off the label
(`Volume.daddr_of`), so the rule is what is implemented rather than the
coincidence. The same page warns the coincidence need not hold: "there may be
dead space between logical volumes", and "badspots may cause the VTOC to be
non-contiguous and not adjacent to BAT".

**p. 2-8 is the block header this project has been parsing**, field for field:
`+00 .uid`, `+08 .page` "page number in file", `+0C .dtm` "**time written
(clock.high32)**", `+10 .blk_type|.sys_type`, `+14` unused, `+18 .chksum`,
`+1C .daddr`, ending `+20`. **BLKTYP** 0 data, 1/2/3 the level-1/2/3 index
blocks of a file map; **SYSTYP 0 File, 1 Directory, 2 System directory** — which
names the field `awd_read.py` had measured and called "root directory".

**And `.dtm` being `clock.high32` closes the 262,144 µs question** that
Chapter 1's clock page opened: the block header's time is the clock's upper
half, and a low-order bit of 4 µs sixteen places down makes that half tick every
2^16 × 4 µs = **262,144 µs**, which is the interval
[[volume-label-mount-history]] measured. *Not reconciled*: p. 1-5 also says
`clock.high`'s low-order bit "represents approx. four milliseconds", which is
neither 4 µs nor 262 ms; recorded as printed rather than explained away.

**The file map** (p. 2-11): 32 direct pointers at `+00`-`+7C`, then level-1 at
`+80`, level-2 at `+84` and level-3 at `+88`, each indirect block holding **256
pointers**. "Maximum file size = (32+256+256**2+256**3)*1024 bytes =
17,247,300,000 bytes" — the printed total this project's test already asserts is
rounded, the expression giving 17,247,272,960. "File map resides in VTOCE and
AST entries."

**The SR9 directory, which an SR10 volume does not use but whose architecture it
keeps.** A directory is HEADER + LINEAR LIST + INFO BLOCK + HASH THREADS +
ENTRY BLOCKS. The header gives the hash modulus, a **linear list of 18 entries**,
a **pool of 429 entry blocks**, **3 entries per block**, the free-block thread,
the entry count and a **maximum of 1300**. An entry is a **32-byte name**, three
unused words, a name length and an **entry type — 0 not in use, 1 name/UID pair,
3 name/link-data pair** — then four words of entry data. An entry block is 150
bytes: next and previous block numbers, a use count and a **block type — 0 not
in use, -1 a hash block with 3 directory entries, -3 a link-text holding block**.
The hash is `sum := ord(name[i]) + 2*sum` then `mod HASH_VALUE`, and a search
looks in the linear list first, then follows the hash thread.

**What survives into SR10**, against what this project measured off a 1992
volume: the header-then-list-then-entries architecture, and the distinction
between a **name/UID entry** and a **name/link-text entry** — SR9's types 1 and
3 against SR10's flag bytes `02` and `04`. What changed is the entry itself,
from a fixed 32-byte name to a variable-length one. Recorded as a correspondence,
not as a decode: nothing here licenses reading an SR10 entry with these offsets.

Also on these pages: the **ACL entry** (person, project, organization and
subsystem UIDs, node ID, expiry date, rights); the **BAT** as `array[0..255] of
bat_lword_t` with "**BAT bit = 1 if block is available**" and bit 0 of word 0
being `bat_hdr.base_add`; the **BAT header** at label offsets `+2C` through
`+40`, which is exactly what `ap_volume.h` and `awd_read.py` parse, with
`V` volume-trouble "set by OS if volume needs salvaging, cleared by SALVOL",
`C` CHUVOLed and `B` being CHUVOLed; `disk_$error_info`; and the **registry
format**'s header and PPO record.

## Chapter 3, *Programming Information*, pp. 3-1 to 3-10 (PDF 60-69) — read whole 2026-09-13

**Four of its ten pages are reprinted from the MC68000 manual** and say so in a
footnote: the addressing-mode table (p. B-1), the condition-code table and the
conditional-test table (both p. A-4). This project has walked the Motorola
manuals, so those pages add nothing and the footnote is what establishes that
rather than a guess.

**What is Apollo's, and it bears on an open plan item: the Entry Control
Block.** p. 3-7, `db_$ecb_rec`:

    +00  JUMP TO PROCEDURE   .jmp, .cs    (six bytes -- a real JMP)
    +06  --> DATA AREA       .db
    +0A  - - - - B I A N D   .keys
    +0C  DEBUG INFO          .debug
    +10

with `B` stop looking back in the stack for inhibit routines, `I` inhibit async
faults, `A` Apollo software, `N` debug info present, **`D` DB register not
saved**. And p. 3-4's calling sequence uses it:

    MOVE.L  ECBADR,A0     GET ADDRESS OF ECB
    JSR     (A0)          JUMP AND PUSH PC
    ...
    MOVE.L  6(A0),DB      LOAD MY DATABASE FROM ECB

So `jsr (a0)` **jumps into the ECB itself**, whose first six bytes are a JMP to
the real entry point, and the callee then loads its data base from `+06`. That
is the structure behind the DS5500 item's `movea.l d(a5),a0; jsr (a0)` through a
transfer vector, and `[DP]`'s "an unresolved vector is supposed to point at a
dynamic link snapper" is a statement about what sits at `+00` of one of these.
Recorded for that item; nothing acted on here.

Also Apollo's: the **stack frame** (`SB+00` caller's SB, `+04` the ECB pointer,
`+08` a unit list, `+0C` the caller's DB — "optional; the *DB not saved* bit in
ECB signals that it is not present" — `+10` the return PC, `+14` the first
argument), and "**registers other than DB, SB, SP are not preserved**"; the
**status word** `F|SSSSSSS|A|MMMMMMM|CCCCCCCCCCCCCCCC`, repeated from chapter 1;
the **filename suffixes** (`.BS` a boot shell command, `.RFC` "run file
converter — RFC command (output), `/sysboot` (input)", which is how a `/sysboot`
is made); and the **pathname syntax** — `//` the network root, `/` the node
entry directory, `~` the naming directory, `\` the parent, and **`` `node_data``
for `/sys/node_data[.nn]``**, which is the backquote this project's console
scripts type. Names may hold `A-Z a-z 0-9 $ _ .` and **cannot start with `_`,
`.` or a digit**.

**Both address-space maps are the 1985 machines'**, non-DNx60 and DNx60, and
neither is a Series 3000 or 4000: physical space puts the trap page at 0, the
PROM at `400`, I/O objects, display bitmaps, an optional half-megabyte and a
PROM data area below main memory; virtual space puts global libraries at `8000`,
a **global A boundary** at `200000`/`800000`, per-process static data, **a guard
segment either side of the user stack**, per-process supervisor space, a
**global B boundary**, then AEGIS, the display bitmaps and the I/O control pages.
`[AEGIS]` §9 gives the same shape for SR9; the value here is that the guard
segments and the two global boundaries are drawn with their addresses.


## Chapter 4, *Error Codes and Messages*, pp. 4-1 to 4-17 (PDF 70-86) — read whole 2026-09-13

**This chapter names five things this project diagnosed by measurement.**

- **`00120020` is "supervisor fault while resource lock(s) set."** The
  `disk-needs-access-time` memory records `00120020` as the symptom of zero disk
  latency and never had the code's meaning. It has it now, and the meaning fits
  the diagnosis exactly: with no latency the disk's completion fired inside a
  region that held a lock.
- **`00280022` is "controller timeout"**, under OS / cartridge tape manager —
  which is what the tape item already says it is, now from the vendor.
- **`000E0007` is "name not found"**, under OS / naming server — the
  `e0007-name-not-found` memory's module-0E decode, confirmed.
- **`001B0001` is "no os paging file -- please run invol option 8."** And the
  document prints that *same code* three times with three different meanings
  ("node ID mismatch", "checksumming already enabled", and this), which is an
  erratum in the manual rather than in the reading.
- **`0012001C` "unimplemented SVC"**, `0012000A` "unimplemented instruction",
  `0012000C` "bus time-out", `00120011` "access violation" — the fault handler's
  whole vocabulary, which is what a crash record's status word carries.

this project has seen.** p. 4-17:

    boot error: unable to read pv_label
    boot error: volume "N" not found
    boot error: unable to read lv_label
    boot error: unable to read root_dir
    boot error: SAU not found in root_dir      <-- this one
    boot error: SAU uid not found
    boot error: unable to restore SAU_dir
    boot error: "FILENAME" not found / uid not found / unreadable / not a file
    boot error: missing file name

## Chapter 5, *System Debugging*, pp. 5-1 to 5-18 (PDF 87-104) — read whole 2026-09-13

**The whole chapter is instruments, and three of them answer questions this
project answered by hand.** Recorded in `docs/references/MD.md` rather than here,
because that is where a reader looking for MD will go: the full **Mnemonic
Debugger command set with meanings**, the **command grammar** (`:I/:B/:W/:L`,
`:O/:D/:H/:A`, `$num` and `<base>$num`, "all numeric input defaults to
hexadecimal"), the **boot shell's own command list**, the **crash analysis**
procedure and the **four-command system dump**.

The three that matter:

- **`LD` lists the SAU directory of the boot device.** The session spent on
  `boot error: SAU14 not found in root_dir` could have asked the machine.
- **`STCODE <status-code>` prints a status code's text**, from the boot shell.
  Every code this project has looked up against chapter 4 by hand is printable
  on the machine.
- **`EY <filename>` traps twice** — once before passing control, and for AEGIS
  again "**after establishing the OS mapping and before calling `OS_$INIT`**",
  with `AEGIS.MAP` in the SAU directory giving the virtual addresses. The DS5500
  volume carries `/sau14/domain_os.map` and `awd_read.py` can extract it.

**And `DI`'s full form is here** — `DI <W>|<F>|<N> [<nn>]|<S> <0-3> <1-10>`,
"Winchester, Floppy, node (nn), storage module unit 0-3, and logical volume
1-10. Defaults are: W, 0, 1" — which is the same command `008860-A03` chapter 2
uses as `DI N 0xxx` for a diskless boot. Two documents, one command, agreeing.

**`DB`, the machine-level debugger**, is documented here too and is a *Domain/OS*
program rather than a PROM one: `db` from a shell, `q` to leave. Its crash-analysis
half reads a dump — `aste`, `dcte`, `dvt`, `mst`, `mste`, `pf`, `pt`, `ve` (print
a VTOCE), `lvl`/`pvl` (print a volume label at an address), `ha` (hash a UID to
an AST), `uid`, `le` (list the system error log), `ts` (traceback a stack), `dr`
(registers at crash), `st` (status at crash) — and it is the tool the `awd_read.py`
work reimplements offline for a *volume* rather than a dump. Two commands are
worth naming for their own sake: **`a7 <value>` "set a7 in dump (dflt is from
`E003FC`)"**, which says where the crashed stack pointer is kept, and
**`da [<clockh>]` "display date (`build_$time`)"**, which converts a
`clock.high` to a date — the same field the block header's `.dtm` carries.

**DEBUG's unadvertised extensions** are listed because "the following commands
and other items are available in the standard DEBUG, but are not advertised to
the public": `FPREGS`, `REGS`, `DB`, and the `CDB` and `DDD` options. Of no use
to this core and recorded because a chapter read whole says what it contained.

**The Lights program** shows network status from within DB — `LI 0FF9C12` on a
DN400/420, `0FF9C02` on a DN300/320, `0FFF9C12` on a DN460 — and "**do not
execute the Lights program from a color node! It will crash the node!**" The
addresses are those machines' ring receive registers and none is this core's.


## Chapter 6, *Peripheral I/O*, pp. 6-1 to 6-17 (PDF 105-121) — read whole 2026-09-13

**The DTYPE field this project prints raw is a class and a drive.** The disk
parameter table groups drives by interface: **class 000** 14" ring/disk PRIAM,
**100** 8" ANSI, **200** 8" ring/disk SMD, **300** 5¼" ST412, then the floppy,
the Intel storage module controller (`CTYPE=4`) and the Xylogics file server
controller. So a `dtype` is *class × 100 + drive*, and the `0504` both of this
project's volumes carry is **class 500, drive 4** — a family later than any row
here, which for a DN3500 is ESDI, the interface `008778-03` gives the OMTI 8621.
The reading is structural rather than a lookup: 1985 has no 500 class.

**And the two DADDR fields in the physical volume label are named by use.** The
next table gives, per drive, the **bad-spot cylinder** and the **diagnostic
cylinder** as DADDR/cylinder pairs — the last usable cylinder and the one before
it — which is what `pv_label.phys_badspot_daddr` at `+98` and
`phys_diag_daddr` at `+9C` hold. `blocks used` then "reflects loss of badspot
and diagnostic cylinders", which is why a volume's usable count is short of
cylinders × heads × blocks/track.

**The I/O MAP here is the MULTIBUS ancestor of the Series 4000's translation
map**, not that map: 256 one-word entries at `FFF800`-`FFF9FE`, an 8-bit VPN
from an 18-bit virtual DMA address (16 from the controller, 0-2 strapped per
controller) giving a 12-bit PPN and a 22-bit physical address. `ap_atmap.h`
models the Series 4000's 64/128-entry version at `017000`; this is the same idea
two generations earlier and is **not** a source for it. Its allocation table is
worth having as a picture of what shared that map: floppy 2 pages, Winchester 2,
**ring transmit 4, ring receive 4, ring 2nd receive channel 4**, colour DMA 33,
bit blit 32, MULTIBUS 64.

**The timers table is the MC6840's register layout, from Apollo.**
`8800` write CR1 or CR3, `8802` read status / write CR2, then
`8804`/`8806`, `8808`/`880A`, `880C`/`880E` as the three counters' high and low
halves — which is `device/ap_mc6840.h`'s part, confirmed by the machine's own
vendor rather than only by the Motorola datasheet. The calendar is at
`8880`-`8884` here where `002398-04` puts the DN3000's at `8900`: a
generational move, recorded because `ap_tape.h`'s address note lists the later
one.

**The touchpad packet is `002398-04` p. 6-20's, printed identically.**
`E8` escape, low 8 bits of X, Y's low nibble over X's high nibble, high 8 bits
of Y; **about 30 data points per second** through **SIO port zero at 1200 baud**;
**X and Y approximately 30 to 1100**. `device/ap_kbd.h` already carries all
three facts with the Rev 4 citation, so this is **one witness printed twice**
rather than two — [[omti-manuals-share-source-text]]'s rule, applied before it
could mislead.

**The magtape controller is the MULTIBUS one and not the SC-499**, as this
record already warned. Its whole interface is here — control page `FE8000`,
vector `B3` (`$2CC`), MULTIBUS level 3, I/O map `FFF980`-`FFF9FE`, `FE80AA`
CHANNEL ATTENTION and `FE80AB` CONTROLLER RESET, the Intel-style system
configuration pointer at `xxxFF6` → configuration block → channel control block
→ parameter block, the sixteen command bytes (`00` initialize through `50` erase
to EOT), and the control and status words bit by bit. None of it is this
machine's tape path.

**Two full keyboard scan-code charts**, the 880 and the Low-Profile, each in
*physical* and *translated (user mode)* form — 256 cells apiece. `ap_kbd.c`'s
table comes from the keyboard's own manual `[KBD]` and is keyed by key rather
than by code, so these are the inverse mapping and a **second witness**. One
landmark checked: the Low-Profile translated chart's `1B` is `ESC`, and
`ap_kbd.c`'s `B1`/ESC sends `0x1B`. A full 256-cell cross-check is real work
with a real chance of finding a transposition, and is a named plan item rather
than a claim made here.

**MULTIBUS devices**, by interrupt level: `1` Interlan Ethernet controller
(003613) and the FPS array processor, `2` the TITN X25 controller, `3` the
Rimfire transport controller, `4` the Intel SMD and Xylogics FSD controllers,
`5` the IKON Versatec controller, `6` the Printronix parallel printer, with
level 0 "reserved for customers". And the **register set** page is the 68000's
with Apollo's names on two registers: **`A5` is DB, the start of the data
section, and `A6` is SB, the top of the current stack frame** — which is the
`A5` the DS5500's transfer-vector item indexes through.

So for this project `002398-03` chapter 7 and `002398-04` chapter 7 are **one
witness printed twice**, which is [[omti-manuals-share-source-text]]'s rule at
the scale of a chapter. That is worth knowing before reading chapters 8 to 11:
they are DN400/DN460/DN550/DSP80 and Rev 4 covers the same machines, so the
expected yield is *confirmation of the printing*, not new facts — and the way to
find out is still to read them.

**What is genuinely new, and it is lineage rather than specification:**

- **The DN300's DMA controller is a Motorola M68450**, at `9000` with four
  channels: ring receive header (highest priority), ring receive data, ring
  transmit, Winchester/floppy (lowest). This core models the **Intel 8237** for
  the Series 3000/4000 — so Apollo changed DMA part between the two
  generations, which is what moving to the AT bus implies and which nothing in
  this project had stated.
- **The device block's addresses are continuous from 1981 to 1987 and then
  diverge.** `8000` mmu, `8400` sios, `8800` timers, `9000` DMA are the same on
  the DN300 and on the DN3000 (`ap_tape.h`'s list). `9400` is not: the DN300
  puts *display* there and the DN3000 the two interrupt controllers. Partial
  continuity, which is more useful than either "the same" or "different".
- **The page frame table entry has a `G` — "page is global" — bit** in Apollo's
  own 1981 MMU, and an **ASID of 0-127**. `[AEGIS]` §9 explains the 68040's `G`
  bit as "ASID 0 is global space, marked by a hardware global bit in the MMU
  hardware page tables"; here is the same idea in the hardware Apollo built
  before it bought one. Lineage, not a specification this core can use.
- **The DN300's interrupt levels**, on 68000 auto-vectors rather than an 8259:
  `1` SIO, `2` keyboard, **`3` ring**, `4` display, `5` disk/floppy, `6` timers,
  `7` parity. The Series 4000 ring is on master IRQ 2 (`RING.md` 107) through a
  different mechanism, but the *relative* order — ring above display and disk,
  below keyboard and SIO — survives.
- **The diagnostic register's `0100 snoop`**: "accept all packets but only set
  ack byte for packets actually addressed to me". A promiscuous mode that leaves
  the acknowledge alone, which is exactly what a ring analyser needs and what a
  model of the card would have to honour.
- **The disk controller at `9C00` is the ANSI/SMD one**, not the OMTI: ANSI
  command and parameter ports, a 16-bit controller status, a separate floppy
  block at `+10` and the **calendar at `+20`**. Its ANSI command set (`40`
  attention control through `6F` load test byte, `00`-`2F` parameter-in) is the
  drive's, not the controller's, and this core's OMTI speaks a different
  language.

The rest is the DN300's own: the BLT registers and their two's-complement
counts, the display control and status registers, the 68010 bus-error stack
frame, the single- and double-precision floating-point formats (the FPU being
"essentially the same as PEB without the cache"), the memory control and status
registers with their **two LEDs**, the MMU's PID/PRIV and status registers, the
PTT at `700000` with "one PTTE every 1024 bytes in table", and the SC2681 and
MC6850 register sets — the last two of which `SCN2681_WALK.md` and
`device/ap_mc68681.h` already carry from the parts' own datasheets.


## Chapter 8, *DN400, DN420, DN600*, pp. 8-1 to 8-47 (PDF 152-198) — read whole 2026-09-13

**One finding, and it upgrades a `RING.md` entry from a derivation to a
statement.** p. 8-38, the DN4xx **Transmit Command Register** at `BC14`:

> `DELAY` — "Enable an additional **seven-bit delay** into the length of the
> network. This may be required to support the recirculation of the token,
> **which is nine bits**."

`RING.md` finding 32 says "a ring must be longer than its own token" and derives
it from `[MAC]` §3.2 and §3.3.2. Here Apollo says it, in 1985, **and gives the
hardware's remedy** — a seven-bit delay the transmitter can insert, which with a
transceiving station's own one to two bits of elastic store reaches nine.
Recorded as findings 32a and 32b; nothing in this core depends on it.

The same register names `FTRANS` ("force transmit ... must be accompanied by the
TMT bit", which is chapter 7's `7000` with its co-requirement stated) and
`CH1DIS` ("disable the second transmit DMA channel ... a zero length data field"
— a header-only frame).

**And one correction to chapter 7's record.** That chapter's note said "the
DN300's DMA controller is a Motorola M68450" and left it there. Chapter 8 shows
the picture is two parts, not one: the **M68450 is the system DMA controller** at
`9000`, and the **ring/disk controller carries an Intel 8237 of its own** at
`BC50`-`BC5E` and `BC70`-`BC7E` — Command/Status, Request, Single Mask, Mode,
Clear Byte Pointer, Master Clear, All Masks, byte-addressed on even addresses,
with its command register's eight bits named. So the 8237's presence in an
Apollo predates the Series 3000 by years; what the AT bus changed is that it
became the *system* controller.

**Two more things worth naming before they are needed.** The **ring/disk
controller's register map** at `BC00` is the byte-addressed ancestor of chapter
7's word-addressed `9800` page, and it reads the **node ID as three bytes** at
`BC0A`/`BC0C`/`BC0E` — relevant to [[node-id-lives-in-battery-ram]]'s question
about where a machine's ID comes from, on a machine that is not this one. And
the **PEB's FPU command set** (pp. 8-26 to 8-29) lists `FPP_$SSIN`, `SCOS`,
`STAN`, `SATAN`, `SEXP`, `SLOG` and their double-precision twins, plus `ATAN2`,
`TRUNC`, `NINT`, `MIN`/`MAX`, `SQRT` and complex arithmetic — **the same
transcendentals `000792-A01` Appendix F says Apollo's compilers emit as 68040
unimplemented instructions** (`FSIN FCOS FTAN FATAN FETOX FLOGN FLOG10
FINT/FINTRZ`). The set Apollo's runtime needs was fixed from the 1981 PEB to the
1990 68040, which is a reason to trust that list as a workload rather than as an
accident of one compiler.

**Everything else is the DN400/420/600's own** and bears on nothing here: board
and display jumpers by CRT type, the BLT registers and their OS virtual
addresses, the DCSR with `GO`/`NIL`/`FROM MM`/`TO MM`/`IEOF`/`IDONE`/`NON
CONF`/`DECR`/`FILL`/`ON`, the DN6xx colour display's microcode control and status
registers, the 68010 fault frame (the same `fault_$bus_info_t` chapter 1 gives),
the fault-vector table, the µPD765 floppy status registers, the I/O map, the
MCSR with its ECC syndrome table, memory board jumpers and the 28-row memory
configuration table, the MMU with its four-value DOMAIN field and dual-CPU
registers, and the **DN6xx monitor timing** — 31.2 µs at 32.051 kHz horizontal,
800 lines at 75.70 Hz or 1024 at 60.0 Hz, with every porch and blanking
interval. That last is **not** a source for this core's display: `GRAPHICS.md`
carries a 1280×1024 monochrome timing set from a Series 3000/4000 source, and
these are different monitors.


### Chapter 8's last pages, 8-42 to 8-47

The DMA mode/request/mask/status registers complete the **8237** picture — the
mode register's `00` demand, `01` single, `10` block, **`11` cascade**, with
address decrement, autoinitialise and the two-bit transfer type, which is the
same encoding `device/ap_i8237.h` models. And the **serial I/O is a Zilog
Z80-SIO**, not the DN300's SC2681: write registers 0-7 with SDLC, hunt phase,
CRC generators, sync characters and a vector register, read registers 0-2 with
the SDLC residue table. A third serial part in one handbook, which is why "the
SIO" is never a safe shorthand across Apollo generations.

will emit a constant sound; toggling DTR with RTS set emits different tones."**
That is how a DN4xx made noise.

## Chapter 9, *DN460, DN660, DSP160*, pp. 9-1 to 9-15 (PDF 199-213) — read whole 2026-09-13

**The DNx60 is the machine `[AEGIS]` means by "forward-mapped", and its MMU is
the 68030/68040's shape a decade early.** p. 9-4: "The DNx60 is a **micro-coded**
machine with a **forward-mapped address translation mechanism (using in-memory
page tables)**. **There is no PTT or PFT.**" Control is through `MOVEC` into
Apollo-defined control registers:

    120-13F  Current Region Registers (0-31)
    11F      Current ASID
    11E      Current Floating Point ASID
    11D      Purge Translation Buffer -- 1 purge the VA in 11C,
             2 purge the entire TB, 4 purge half the TB containing it
    11C      VA used in TB purge
    119      bit 0 enable address translation, bit 1 enable data cache,
             bit 7 domain bit
    113      read hardware and microcode revision levels

and the table walk is three levels with a **global bit at the top**: a region
register is `V | G | physical address of segment map` covering **8 MB of VA**
(32 of them); a segment map entry is `V | access | physical address of page map`
with one page of entries per region; then the page map. Fault vectors `80`
region, `81` segment, `82` page, `83` access violation, **`84` floating-point
ASID trap**.

So Apollo had an ASID-tagged, forward-mapped, in-memory-page-table MMU with a
three-granularity TLB purge **before Motorola shipped one**, `[AEGIS]` §9's
account of the 68040's `G` bit is that lineage arriving back in Apollo's hands,
and §11.2.3's "BST chain for forward-mapped systems" names this machine.
Recorded as context for the 68040 MMU work; nothing here is a specification this
core can use.

**The rest is the DNx60's own**, and most of it is a cross-reference to chapter
8: the address space (traps at `200800`, PROM at `400`, ring 1 and 2 at `B800`
and `BC00`, the **i-caches at `D000`-`DC00`** and the **writable control store at
`C000`**); the **CPIO** — a second processor that runs when the CPU does not,
with control, status and **LED registers** at `8000`/`8002`/`8004` and status
bits for halted, slave, not-master, bus timeout and **`N` normal mode, 0 =>
Service Mode**; the **micro-machine control registers**, none of them mapped,
with `T` cause trap to Micro Exec, `I` enable instruction cache, `M`/`S`/`C`
macro/micro/clock step and `E` enable (0 => reset) — a hardware single-stepper;
the fault types in three groups; the long fault frame with a `'0BAD' SIGNAL`
word at `+0E`; the IEEE single and double formats; 64 possible memory control
register addresses at `$20` intervals; and the **two SC2681s giving four SIO
lines**, where **"lines 0 (the keyboard, which runs at 1200 baud) and 1 are
paired on one chip"** — a second statement of the keyboard's rate, which this
core models.
