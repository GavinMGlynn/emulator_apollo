## §1.4.1 corrected a field and confirmed four others

> "SR10.4 provides support for the new Domain Series (DS) 5500, which is an
> **MC68040-based CPU board upgrade** to the Domain Series 3500, 3550, and 4500
> personal workstations.
>
> All existing graphics, networks, mass storage, and backup devices presently
> available on the DN3500, DN3550 and DN4500 workstations are supported. All
> memory modules shipped with the DN3500, DN3550 and DN4500 workstations are
> also supported. In addition, a **new 16-MB memory module has been added which
> gives the DN5500 a total memory capacity of 64 MB**.
>
> Because the MC68040 combines the MC68030 and MC68882 chip set into one package
> and provides greater performance, the **Floating-Point Accelerator Board**
> presently available on the DN3500, DN3550 and DN4500 **is not supported** on
> the DN5500.
>
> **The PC AT bus and onboard I/O are retained on the DN5500.** To optimize
> performance, a **new memory controller and bus interface** have been designed.
> **A new I/O protection mechanism has been designed to support the 4-KB page
> I/O mapping of the MC68040.** The new CPU board uses the **25 MHz** version of
> the MC68040."

**The correction**: `ap_model.c` gave the DN5500 a 32 MB ceiling citing `[CFG]`,
the *HP-Apollo Products Configuration Guide* of **December 1989** and its July
1990 quick reference — **both two years older than the machine**. It is 64 MB.
`model_suite` then required the DSP5500 row to follow, which is the suite
catching the second half rather than the author remembering it.

**The confirmations**: the 25 MHz clock, the on-chip FPU with no accelerator
board, and the retained AT bus and onboard I/O were all already in the row from
other sources.

**And one sentence names something this project found the hard way.** "A new I/O
protection mechanism has been designed to support the 4-KB page I/O mapping of
the MC68040" is `board/ap_ioprot.*`, which exists because a DS5500 PROM clears
four long words at `07000000` before it has a stack and the machine died 137
instructions in without it. `019411-A00` Table 2-5 named the region; nothing
said what it was *for*. **The empirical placement and the documented purpose
agree and neither was derived from the other.**

*It also settles the naming*: the document uses "Domain Series (DS) 5500" and
"DN5500" in adjacent sentences for the same machine, which is why both appear
across this project's own records.

## §1.4.1's last two paragraphs, which the first reading stopped short of

Beyond the memory modules quoted above, §1.4.1 says three more things:

> "Because the MC68040 combines the MC68030 and MC68882 chip set into one
> package and provides greater performance, **the Floating-Point Accelerator
> Board presently available on the DN3500, DN3550 and DN4500 is not supported on
> the DN5500.**"
>
> "The PC AT bus and onboard I/O are **retained** on the DN5500. To optimize
> performance, a **new memory controller and bus interface** have been designed.
> **A new I/O protection mechanism has been designed to support the 4-KB page
> I/O mapping of the MC68040.** The new CPU board uses the **25 MHz** version of
> the MC68040."

**The I/O protection sentence is the one that matters**, and it is now cited in
`board/ap_ioprot.h`. That region — `019411-A00` Table 2-5's
`07000000`-`0700FFFF` — is modelled as storage with the *meaning* of a byte
marked `PROVISIONAL`, because Table 2-5 gives it a title and no register and the
parent handbook `007861-A01` is not scanned anywhere. This gives its **purpose**:
it exists because the 68040 pages at 4 KB where the 68030 pages at 1 KB, so the
older machines' I/O protection could not express a 68040 page. A purpose is not
a layout and the `PROVISIONAL` stands; what it removes is the question of why
the region is new to this model.

**25 MHz** confirms the clock this core runs a DS5500 at, and the FPA sentence
says a DS5500 has no `ap_m68881` — which is how this core has it, the 68040's
FPU being on-chip.

## §4.12, four MC68040 errata, and what they mean for an instruction core

*Programming Limitations*, p. 4-15, verbatim:

> - "The new 68040 **MOVE16** instruction must be preceded by a **NOP** in order
>   to work correctly. (Domain compilers never generate a MOVE16 instruction.)"
> - "**Indirect accesses**, where the intermediate access (to fetch the address)
>   is to a **serialized page** causes the **CPU to lock up**. Avoid this
>   construct. (Domain compilers do not generate this construct.)"
> - "Certain instructions (**FMOVE, FMOVEM, MOVEM**) can cause **double writes**
>   to occur, even to serialized locations, unless they are preceded and followed
>   by a NOP. Beware of this when writing GPIO drivers."
> - "The **FScc -(Ay)** instruction does not work. Avoid this construct. (Domain
>   compilers do not generate this construct.)"

**These are defects of the part as fitted to this machine, not of the
architecture**, and they belong to the 68040 instruction core when it is
written. None of the four is reachable in this core today: `MOVE16` exists as a
bus-access type and a timing row and has no decoder, and there is no `FScc` at
all. Recorded on the plan under the 68040 item rather than implemented.

**What they do *not* reveal is a missing feature.** "Serialized" is the 68040's
page cache mode `CM = 10`, *noncachable serialized*, and
`ap_m68040_descriptor.h` already carries all four modes with
`AP_M68040_CM_NONCACHABLE_SERIALIZED` among them; `ap_m68040_bus.h` records that
"cachable writethrough versus serialized noncachable only affects read
accesses". So the mode these errata are about is modelled and the errata are
about what the silicon does wrong with it.

**And three of the four say Domain's own compilers avoid the construct**, which
is the reason a release could ship with them. Reproducing an unstated failure —
"does not work correctly", "locks up", "can cause double writes" — would be
inventing behaviour, which `CLAUDE.md` forbids; the honest position is that the
instruction core will implement the *architectural* behaviour and this section
is why a divergence from real hardware, if one is ever measured here, would not
automatically be our bug.

## §4.10, hardware bugs, and the two rows about machines this core models

**§4.10.3, Logical Volume Limitation** — "The maximum logical volume size for
striped disks on the DN10000 is 16-GB. For other nodes with **4-KB disk block
size (SAU11, 12, and 14)** it is 4-GB, and it is **2-GB on SAU7, 8, and 9**
nodes."

So a **DS5500 (`sau14`) uses a 4-KB disk block** and a DN3500 (`sau7`) does not.
The section gives no block size for sau7/8/9 and none is inferred here.

**§5.5 says the same group differently, and more usefully**: "The maximum file
size on **SAUs 10, 11, 12, 14 (4K-page machines)** has been increased from 2 to
4 gigabytes. On other machines, the limit remains 2 gigabytes." So those are
**4K-*page*** machines, not merely 4-KB-blocked ones — and everywhere else on
this shelf an Apollo page is 1024 bytes (`[GPIO]` glossary: "page: 1024 bytes;
the unit of measure in our systems").

**That is a prediction a future run can falsify.** The 68040's page size is TC
bit 14 — 4 KB or 8 KB, both modelled, `ap_m68040_regs.h`'s `page_size` — and
Domain/OS on a DS5500 is a 4K-page system, so when this core's DS5500 finally
turns translation on, **`TC` should read `P = 0`**. Nothing depends on it today:
the DS5500 runs with `translation off` and `tc 00000000` through the whole boot
this core reaches. Recorded so that if it comes up 8 KB, that is a finding and
not a surprise.

**§4.10.7, Network Limitation** — "On Series 400t and **DN5500** systems, the
**802.5 Token Ring controller cannot be set to unit 1. You must use unit 0
setting.**"

*This is the 802.5 card, not the Apollo Token Ring*, and the two are separate
products — `[GPIO]` Table 3-1 lists "Apollo Token Ring Network Controller-AT" at
`220-23F`/`320-33F` and the 802.3 controller at `300-307`, and 802.5 is a third.
So it does **not** settle `RING.md` 134's unit-0/unit-1 question for the Apollo
ring, and must not be read as if it did. What it does show is that a
strap-selectable unit 0/1 is the normal arrangement for a ring controller on
this bus, and that on a DN5500 in particular unit 1 is unusable.

**§4.14, SAX Limitations** — "**If the ID of a SCSI cartridge tape is not set to
0, SAX fails.**" Worth having for the DS5500 SCSI item, whose exerciser is SAX.

§4.10.1, 4.10.2, 4.10.5, 4.10.6 and 4.10.8 are Series 400/425, Meerkat displays
and a dial set, and concern no machine this core models.

## §2.3, §2.4, §2.5, and the install route

"Installation of SR10.4 on an existing node **does not require disk
initialization (`invol`)**" (§2.3), but if you do not, "be sure to use the
`config` utility to reconfigure before installing SR10.4, since the
configuration questions for SR10.4 are substantially different from those for
earlier SR10 releases" (§2.3.1). §2.4: "At SR10.4, support is discontinued for
SAUs 2, 3, 4, 5, and 6." §2.5: "SR10.4 is **unconditionally installed with
closed Access Control Lists**", limiting write access on system files to root —
which is worth knowing before anything tries to write to `/lib` or `/sys` on a
restored volume.

## One more hardware constraint, and it bears on the SCSI item

§3.3.6's documentation corrections carry a replacement notice for *Using the
CD-ROM Reader*:

> "**NOTICE: You cannot use a CD-ROM drive in a Series 35xx, 4000, or 4500
> system that uses a non-SCSI cartridge tape drive. You must either remove the
> ctape controller from the system or replace your non-SCSI ctape drive with a
> SCSI ctape drive.**"

The **non-SCSI cartridge tape drive is the SC-499 this core models**, and the
Series 35xx/4000/4500 are the machines a DS5500 is a CPU upgrade to. So on
exactly this machine class the SC-499 controller and a SCSI controller **cannot
both be fitted**. The notice does not say why — address, IRQ or DMA — and none
is inferred here. It is recorded because the DS5500 SCSI plan item proposes
adding SCSI to a machine that has the cartridge controller fitted, and this says
a real one could not have both.

The same page also changes "the minimum boot ROM revision for booting from a
Series 2500 from **4.0 to 4.1**".

## Method, and why it is recorded

This document has **no text layer at all** — `pdftotext` returns 202 form feeds
— so every page costs a render, and the walk record said from the start that it
"should be read against specific questions rather than front to back".

What was done instead, on 2026-09-12: all 202 pages rendered at 200 dpi, all 202
**OCR'd with `tesseract` for triage only**, and every page whose OCR carried
hardware vocabulary read as a **page image**. The OCR was never used as a source
for a fact — `CLAUDE.md`'s rule about reading page images stands, and this
document is exactly the kind of scan that rule exists for. Twenty-seven pages
scored above the threshold; all were read, along with the full contents, all of
chapter 1's hardware sections, chapter 2's §2.1-2.5, §2.7.1 and §2.8, chapter
4's §4.9-4.16, and chapter 5 entire.

**What the remainder is**: chapter 1's §1.6-1.7 (threads, NCS 2.0, TCP/IP,
printing, command changes), chapter 3's man-page and help-file lists, chapter
4's §4.1-4.8 (Domain/OS, X11, HP VUE, NCS and DSEE bugs) and chapter 6 (eight-bit
native language support). None of it concerns hardware this core models, and the
triage found no hardware vocabulary in any of it. That is a *claim about the
triage*, not a claim to have read every word of those pages, and it is written
that way deliberately.

## §1.4.7.5's tape close algorithm, and what the distribution media actually show

The tape chapter is about DDS drives, but one paragraph describes the **driver's
close routine** in general terms:

> "1. If the last operation was a write ... the driver automatically writes **two
> filemarks**. If the 'no rewind' bit is not set, the tape is then rewound to
> LBOT. If the 'no rewind' bit is set, the driver backspaces the tape one
> filemark and exits ... 2. If the last operation was a read ... if the 'no
> rewind' bit is not set, the tape rewinds to LBOT."

**The five SR10.4 cartridges do not look like that**, measured: no two mark
blocks are ever adjacent on any of them. They carry marks in *triples* a few
blocks apart — `019594-001` has 19168, 19171, 19175 — which is ANSI label
bracketing, `MARK EOF1 EOF2 MARK HDR1 HDR2 UHL1 MARK`, and a single mark near
the end. Block 0 is `VOL1ST0194 … apollo`, block 1 `UVL1`, 2-4
`HDR1`/`HDR2`/`UHL1`, block 5 the first mark. So the distribution volumes were
not written by a driver close of the kind described; `image/ap_ct.h` and
`tools/ct_extract.py` already have this structure and nothing changes. Recorded
so that the "two filemarks" sentence is not later read as a statement about
these images.
