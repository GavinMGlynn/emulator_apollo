## Chapter 10's `distaa` and `install` entries — 10-16 to 10-19

The two tools a scripted install actually needs, and `distaa`'s first sentence
is the reason to prefer them: it "loads products **non-interactively**".

    distaa {-a | selection_file} [-f] [-v] [-e max_errors] [-m media_type] AA

`-a` loads everything; a *selection_file* loads one product or a subset.
**`-f` forces every object** — without it `distaa` loads only what is not already
in the Authorized Area, which makes a re-run cheap and a forced re-run explicit.
`-e max_errors` sets an abort threshold and **without `-e` `distaa` does not abort
on load errors at all**, which a script must account for. `-m` is `c`, `f` or
`m`, and cartridge is the default. The `AA` need not already be an Authorized
Area; `distaa` creates the `install` subdirectory.

    install [-dehilmoprtvx] -s AA {-c configuration_file | -a | -u} {target | -n target_list}
    install -A [-hoprtvx] -s AA {-c configuration_file | -u} {target | -n target_list}
    install -D product_name version [-oprtvx] -s AA {target | -n target_list}

Three forms: install, reset ACLs, deinstall. **"Only three [parameters] are
required for installing products"** — `-s` for the Authorized Area, one of
`-a`/`-c`/`-u` for the configuration, and at least one target — "We also
recommend using the `-x` (continue on error) and `-v` (verbose) options."

*So the minimum is smaller than Chapter 5's example suggests*: `-a` needs no
configuration file at all, where p. 5-23's line names one.

## Chapter 11's Authorized Area components — 11-1 to 11-16

**Table 11-1 is the whole layout**, and it confirms the paths this project read
off the cartridge as file names:

| component | location |
| --- | --- |
| media TOC | `install/toc` |
| install tools | `install/tools`, `install/minst` |
| help files | `install/help/<tool>.hlp` |
| product directories | `install/ri.apollo.<product>.v.<version>` |
| selection files | `install/templates/apollo/<product>.v.<version>/aa.<name>` |
| override files (supplied) | same directory, `ov.<name>` |
| override files (**active**) | `install/overrides/ri.apollo.<product>.v.<version>` |
| configuration files | same directory, `cf.<name>` |
| release documentation | `install/doc/apollo` |
| installation log | `install/log_file` |
| `excludes.list` | `install/overrides/excludes.list` |

**And p. 11-16 names the exact file this project derived from the media**: "the
pathname of the default configuration file for version 10.4 of Domain/OS is
`AA/install/templates/apollo/os.v.10.4/cf.os`." Document and cartridge agree to
the character.

*The release index is the blueprint* (p. 11-8): one per product directory, named
like it, defining the configuration questions and **their default answers**, the
subcomponents, the installed objects' initial ACLs, and the product's
dependencies — "most dependencies are dependencies on a particular version of
Domain/OS". That is where `config`'s `(D)` answers come from, and why a default
configuration file is enough to install without answering anything.

*Override files are a filter, not a selection* (p. 11-13): once **activated** —
copied to `install/overrides/ri.apollo.<product>.v.<version>` — an override
restricts what `config` will offer *and* overrides a configuration file that
asks for more, "similarly ... if a user installs products with the `-a` option
... or the `-u` option". So an override left active from an earlier subset load
silently narrows a later full install, which is worth knowing before one is
copied into place.

## Chapter 11, *Relation of Authorized Areas to Distribution Media* — 11-21

Two pages, read because they are the *documentary* statement of the cartridge
structure this project derived from the images, and they agree with it.

> "All media types are in **`wbak` format** ... **Files 2 through *n*** on the
> media contain the product release indexes and the actual products. **File 1**
> contains the following administrative objects: installation tools (in
> `install/tools`, `install/minst`), help files (`install/help`), HP-supplied
> selection, override and configuration files (`install/templates/apollo`),
> online release documentation (`install/doc/apollo`), TOC files
> (`install/toc`)."

**So the file marks separate `wbak` files**, which is what `ap_ct.h`'s measured
layout says from the other side: the boot cartridge is one data file between
marks at 16/22 and 104,838, and "the four software cartridges ... hold 11 to 41
marks each, **separating the files of the distribution**". A structure derived
from five images and a structure stated in the manual, arrived at independently.

*And it explains why Chapter 5 needs two commands rather than one*: "`distaa`
loads only the products and product release indexes; it does **not** load any
objects from file 1. Therefore, if you use `distaa` to load products, you must
restore the appropriate objects from file 1 with the `rbak` command **prior to**
loading the products." `rbak` reads file 1, `distaa` reads files 2..n, and
`minst` does both.

## Chapter 12, *Installation Errors and Warnings* — read whole, 12-1 to 12-7

Read because the next thing this project runs is an install, and a scripted run
that cannot recognise a failure will wait for a success that is not coming.

**And it names a trap in this project's own script.** `install` ends with one of
two messages:

```
RAI install has successfully completed.
RAI install has completed with errors.
```

`tools/mame-oracle/install-domainos.cmds` waits for
`RAI MINST has completed`, which is the outer tool's line and survives either —
so that file is safe. Anything that waits for **`successfully`** is not: an
install that completes *with errors* still completes, and the script would hang
on a machine that had finished. Wait for `RAI install has completed` and read
the word before it, or expect both.

*The labels are greppable by design*: "`install` prefixes all warnings with the
label `WARNING:` and all errors with the label `ERROR:`", which is what a
console monitor should watch for rather than the individual texts.

**Errors** (12-3 to 12-5), each with its remedy: cannot access the Authorized
Area (check `-s`); cannot install soft link / must be a local copy, both cured
by re-running with **`-m`** (do not respect customization); could not copy file
(check `install` is owned by `root` with **setuid** on); could not find UID (run
**`salvol`**); could not get node UID (**`ctnode`** it); could not hard link;
could not preserve or place original ACLs, where install leaves the displaced
object as **`/install/rai_acl_temp.<number>`** on the target; not found in
authorized area; and **"Installation of … has been aborted"**, which is an ISP
mismatch — "a product whose ISP type (**m68k** or **a88k**) differs from that of
the target node ... may prevent the target from booting", overridden with `-h`.
*That one is worth having on a DS5500*, where the machine type and the release's
per-machine directories are exactly what this item is negotiating.

**Warnings** (12-6 to 12-7): could not change type / could not delete, both
pointing at `install` not being setuid `root`; could not create baseline file,
which does not stop the install but leaves the node without "an accurate account
of what is installed"; invalid configuration for remote install; remote process
call failed, which happens when `/sys/spm/spm` is not running on the target;
target path file not found or unreadable; and "would install through a link -
item is ignored".

And the standing advice, which applies to every run here: "**do not reboot until
after you resolve any error conditions**", and a re-run is cheap because
"`install` copies only those objects that it did not successfully install during
the first run".

## Chapter 5, *Loading and Installing Products* — read whole, 5-1 to 5-29

Read for one question: **can the DS5500 install be driven without `minst`'s
prompts?** It can. Chapter 5 does the same job with four tools and command
lines, and `minst` is explicitly a front end over them (Chapter 10, p. 10-43:
"You can do everything `minst` does by invoking other commands directly").

| step | command |
| --- | --- |
| load the administrative objects | `rbak -dev ct0 -ms -sacl -pdt -force -du -f 1 -all` |
| load the products | `AA/install/tools/distaa -f -m c -a AA` |
| *(optional)* configure | `AA/install/tools/config -s AA -c configuration_file` |
| install | `AA/install/tools/install -vx -s AA -c configuration_file target …` |

`dev` is `ct0` for `rbak` and **`c`** for `distaa` — the two tools spell the
cartridge differently, which is the kind of detail a script gets wrong once.

**And `config` is optional, which is what makes the whole thing scriptable.**
p. 5-12: "Instead of configuring a product, you can supply the pathname of the
**default configuration file that ships with every product** as an argument to
the `install` tool." p. 5-23 says where they are: the Authorized Area
subdirectory `install/templates/apollo/product_name.v.version`, named
**`cf.product_name`**. So no interactive answer is needed anywhere in the
sequence.

*The completion message is the one this project already waits for*:
`RAI install has successfully completed`.

**What is left interactive is the media**, and only the media: "If the products
reside on more than one piece of media, you are prompted during the load process
to remove media from the drive and replace it with the next piece" (p. 5-8).
That is the `swap` verb's job and nothing else needs one.

*Also from this chapter*: **selection files are ASCII** and editable —
`install/templates/apollo/<product>.v.<version>/aa.<name>`, e.g.
`aa.aegis_small` — a list of `move` lines whose last field is `-rootaa` or
`-nil`, so a subset can be loaded by editing one. And a note this project should
heed when it gets there: "If you are loading Domain/OS from cartridge tape, be
sure to insert the **first product volume, not the boot volume**" — `019594-001`,
not `019593-001`.

**One trap in the chapter, and it is checked rather than left standing.** p. 5-14:
"when both the **m68k** and **a88k** versions of a product reside in an
Authorized Area, `config` considers the a88k version *later than* the m68k
version ... if you use the **`select all`** command, and the products
`ri.apollo.os.v.10.4` and `ri.apollo.os.v.10.4.p` reside in the Authorized Area,
**only `ri.apollo.os.v.10.4.p` (the a88k version) is selected**." An `.p`
extension is the a88k build, and Chapter 12's aborted-install message says an ISP
mismatch "may prevent the target from booting" — so a scripted `select all` on
mixed media would install the wrong architecture on a 68040.

*It cannot bite here.* Searched across the media this project holds:
`019594-001`, `019594-002` and `019593-001` carry **zero** occurrences of
`ri.apollo.os.v.10.4.p` against 97,495, 122,650 and 800 of the plain form. These
cartridges are m68k only, so `select all` is safe on them — recorded with the
count so a later reader does not have to re-derive it, and so the check is
repeatable if other media arrive.

**And `config` defaults everything it is not told.** "All configuration questions
have a default answer, indicated by a `(D)`", `<RETURN>` at the `==>` prompt
takes it, and "if you exit the configuration session without answering all of a
product's configuration questions, the unanswered questions are automatically set
to their default values" (p. 5-16); the same holds for a product selected but
never configured (p. 5-13). So even the interactive tool reduces to `select all`
then `exit`.

*Step 8's override activation is conditional*, which a full load skips: it is
needed only "if you used a selection file ... to load a subset of a product, or
if you loaded a different configuration of a product that already resides in the
Authorized Area" (p. 5-9).

**The transcripts are what a script matches on.** `install` announces itself
`RAI Install Tool V2.T11 12 Dec 90` and `config` `RAI Config Tool --- Version
2.01 09 Aug 90`; a `config` session ends `Validating selected products, please
wait ...` then `New configuration file saved in <path>`; an `install` run prints
its switch settings back ("Continue on error has been selected", "Object
customization is on"), then `Installing //<node>`, baseline-file lines, a
`Directory region:` / `File Region:` / `Link Region:` breakdown, and finally
`RAI install has successfully completed`. Chapter 12 gives the other ending.

*Deinstall is the same tool*: `install -D product_name version -vxs AA target`,
with the warning that it is "best reserved for optional products. Do **not** use
this method to remove Domain/OS. To remove Domain/OS, initialize the disk using
the `invol` utility" (p. 5-27).

**Scope, so this is not over-read.** Chapter 5 says it is for optional products,
patches, PSKs and Domain/OS *updates*, and that installing Domain/OS on a new or
initialized node is Chapter 1's or Chapter 2's procedure. Whether the tool-level
route is a legal substitute for Step 4 on a freshly restored volume is not
stated here, and `minst` remains what Chapter 1 tells you to run.

## Chapter 10's `minst` entry — read whole, 10-42 to 10-46

p. 1-18 says "For more information, see `minst` in Chapter 10", and this project
had never looked. It settles the one thing `install-sau14.cmds` calls out as not
established — "MINST's exact selection interface at that step".

**The SAU selection is not a prompt: it is a consequence of the mode.**

> "When you install Domain/OS, **novice mode installs only the `/sau` directory
> for the machine type of the target node**. This means other machine types
> cannot boot diskless from the target node. Expert mode allows you to choose
> which `/sau` directories to install."

So the run that produced `dn3500-sr10.4-installed.awd` got `/sau7` **because the
target was a DN3500**, not because of an answer anyone gave; and a DS5500 run in
novice mode installs `/sau14` for the same reason. *That removes the unknown this
item has carried since 2026-09-10* — a DS5500 MINST needs no SAU selection at
all. (The **template** number, 11, is the aegis/bsd/sys5 size configuration, a
different question; and Chapter 1 p. 1-24 has `minst` loading **every** SAU into
the Authorized Area unconditionally in either mode, which is why the AA held
`sau7 sau8 sau9 sau11 sau12 sau14` and the *node* held one.)

**And the cartridge sequence is stated where the `swap` verb needed it:**

> "If the set of distribution media contains more than one tape volume, `minst`
> prompts you in sequence to insert each tape into the drive. However, if you
> select a product or product subset that does *not* contain any objects on one
> of the tapes, `minst` skips the prompt for that particular tape volume."

The rest of the entry:

- **`minst [authorized_area]`**, at `AA/install/tools/minst`. The argument is
  optional; without it `minst` prompts. The directory "can be *any* existing
  directory" and `minst` creates the `install` subdirectory if it is not already
  an Authorized Area — but for an optional product it should be an existing AA,
  because optional-product media carries no tools or pre-SR10.4 ones.
- **It starts automatically on login after a boot from distribution media**, and
  you can quit it, `cp /com/sh`, and use the tools directly instead.
- **Two phases, load then install**, and "You cannot skip the load phase.
  However, you can quit after the load phase and skip the installation phase."
  The load phase is `rbak` for the administrative objects then **`distaa`** for
  the products; the install phase is **`install++`**, which invokes `config` and
  `install`. So `minst` is a front end over the four tools, and Chapter 5 is the
  same job done with them directly.
- **Novice against expert**, eight differences, of which three matter here: the
  `/sau` rule above; novice "unconditionally installs products ... with hard
  links to the products in the Authorized Area", which is Chapter 1 p. 1-19's
  warning from the other side; and **expert mode can save the answers to a file
  for reuse on later runs**, which novice cannot — the closest thing to a
  scripted install the tool offers.
- Novice mode "allows you to install products only on the node connected to the
  tape or floppy drive", which is this machine.

## Chapter 1, *Installing Domain/OS from Media* — read whole, 1-1 to 1-25

**The procedure this project has been executing by hand since Phase 4**, in
seven steps. Steps 4 and 5 were recorded above from the first reading; here is
the rest, and then the three places this project's route departs from it.

**Step 1, prepare** (1-3 to 1-8). SR10.4 installs from cartridge tape on **any**
SR10.x and from magnetic tape on SR10.4 or later; pre-SR10.4 magnetic-tape
installs booted from **floppy disks**, "a process not described in this manual".
SR10.4 does **not require** disk initialization but recommends it, for disk
quotas and performance. **Table 1-1** is the SAU-to-machine map this plan has
cited: `/sau7` DN3500/3550/4000/4500 and the DSP variants, `/sau8` DN3000, `/sau9`
DN2500, `/sau10` DN10000, `/sau11` 9000/425S and 425T, `/sau12` 9000/400S and
400T, **`/sau14` DN5500** — and nothing else. **Table 1-2** lists the types SR10.4
drops (`/sau2`-`/sau6`), and "SR10.4 does not support any of the machine types
that support the use of storage modules". A node's own SAU number comes from
**`bldt`**, its machine type from `/com/netstat -config`. A DSP needs "a dumb
terminal to serial I/O line number 1 (**SI01**), an RS-232 port ... to act as the
system console" — which is where this core's runs type, and the reason
`siologin-blocker-is-above-the-interrupt` found Domain/OS serving `/dev/sio1`.

**Step 2, back up** (1-9 to 1-11). `wbak -dev ct0 -l -nhi -f end -fid <id> …`,
and the instruction that matters for a reader of a restored volume: **do *not*
back up `/sys` or `/com`** — "you want to use the new versions of these that get
installed with Domain/OS".

**Step 3, initialize and boot** (1-12 to 1-17), thirteen numbered steps:

| | |
| --- | --- |
| 1 | **NORMAL (versus SERVICE) mode**, a toggle switch on the back panel |
| 2 | `shut` to MD; wait for `SHUTDOWN SUCCESSFUL` and a prompt "always ending in a `>`" |
| 3 | `RE` `<RETURN>` `<RETURN>`, then the MD banner. "If the MD message does not appear after you press `<RETURN>` the second time, repeat the process" — this project's knock, in the manual |
| 4 | mount **`crtg_std_sfw_boot_1`**, write-disabled |
| 5 | `DI C` (`DI T` on a Series 2500) |
| 6 | **`EX CALENDAR`** — "ensures that the disk initialization program (`invol`) creates **correct Unique Identifiers (UIDs)** for the objects it creates on the disk" |
| 7 | `RE` |
| 8 | `DI C` |
| 9 | **`EX INVOL`** — option 1 (or 3), then option 8 for the paging file, `Anything more to do?` `y` then `n`. Chapter 3 is the detail |
| 10 | `RE` |
| 11 | `DI C` |
| 12 | **`EX CALENDAR` again** — "sets the correct time for objects subsequently installed on the disk" |
| 13 | `EX DOMAIN_OS`, `y` to `*** This program will replace system software on your disk.`, then **`GO`** at the `)` prompt |

**`GO` is the step this project never had.** It "starts the DM and the login
prompt appears. If you are at a DSP, the SPM is started" — and p. 1-18 has
`minst` starting **automatically on that login**. So `)` `GO` → login as `user`
→ `minst` is the whole of the hand-off from Step 3 to Step 4, and a script that
stops at the restore stops one command short of it.

**And the boot leaves a minimal Authorized Area** at the node's entry directory:
`/install/tools`, `/install/help`, `/install/doc/apollo`,
`/install/templates/apollo/os.v.10.4` and `/install/toc` — "The Domain/OS product
is **not** loaded into the Authorized Area at this time." This core's restore
console lists exactly those, `install/tools/cfgsa` and
`install/templates/apollo/os.v.10.4` included.

**Step 6, restore user files** (1-22): `rbak -dev ct0 -l -sacl -pdt -force -du
-fid <id> -all`, with `ct0`/`f0`/`m0` for the three media. Not this project's
path — the boot-volume restore is RBAK_BS, driven by `EX DOMAIN_OS`.

**Step 7, administrative tasks** (1-23 to 1-25). `ctnode <name> <node_id> -l -r
-root` then `ctnode -l -update` to catalogue the node, whose id `lcnode -me` or
`bldt` displays. And a fact that explains the SAU selection this project met on
the DN3500: **`minst` "unconditionally loads the `sau` directories for *all*
machine types supported by that release into the Authorized Area"**, in either
mode — so an AA always holds every SAU, and which `/sauN` reaches the *node* is
a `config` question. That is why `install-sau14.cmds`'s template **11** left
`sau7 sau8 sau9 sau11 sau12 sau14` in the AA.

## Chapter 3, *Running `invol`: A Detailed Account* — read whole, 3-1 to 3-11

**This is the chapter `tools/dn5500/README.md` was written in place of.** That
file lists "four things in the dialogue that C50's table does not have", each of
which cost a run here to discover. Three are in this chapter and the fourth
turns out to be a *conflict* rather than an omission.

| | README's correction, learnt by running the machine | the chapter |
| --- | --- | --- |
| 1 | "`Select disk:` is asked after **every** option, not only option 7" | **Confirmed.** p. 3-4 step 2 asks it after option 1; p. 3-7 step 2 asks it again after option 8, in the same words |
| 2 | "`Anything more to do?` follows an option" | **Confirmed.** p. 3-7 step 8 — `y` brings the menu back, and p. 3-8 step 5 — `n` ends `invol`, which "returns to the calling program (the Mnemonic Debugger or a shell)" |
| 3 | "Option 8 has two dialogues — the menu says *create or modify*" | Not settled here: the chapter documents the create path only |
| 4 | "The DS5500's default paging size is **1000 kB**, where the DN3500's is 640" | **A conflict, not a gap.** The prompt's default is `640` and the recommendation is "**2048 blocks for Series 10000 and Series 400** workstations, and **640 blocks for all other workstation types**" for SR10.2/10.3/10.4 (590 for SR10.0/10.1). A DS5500 is neither of the two named series, so the manual would put it at 640 — and the machine published 1000. The README's rule, "take the default the machine publishes, not the one another machine did", is the right one and now has a named disagreement under it |

The rest of the chapter, for the record:

- **The menu, verbatim** (p. 3-3), headed `invol (initialize_volume), revision
  10.4, April 22, 1991 1:20:13 pm` — the same banner the DS5500 printed. Options
  `0` EXIT, `1 [-fnb5um]` initialize virgin physical volume, `2 [-fnb5u]` add a
  logical volume, `3 [-fnb5]` re-initialize an existing logical volume, `4`
  delete, `5` list, `6 [-e]` list badspots, `7 [-f]` initialize physical badspot
  list, `8` create or modify an os paging file, `9` add to badspot list, `10`
  **OBSOLETE**, `11` remove from badspot list, `12` configure disk quota table.
- **The flags.** `f` don't re-format, `u` don't prompt — use defaults, `n` make
  non-bootable volume, `b`/`5` bsd/sys5 unix acls, `m` multi-disk group. `b` and
  `5` are "superfluous as of SR10.4"; **`-u` and `-n` are recommended against**;
  `-f` is recommended when the disk is not new, which is what makes option 1
  affordable against a file-backed medium here. `-m` "causes `invol` to display
  somewhat different prompts", so a striped group is a different dialogue.
- **`Select disk:`** is `[w=Winch|f=Floppy|q=Quit] [ctrl#:] [unit#]`, defaults
  controller 0 unit 0, so a single Winchester is just `w`.
- **The steps**: physical volume name; verification `1 - no verification`,
  `2 - write all blocks on the volume`, `3 - write and re-read all blocks`;
  `Expected average file size, in kB (CR for default, 5 kB)`; logical volumes as
  `"size, name"`, `all` for the rest, up to ten, terminated by a blank line;
  `Use pre-recorded badspot info?`; then `Initialization complete.`
- **Two structural facts** worth having beside `ap_awd.h`: a logical volume must
  be **at least 30 blocks and a multiple of the track size**, and **the physical
  volume label occupies the first block**, so the first logical volume is always
  one less than a multiple of the track size.
- **A machine-dependence in the formatting order**: on a Series 2500 or 400 with
  a SCSI disk, `invol` formats the whole disk immediately after the physical
  volume name and prints `Formatting`; "on other workstation types, `invol` does
  not format the disk until after you request badspot information in step 7".

## Part 1's introduction, pp. I-1 to I-13 (PDF 21-33) — read 2026-09-12

**The Authorized Area is the whole installation model** and this is where it is
defined. An Authorized Area is an ordinary directory whose only required feature
is an `install` subdirectory; products in it are dormant; getting an operational
product onto a node is **always two steps** — *load* from media into an
Authorized Area (`distaa` or `minst`), then *install* from there to a node
(`install`, `install++` or `minst`) — and "you cannot install a product directly
from media and bypass an Authorized Area". Installing Domain/OS from media on a
new node creates one automatically, which is why the DN3500 volume this project
built has `/install/ri.apollo.os.v.10.4` on it.

**Three facts that bear on media this project makes and reads:**

- "The administrative objects reside on the **first physical file — file 1 — on
  the first media volume**", separate from the products. That is the file the
  boot program restores to get the installation tools before Domain/OS itself.
- **"As of SR10.4, Domain/OS is distributed on cartridge tape and magnetic tape
  only, with a cartridge tape boot volume for both media types. Prior to SR10.4,
  Domain/OS was distributed on floppy disks as well ... with floppy disk boot
  volumes for the magnetic tape and floppy product media."** So an SR10.4 boot
  volume is *always* a cartridge, and the SR10.3 cartridge hunt this project ran
  was looking for the right kind of object.
- **"On all media types, the products are in `wbak` format"**, written by the
  `wbak` command.

**Naming, which a reader of an extracted volume needs**: a product directory is
`ri.apollo.`*name*`.`*version* — `ri.apollo.os.10.4` for SR10.4 — and each
contains a binary **release index** of the same name defining its configuration
questions. A version's last component distinguishes the **ISP type**: a digit is
m68k, a "p" is a88k (Series 10000, PRISM). `tools/awd_read.py` walks exactly
these directories on the DN3500 volume.

**The five core tools** are `distaa` (load from media), `config` (answer the
release index's questions into a configuration file), `install` (install a
configuration to nodes; also deinstall and reset permissions), `cfgsa` (restrict
what `config` may offer, and build selection files), `mrgri` (merge a patch or a
PSK into the product it patches, or merge the a88k and m68k versions). Two
layered ones: `install++` = `config` + `install`, `minst` = `distaa` +
`install++` **and** the restore of the administrative objects the others leave
to hand.

## Chapter 2, *Installing Domain/OS Across the Network*, pp. 2-1 to 2-28 (PDF 59-87) — read 2026-09-12

**The finding that matters to this project is the diskless boot.** Steps 5 and
12 of the workstation procedure:

    > DI N 0xxx        (Apollo Token Ring — xxx is the partner's hex node ID)
    > DI E 0xxx        (ETHERNET)
    > EX DOMAIN_OS

`DI` selects **another node as the boot device** and `EX DOMAIN_OS` boots the
target from it, "a process called *booting diskless*". The partner must be
running Domain/OS and **`netman`** (`cps /sys/net/netman` at its DM prompt, or
`/sys/net/netman &` at a shell), and must have the target's `/sau`*x* directory.

**Why that is worth having**: the ring plan item's verification needs *traffic*,
and `FINDINGS.md` C229 established that two booted nodes sitting idle exchange
none — "the operating system never armed a transmit". A diskless boot is the
opposite case: the target has **no disk of its own to read** and every page it
executes crosses the ring. It needs no shell, no `lcnode` and no `siologin`,
which is what the item has been waiting on. Recorded as a route, not run.

**Other facts this chapter states outright:**

- **"SR10.4 does not support any of the machine types that support storage
  module devices"**, so that whole class is out of scope for this core.
- **SR10.4 does not *require* disk initialization** on a node already running
  SR10.*x* — initialization is recommended "to take advantage of performance
  enhancements and new functionality, such as disk quotas".
- **`calendar` is run before `invol` and again after, and the first run is not
  optional**: "Running `calendar` at this point ensures that the `invol` program
  creates correct Unique Identifiers (UIDs) for the objects it creates on the
  disk", and the second "sets the correct time for objects subsequently
  installed". This project reached the same conclusion by running the machine
  ([[the-ds5500-route]]'s CALENDAR preamble); here it is stated.
- **`invol` option 1** initializes a virgin physical volume, **3** re-initializes
  an existing logical volume, **5** reports how many logical volumes a disk has,
  **8** creates or modifies the OS paging file. And **"as of SR10.4, Domain/OS
  dynamically allocates paging file disk blocks as needed. The size you specify
  with `invol` is the *initial* size, which then grows or shrinks as required."**
- Four commands that report a machine to itself: **`bldt`** prints
  `**** Node net_id.node_id **** "//node_name"` and the **SAU number in
  parentheses after `Domain/OS kernel`**; `bldt //partner` does the same for
  another node; **`/com/netstat -config`** or **`/etc/nodestat -config`** prints
  the machine type (for example `DN3500`); **`/com/lvolfs`** the volume's size.
- The MD dialogue is `RE`, `<RETURN>`, then the banner — `MD7C Rev. 6.0` in the
  book's example — and "the prompt depends on the node firmware, but **it always
  ends in a `>`**", which is what `tools/md-shell.sh` matches on.
- Mounting a target volume: `/com/mtvol {w|wx.y} [lv] /pathname` in Aegis, where
  `wx.y` is a Series 2500's controller and unit; `/etc/mount /dev/dsk/WNd0s1`
  (SysV) or `/dev/wnNa` (BSD), both needing `root`.
- `install++` is invoked as `AA/install/tools/install++ -vxs AA [-c config] target`
  and drives `config`'s `CONFIG>` prompt: `select os 10.x`, `configure os 10.x`,
  `reanswer`, `reconfigure`, `STOP`, `exit`. Errors in its transcript are
  prefixed `ERROR:` and warnings `WARNING:`, which is what a script greps for.

**And one trap stated outright, worth checking against this core's node model**:
after `EX DOMAIN_OS`, "**if the network has a net ID other than 0, the system
hangs when it attempts to start the standard daemons and does not finish
booting.** If this happens, physically disconnect the node from network, change
the net ID, and reboot." A booted Domain/OS that stops at the daemons is
therefore a *net ID* symptom before it is anything else.

**The DSP half of the chapter** (pp. 2-18 to 2-29) is the same procedure with
the target having no keyboard or monitor, and it names the commands that reach
one: **`crp -on `*node_id*** creates a process on the target from the partner and
opens a `crp` window on it, `/com/calendar` and `/etc/invol` are then run *in
that window*, **`shutspm`** logs out of it, and the target is reset "in an `emt`
window over a serial line or using a dumb terminal connected to serial line" —
`RE`, `<RETURN>`, `EX DOMAIN_OS`, which is exactly how `tools/md-shell.sh`
drives this project's machines.

**Cataloguing, which the multi-node item needs**: after initialization a node is
named `//node_`*node_id* from its own hexadecimal node ID, and
`ctnode `*name*` `*node_id*` -l -r -root` gives it a name in the master network
root while `ctnode -l -update` fills its local registry with the other nodes'
names. **`lcnode -me`** prints a node's own ID — the command the ring item names,
confirmed here with its switch.


## Chapter 6, *Restricting Product Configurations*, pp. 6-1 to 6-9 (PDF 135-143) — read 2026-09-12

**Nothing here is about hardware, and that is the finding.** `cfgsa` is an
administrator's tool for constraining what `config` may offer: for each of a
product's configuration questions the administrator enters `answer` (preselect,
and the question never appears), `limit` (present a reduced answer set) or
`user` (the default, no constraint), with `help`, `refresh` and `abort`
alongside; `show` displays the constraints, `revert` drops them, `save` writes
them and `exit` leaves. The result is an **override file** named
`ri.apollo.`*product*`.v.`*version* in *AA*`/install/overrides`, and being in
that directory is what makes it *active*; `generate` writes a non-active one
plus a selection file for Chapter 7's use.

The worked example lists an Authorized Area's products — `ada 3.0`, `c++ 2.0.0.m`,
`dsee 3.3.2`, `hpvue 1.0`, **`os 10.4`**, `pas 8.8.m`, `pas 8.8.mpx` — which is
the naming convention Part 1's introduction gives, seen in use, and the `.mpx`
suffix is the a88k ISP.

*Recorded at this length on purpose*: a walk record that says only "no hardware
content" cannot be told from a chapter nobody opened.
